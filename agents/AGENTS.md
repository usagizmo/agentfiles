# AGENTS.md

## タスクの進め方

規模の定義（各 skill が参照する SSOT）:

| 規模   | 定義                                                                 |
| ------ | -------------------------------------------------------------------- |
| 軽微   | 挙動を変えない局所変更（typo・コメント・等価リファクタ）             |
| 中規模 | 挙動変更あり（バグ修正を含む。局所でも該当。骨格は変えない）         |
| 大規模 | 責務・API・データフロー・永続形式・security/correctness 境界を変える |

### 作業単位

1 ブランチで直しきる。気づいた課題・既存不具合・周辺改善は、テーマが違っても場所が違っても同じブランチで片付ける。

- PR を機能ごとに**分割しない**。分けないのはブランチと PR で、コミット粒度は `commit` skill のまま
- コードは切り出さない。ブランチのスコープを大きく超えるものは、行き先の決定を人へ返す
- 文書は骨格を動かす変更（構成の組み替え・大幅な圧縮）**だけ**切り出す。線は骨格か中身かで引き、「走っている課題の予定範囲に当たるか」では引かない

切り出すと決めたものは、project が定める受け皿へ置く。まとめに残して**終わりにしない**。受け皿を持たない project では、現在のブランチで解消しきるか、行き先の決定を人へ返す。

文書の課題は、受け皿の中で最優先の位置へ置く（位置は project が定める）。欠陥と骨格の変更提案を区別しない。並べ替えは切り出した工程が行ってよい。

この節の適用主体は、実装ブランチを持つ工程。ブランチを持たない工程は、発見を受け皿へ置く。受け皿が無ければ人へ返す。

## 判断の分担

製品・機能の判断はユーザー。機能を足す・削る・仕様を変えるのは、指示か承認があるときだけ。「使われていなさそう」「あった方が便利」で増減**しない**。

それ以外はエージェントが決めきる。人に投げる前に `consult` で確証を上げる。判断基準が無いなら、基準を作って skill に書く。

ユーザーに判断を仰ぐときは、判断軸を添えて一般的な技術者が読んで分かる形にする:

- 前提 — 今どうなっているか。なぜ判断が要るのか
- 選択肢と各案の帰結 — 何を得て何を失うか。可逆かどうか
- 推奨 — どれを選ぶか + 理由
- 判断が変わる条件 — 前提のどれが違えば結論が変わるか

「A と B どちらにしますか」だけを**投げない**。ユーザーは細かい設計を把握していない前提で書く。専門用語には 1 行の説明を添える。

## 層契約

| 気づきの性質                                                      | 反映先                                                |
| ----------------------------------------------------------------- | ----------------------------------------------------- |
| 製品非依存の原則・作業衛生・default stack（「コーディング規約」） | 本ファイル                                            |
| skill の手順・基準・skill 間の棲み分け                            | 該当する共通 skill                                    |
| その project 固有                                                 | project の AGENTS.md / skills（上の追加・具体化のみ） |
| 特定 harness の起動・配線に依存する                               | その harness の設定側。本ファイルには書かない         |

- 両書き禁止。矛盾を見つけたら適用せず報告する（**例外は成立条件を明示**したとき）
- 上げるのは再利用できる判断だけ
- project 差分は skill 単位にも効く: 同名 `<skill>-project` skill があれば、本体 skill は手順を始める前に invoke し、追加・具体化のみ適用する。基準・手順・完了条件を**緩める記述は適用せず報告する**。`<skill>-project` は単体では invoke しない

## 設計原則

トップエンジニアが目指す、理想的で美しく合理的な設計を追求する。

優先順位（上位が優先）:

1. 根本解決を優先。部分パッチで済ませず、原因側を直す。明示された互換契約・migration・外部 API 安定性は守る
2. 構造の美しさ。ドメインに沿った設計、重複の一元管理（SSOT）、既存パターンとの整合性

実装方針:

- 不変条件・順序制約は型で固定する（コメントや env に頼らない）
- 最終形に不要なコードは初手から**書かない**（feature flag / deprecated alias / 互換 shim / 後で削除する前提の温存コード）
- production / test の差は型 (DI) で表す（env bypass で分岐**しない**）
- テストは落ちることを実測してから足す。回帰テストは修正を faithful に revert して、characterization test は対象を壊して落とす。修正前に落ちない回帰テストは characterization test と明示する

## ボーイスカウトルール

編集したコードの周辺を、着手前よりも綺麗にする。関連する改善（型の厳密化・dead code 削除・重複の共通化）は同じ変更にまとめる（切り分けは「作業単位」）。

- dead 判定は caller chain を実コードで辿る。grep 結果**だけで決めない**。判別不能ならユーザーに確認する
- 改善した箇所は完了時に簡潔に報告する

## 文章の書き方

動くために読む文章に適用する — 応答・Issue / PR 本文・commit message・コードコメント・AGENTS / skills / 開発者向け docs。

製品として顧客に見せる文章には**適用しない** — UI 文言・LP やマーケティングのコピー・ユーザー向け docs / メール / 記事。指定が無ければ既存のトーンに合わせる。

- 規則本文には規則だけを書く。理由は commit message に書き、本文へ写さない。判断の提示・検証結果・commit message には理由と根拠を書く
- 削る: 前置き・クッション語・ぼかし・自明な副詞・言い換え・装飾・時系列の経緯・作業の実況・実測値・失敗の事例
- 残す: 否定と限定と例外（ない・禁止・不可・のみ・だけ・除く・以外）・分岐に使う数値と単位・コードブロック・エラー文言の原文・SSOT の所在
- 規則は断定で書く。「〜した方がよい」ではなく「〜する」「〜しない」
- 規則の実体がコード（型・テスト・設定値）にあるなら、文書はその在処を指す 1 行にする。述語も既定値も**写さない**
- コードの理由は定義側の doc comment に置く。指した先を変えるときは、そのファイルを全文読む
- 規則を言い直さない。別の場所で要るなら参照で指す
- 確立した技術用語は訳さない（`dead code` `stale` `advisory` `lease`）。助詞は削らない。略語を新造しない（`cfg` `impl` `req`）
- 文書を編集したら、触った範囲をこの形へ寄せる（範囲の切り分けは「作業単位」）。記法（強調・表・折り返し・Markdown）と理由を別ファイルへ出す条件は agent-facing 文書**だけ**の規則で、`docs` skill が持つ

## コーディング規約（default stack: Bun / TypeScript / Svelte 5）

ツール（runtime / test runner / linter / formatter）は新規に入れるときの default。既に採用済みのものがある repo はそれに従う。採用済みの判定は repo 内の設定ファイル・lockfile・`packageManager`で、コマンドが在ることは根拠に**ならない**。言語・書き方の規則は常時適用する。

### lint / format

- linter / formatter は repo の依存に入れ、global に**置かない**。global に置くのはランタイム（node / bun 等）まで
- 設定ファイルが在る repo でだけ走らせる
- oxlint / oxfmt を使う

### ランタイム（Bun）

- test runner は `bun test`
- Bun 組み込み（`Bun.*` / `bun:*`。例: `Bun.file` `Bun.Glob` `Bun.TOML` `bun:sqlite`）に対応物が無いものだけ、依存または `node:*` を使う
- 成果物が Node で動く code（判定: `engines.node` / Node adapter / 公開ライブラリの dist）では Node 互換 API だけを使う

### TypeScript

- ソースは `.ts` で書く。`.js` / `.mjs` / `.cjs` を書か**ない**（ツールが拡張子を要求する設定ファイルは除く）
- `any` **禁止** → `unknown` または適切な型
- `interface` より `type` を優先
- デバッグログは `console.debug`

### Svelte 5 Runes

- 派生値は `$derived` / `$derived.by`（getter で代替**しない**）
- リアクティブな Map/Set は `SvelteMap` / `SvelteSet`（リアクティビティ不要なら `new Map` / `new Set` で可。lint 抑止時は理由を書く）
- Rune を使う TS ファイルは `.svelte.ts`
