# AGENTS.md

## 判断の分担

製品・機能の判断はユーザー。機能を足す・削る・仕様を変える・人に見せる面を変えるのは、指示か承認があるときだけ。「使われていなさそう」「あった方が便利」で**増減しない**。

それ以外はエージェントが決めきる。人に投げる前に `consult` で確証を上げる。

ユーザーに判断を仰ぐときは、細かい設計を把握していない前提で、次を添える:

- 前提 — 今どうなっているか。なぜ判断が要るのか
- 選択肢と各案の帰結 — 何を得て何を失うか。可逆かどうか
- 推奨 — どれを選ぶか + 理由
- 判断が変わる条件

## 設計原則

トップエンジニアが目指す、理想的で美しく合理的な設計を追求する。

1. **ゼロベース**。いまのコードから差分を積まず、ゼロから設計した理想形を描いてから、そこへ向かう差分を取る
2. **根本解決**。部分パッチで済ませず、原因側を直す。明示された互換契約・migration・外部 API 安定性は守る
3. **構造の美しさ**。ドメインに沿った責務分割、SSOT、既存パターンとの整合

- 不変条件・順序制約は型で固定する（コメントや env に頼らない）
- 最終形に不要なコードは初手から**書かない**（feature flag / deprecated alias / 互換 shim / 後で削除する前提のコード）
- production / test の差は型 (DI) で表す（env bypass で**分岐しない**）
- テストは落ちることを実測してから足す。回帰テストは修正を revert して、characterization test は対象を壊して落とす

## ボーイスカウトルール

編集したコードの周辺を、着手前よりも綺麗にする。気づいた課題・既存不具合・周辺改善は、テーマが違っても場所が違っても同じブランチで直しきる。PR を機能ごとに**分割しない**。

- dead 判定は caller chain を実コードで辿る。grep 結果**だけで決めない**。判別不能ならユーザーに確認する
- ブランチのスコープを大きく超えるものは、無言で捨てず、行き先の決定を人へ返す
- 改善した箇所は完了時に簡潔に報告する

## 規模

**軽微**は挙動を変えない局所変更（typo・コメント・等価リファクタ）。それ以外は**中規模以上**。

## 層契約

| 気づきの性質                              | 反映先                                                       |
| ----------------------------------------- | ------------------------------------------------------------ |
| 製品非依存の原則・作業衛生・default stack | 本ファイル                                                   |
| skill の手順・基準・skill 間の棲み分け    | 該当する共通 skill                                           |
| その project 固有                         | project の AGENTS.md / `<skill>-project`（追加・具体化のみ） |
| 特定 harness の起動・配線に依存する       | その harness の設定側                                        |

両書き禁止。矛盾を見つけたら適用せず報告する。上げるのは再利用できる判断だけ。

同名の `<skill>-project` skill があれば、本体 skill は手順を始める前に読み、追加・具体化のみ適用する。基準・手順・完了条件を**緩める記述は適用せず報告する**。`<skill>-project` は単体では invoke しない。

## 文章の書き方

動くために読む文章（応答・Issue / PR 本文・commit message・コードコメント・agent-facing 文書）に適用する。製品として顧客に見せる文章には**適用しない**。

- 規則本文には規則だけを書く。理由は commit message か定義側の doc comment に置く
- 削る: 前置き・クッション語・ぼかし・言い換え・経緯・作業の実況
- 残す: 否定と限定と例外（ない・禁止・のみ・除く）・分岐に使う数値と単位・エラー文言の原文・SSOT の所在
- 規則は断定で書く。規則の実体がコードにあるなら在処を指す 1 行にし、述語も既定値も**写さない**
- 確立した技術用語は訳さない。略語を新造しない

## コーディング規約（default stack: Bun / TypeScript / Svelte 5）

新規に入れるときの default。既に採用済みのものがある repo はそれに従う。採用済みの判定は repo 内の設定ファイル・lockfile・`packageManager` で、**コマンドが在ることは根拠にならない**。

### lint / format

- linter / formatter は repo の依存に入れ、global に**置かない**。設定ファイルが在る repo でだけ走らせる
- oxlint / oxfmt を使う

### ランタイム（Bun）

- test runner は `bun test`
- Bun 組み込み（`Bun.*` / `bun:*`）に対応物が無いものだけ、依存または `node:*` を使う
- 成果物が Node で動く code（`engines.node` / Node adapter / 公開ライブラリの dist）では Node 互換 API だけを使う

### TypeScript

- ソースは `.ts` で書く。`.js` / `.mjs` / `.cjs` を**書かない**（ツールが拡張子を要求する設定ファイルは除く）
- **`any` 禁止** → `unknown` または適切な型
- `interface` より `type` を優先
- デバッグログは `console.debug`

### Svelte 5 Runes

- 派生値は `$derived` / `$derived.by`（getter で**代替しない**）
- リアクティブな Map/Set は `SvelteMap` / `SvelteSet`（リアクティビティ不要なら `new Map` / `new Set` で可。lint 抑止時は理由を書く）
- Rune を使う TS ファイルは `.svelte.ts`
