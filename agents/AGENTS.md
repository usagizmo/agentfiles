# AGENTS.md

## タスクの進め方

- 規模の定義（各 skill が参照する SSOT）:

| 規模   | 定義                                                                 |
| ------ | -------------------------------------------------------------------- |
| 軽微   | 挙動を変えない局所変更（typo・コメント・等価リファクタ）             |
| 中規模 | 挙動変更あり（バグ修正を含む。局所でも該当。骨格は変えない）         |
| 大規模 | 責務・API・データフロー・永続形式・security/correctness 境界を変える |

### 作業単位

**1 ブランチで直しきる**。気づいた課題・既存不具合・周辺改善は、テーマが違っても同じブランチで扱う。

- **実装中に気づいたものは直す**。テーマが違っても、別の場所でも、そのブランチで片付ける
- 目の前の課題を Issue へ逃がさない・PR を機能ごとに分割しない
- 分けないのはブランチと PR。コミット粒度は `commit` skill のまま

切り出すと決まったあとの行き先（Issue にするか、まとめに残すか）は `resolve`。

**適用主体は、実装ブランチを持つ工程**。自分ではブランチを持たない工程（キューを回すだけ・計画する
だけのもの）には適用対象が無いので、**そこに「発見を自分で抱えない」規約があっても矛盾ではない**。
**代わりに、ブランチを持たない工程は発見の行き先を持たなければならない** —— 抱えないだけで渡し先が
無いと、気づいたことが揮発する。

## 判断の分担

**製品・機能の判断はユーザー**。機能を足す・削る・仕様を変えるのは、指示か承認があるときだけ。
「使われていなさそう」「あった方が便利」で勝手に増減しない。

**それ以外はエージェントが決めきる**。人に投げる前に、まず `consult` で確証を上げる。
判断基準が無くて迷ったなら、**基準を作って skill に書く**（次から自動で決まる）。
人を呼ぶのは製品判断のときだけ、が到達点。

ユーザーに判断を仰ぐときは、**判断軸を添えて一般的な技術者が読んで分かる形**にする:

- 前提 — 今どうなっているか。なぜ判断が要るのか
- 選択肢と各案の帰結 — 何を得て何を失うか。可逆かどうか
- 推奨 — どれを選ぶか + 理由
- 判断が変わる条件 — 前提のどれが違えば結論が変わるか

**「A と B どちらにしますか」だけを投げない**。ユーザーは細かい設計を把握していない前提で書く。
専門用語には 1 行の説明を添える。

## 層契約

| 気づきの性質                                           | 反映先                                                |
| ------------------------------------------------------ | ----------------------------------------------------- |
| 製品非依存の原則・作業衛生・default stack（TS/Svelte） | 本ファイル                                            |
| skill の手順・基準・skill 間の棲み分け                 | 該当する共通 skill                                    |
| その project 固有                                      | project の AGENTS.md / skills（上の追加・具体化のみ） |
| 特定 harness の起動・配線に依存する                    | その harness の設定側。本ファイルには書かない         |

- 両書き禁止。矛盾を見つけたら適用せず報告する（例外は成立条件を明示）
- 作業中に気づいた改善は上表に従って反映する。一回限りの判断は上げず、再利用できる判断だけを上げる。自明な修正はその場で直し、判断が要るものはユーザーに提案する
- project 差分は skill 単位にも効く: 同名 `<skill>-project` skill が存在すれば、本体 skill は自分の手順を始める前にそれを invoke し、追加・具体化のみ適用する。基準・手順・完了条件を緩める記述は適用せず報告する。`<skill>-project` は単体では invoke しない

## 設計原則

トップエンジニアが目指す、理想的で美しく合理的な設計を追求する。

優先順位（上位が優先）:

1. **根本解決を優先**: 部分パッチで済ませず、原因側を直す。明示された互換契約・migration・外部 API 安定性がある場合はそれを守る
2. **構造の美しさ**: ドメインに沿った設計、重複の一元管理（SSOT）、既存パターンとの整合性

実装方針:

- **不変条件・順序制約は型で固定する**（コメントや env に頼らない）
- **最終形に不要なコードは初手から書かない**（feature flag / deprecated alias / 互換 shim / 後で削除する前提の温存コード）
- **production / test の差は型 (DI) で表す**（env bypass で分岐しない）
- **回帰テストは「修正前に落ちる」ことを実測してから足す**（修正を faithful に revert して確認する）。緑であることは差を見分ける証拠にならない。落ちないならそれは回帰テストではないので、characterization test と明示する

## ボーイスカウトルール

編集したコードの周辺を、着手前よりも綺麗な状態にする。スコープが広がっても、関連する改善（型の厳密化、dead code 削除、重複の共通化など）は同じ変更にまとめる。分量増・テーマ違いを理由に後回しにしない。

- dead 判定は grep 結果だけでなく caller chain を実コードで辿る。判別不能ならユーザーに確認する
- 改善した箇所は完了時に簡潔に報告する

## 文章の書き方

**動くために読む文章に適用する** — 応答・Issue / PR 本文・commit message・コードコメント・AGENTS / skills / 開発者向け docs。

**製品として顧客に見せる文章には適用しない** — UI 文言・LP やマーケティングのコピー・ユーザー向け docs / メール / 記事。そこでは文体が製品仕様なので、指定が無ければ既存のトーンに合わせる。

### 文体

**端的に書く**。削るのは冗長さであって、判断材料ではない。短くすること自体を目的にしない。

- 削る: 前置き・クッション語（一応・とりあえず・基本的に）・ぼかし（〜かもしれない・〜と思われる）・自明な副詞（適切に・正しく）・同じ内容の言い換え・装飾・時系列の経緯（以前は〜だった・いつ変えた）・作業の実況（これから〜する・確認した）
- 残す: 否定と限定と例外（ない・禁止・不可・のみ・だけ・除く・以外）・数値と単位・コードブロック・エラー文言の原文・**規則が要る理由と数値の導出根拠**・SSOT の所在
- **確立した技術用語は訳さない**（`dead code` `stale` `advisory` `lease`）。訳すと判定範囲がぼやける（`dead code` →「不要なコード」にすると「動くが要らない」まで含み、到達不能という機械的判定が失われる）。確立した英語名が無い概念は説明的な日本語で書く
- **助詞は削らない**。落とすと係り受けが壊れ、条件の適用範囲が読み取れなくなる
- **略語を新造しない**（`cfg` `impl` `req`）。トークナイザはフル語と同じに分割するので節約はゼロで、読み手のデコードコストだけ増える

### Markdown 記法

- **強調の内側の端に置いた全角約物は、外側の文字次第で `**` を無効にする** — CommonMark の flanking 規則で、閉じ `**` は直前が約物・**直後が通常文字**だと閉じ記号と認められず、GitHub 等で `**` がそのまま表示される。開き `**` は直後が約物・**直前が通常文字**だと開き記号にならない
- 壊れるのは外側に通常文字が続くときだけで、行末・空白・約物が続くなら成立する。`**…ない。**続く文` と `する**「A」**は` は壊れ、行末の `**…ない。**` は成立する
- 壊れる並びになったら、約物を `**` の外へ出すか、`**` の外側に半角スペースを置くか、`<strong>` を使う

## コーディング規約（default stack: TypeScript / Svelte 5）

常時適用の薄い default。プロジェクト差分は各 repo の AGENTS.md / skills。

### lint / format

- **linter / formatter は repo の依存に入れ、global に置かない**。global にあると設定ファイルの無い repo でも既定値のまま完走するので、Prettier repo で `oxfmt .` を叩くと全ファイルが別の規則で書き換わる。global に置くのはランタイム（node / bun 等）まで
- **設定ファイルが在る repo でだけ走らせる**。**コマンドが在ることは採用の根拠にならない**
- 新規に入れるなら oxlint / oxfmt。既に ESLint / Prettier がある repo はそれに従う

### TypeScript/JavaScript

- `any` 禁止 → `unknown` または適切な型
- `interface` より `type` を優先
- デバッグログは `console.debug`

### Svelte 5 Runes

- 派生値は `$derived` / `$derived.by`（getter で代替しない）
- リアクティブな Map/Set は `SvelteMap` / `SvelteSet`（リアクティビティ不要なら `new Map` / `new Set` で可。ESLint 抑止時は理由を書く）
- Rune を使う TS ファイルは `.svelte.ts`
