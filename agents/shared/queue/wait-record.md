# 人に聞くとき

**人の答えを待って応答を終えるなら、聞く前に Issue コメントへ固定 marker で記録を残す**。質問の本文は記録側に置く。選択 UI や応答へ出すのは、記録を指す短い問いだけにする。

セッションは消える。**セッション文脈はキャッシュ、外部化した記録が復旧契約**。multiplexer が返す「人待ちの印」は即時観測用のキャッシュ。

## 発動点は「聞くこと」であって、止まる理由ではない

**述語は「人に聞いて、答えを待って応答を終えるか」の 1 つ**。各 skill の停止条件の表に当たったかどうかでは判定し**ない**。

**外からの依頼では発動点は立たない**。上位・人・他セッションのどれから書けと言われても、この記録自身の発動条件が偽なら書かない。依頼を受けて発動条件を再評価することは残る。人が本当に聞いて応答を終えるなら述語は真。

**発動点は聞くたびに立つ**。一度 `cleared` にした記録でも、もう一度聞くなら同じ記録を `waiting` へ戻す。「記録はもう書いた」で済ませ**ない**。

書かないと、外からはこう見える。

- 人待ちの SSOT は記録なので、**印はあるが記録が無い = `Conflict`** にしか見えない
- **詰まりの経過時間を出せない**（記録の更新時刻が無い）
- fail-closed なので上位のキュー管理は触れず、pane を読まないと何を聞かれているか人に伝えられない
- write を保持したまま止まっているのに、待ちの理由も経過時間も観測できない

## 書かないもの

**実行資源待ちは人待ちではない**。lease が空くのを待つ・休止を伝えられて止まる・CI や別セッションの完了を待つのは、答える人が居ない待ち。書く先はキュー管理側が持つ休止の記録だけで、**待つ側は何も書かない**。

**「待って応答を終えるときは 1 行書く」と取り違えない**。その 1 行は最後の応答に出すものであって、記録ではない。

書くと、機械側でこう転がる。

- `waiting` は実行器の状態ラダーの最上段（`人待ち`）に写るので、その課題は `休止` にも `待機` にも降りられない
- 枠を渡す経路は `待機` / `休止` にしか当たらないため、**二度と自動再開されない**
- 人には「答えれば進む詰まり」として表示されるが、答える質問が無い

理由の欄に「人待ちではない」と書いてあっても、**読む側は `state` しか見ない**。

## 記録が有効かどうか

**「いま待っている問い」が埋まっていることが、人待ちである証拠**。**履歴の側は見ない。**

| 観測                                            | 扱い                                                         |
| ----------------------------------------------- | ------------------------------------------------------------ |
| `waiting` + **「いま待っている問い」が非空**    | 人待ち                                                       |
| `waiting` + 空 + **同じ対象に休止の記録がある** | **人待ちではない**。`cleared` にして、実行資源待ちとして扱う |
| `waiting` + 空 + 実行資源待ちの証跡なし         | **壊れた記録**。自動で解除せず、証跡の矛盾として報告する     |

**空であることだけで解除しない**（本物の質問を選択 UI にだけ出して本文を書き損ねる経路がある）。

この述語を共有側に置くのは、書く側と読む側の両方が引くから。書く側は起こし直されたときにこれで自己修復し、読む側は無効な記録を `人待ち` に写さない。**片方だけに置かない。**

## 手順

1. **記録を upsert する**（下の形式。質問の本文まで書ききる）
   - 書く先は `same-branch.md`。**渡された番号が成員でも、書く先は変わらない**
   - 書く先のコメントを全部取る。**兄弟 Issue は見ない**（成員側の既存は探さない・消さない）
   - 単独行の `<!-- wait -->` を数える（コメント件数ではなく block 数）
   - 0 件なら 1 つ作る。1 件ならそのコメントを書き換える。2 件以上なら書かずに記録不能
   - `cleared` でも、工程が違っても、同じコメント。`phase` は欄を差し替えるだけ
2. **upsert が成功したことを確かめる**。失敗したら聞かずに「記録不能」として報告して終える
3. 記録の upsert を確かめたあと、その時点の SSOT から譜面全体を書き直す（条件は `score.md`）。**記録が質問の SSOT で、そちらは projection**。譜面そのものを作る順序は縛らない
4. 記録を指す短い問いだけを選択 UI / 応答に出す。**本文を二重に書かない**

**複数件をまとめて聞くときは、全対象の記録を書いてからまとめて聞く。**

## 形式

````markdown
<!-- wait -->

```yaml
state: waiting | cleared
issues: [<Issue 番号>] # 対象の列挙。書き先ではない
phase: <止まった工程の名前>
reason: <何が決まらないか。1 行>
```

<!-- /wait -->

## いま待っている問い

`waiting` のときだけ書く（聞き方は `~/.agents/AGENTS.md` —— 前提 / 選択肢と各案の帰結 / 推奨 /
判断が変わる条件）。**ここが質問の SSOT**で、選択 UI はこれを指すだけ。

## 決着した問答

### <日時>

問い / 決まったこと。
````

- **同じ marker のコメントを複数作らない**。状態が変わるときは既存コメントを書き換える
- 書き先は `same-branch.md`。Issue を持たない課題は PR のコメントに置く

**更新は上書きにしない。**

1. 更新する前に、いまの本文を取得する
2. **`yaml` と「いま待っている問い」だけを差し替える**
3. 決着した問いは「決着した問答」の先頭へ移す（**消さない**）
4. **空のテンプレートからコメント全体を作り直さない**
5. 更新したあと取得し直し、履歴が残っていることと、block が 1 つだけであることを確かめる

**`cleared` にするときは、問いを履歴へ移す。**

## 誰が書き、誰が消すか

| 操作                     | 主体                                                                                   |
| ------------------------ | -------------------------------------------------------------------------------------- |
| `waiting` にする         | 聞く当人（計画工程・解決工程のどちらも）                                               |
| `waiting` へ戻す         | **同じく当人**。聞き直すたびに戻す                                                     |
| `cleared` にする         | **同じく当人**。答えを解釈してから消す                                                 |
| `cleared` にする（例外） | **人待ちではないと判定した側**。書く側・読む側のどちらでもよく、先に観測した方が閉じる |
| `cleared` にする（例外） | **着地済み / 取り下げに達したら、片付ける側**                                          |
| `cleared` にする（例外） | **退避先へ移して終えるとき、当人**。答えを待たずに閉じる                               |
| 読む                     | 上位のキュー管理（人待ちの数え上げ・詰まりの表示）                                     |

- **人のコメントが付いただけで消さない**。答えかどうかの解釈は課題の中身の判断
- **`cleared` にしてから再開する**（`waiting` のままだと、外からは止まったままに見える）
- **`cleared` が意味するのは「いま回答を待っていない」だけ**。工程の要求・承認・完了は表さ**ない**
- **前提だけが崩れて待つのをやめるときは、要求が残るかを先に判定する**。残るなら問いを書き直して `waiting` のまま待つ

## 起こし直されたら

**起動したらまず記録を読む**。読む先は書き先と同じ（`same-branch.md`）。`waiting` のまま起こされたなら、前のセッションが死んでいる。

1. **まず「これは人待ちか」を見る**（上の 3 分類）。人待ちでないなら `cleared` にして、実行資源待ちとして待つ側の手順へ移る。**壊れているなら解除せずに報告する**
2. 人がまだ答えていない → **質問を出し直して待つ**。**例外は計画工程**で、待たずに終える経路を持つ（述語と手順はそちらの skill）
3. 人が既に答えている → 解釈して `cleared` にしてから続ける
