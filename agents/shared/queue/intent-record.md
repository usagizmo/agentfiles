# 意図の確認の記録

「実物を見せて、明示的な承認を得た」ことを外部化したもの。

**人待ちの記録では代用できない**。あれは「いま回答を待っているか」を表すので、`cleared` は「もう待っていない」しか意味しない。待つのをやめた理由が「前提が崩れたから」でも同じ値になるので、要求が果たされたかは復元できない。

**セッションまとめでも代用できない**。あれは報告者の推奨であって、人の承認ではない。PR 本文も、意図の確認より後に作られる projection。

## 要るかどうか

**新しい API / CLI / 公開 surface・UI の見た目と操作・設計骨格を変えた**なら要る。それ以外（test に固定できた不具合修正・挙動を変えないリファクタ・docs のみ）は要らない。**要否と結果は、要らないと判定したときも残す**（下記 `not-required`）。

````markdown
<!-- intent -->

```yaml
state: pending | confirmed | not-required
issues: [<Issue 番号>] # 対象集合の全番号
revisions: # 着地面ごとに、見せた時点の head。何を見せたかを固定する
  <owner>/<repo>: <SHA>
reason: <要らないと判定した根拠> # not-required のときだけ
```

<!-- /intent -->

## 見せたもの

<何を、どうやって見せたか>

## 項目ごとの状況

| 項目 | 状況 | 誰が何を承認したか |
| ---- | ---- | ------------------ |
````

同じ marker のコメントを複数作らない。**代表の Issue に 1 つ**（帰属は `same-branch.md`）。Issue を持たない課題は制御面の PR のコメントに置く。**どちらも無いなら着地させない** —— 置き場が無いことを理由に免除すると、最後の砦が、いちばん人の目に触れていない課題で外れる。

**PR を使わない面だけに着地する課題は、PR を持たない**（`landing-surface.md`）。確認が要る変更をそこで扱うなら、**制御面へ Issue を立ててから着手する** —— 着地の直前に置き場が無いと分かっても、そこから作れるのは記録だけで、承認を得る時間は残っていない。

## 3 つの状態

| 状態           | 意味                                                        |
| -------------- | ----------------------------------------------------------- |
| `pending`      | 確認が要るのに、**必要な項目すべての明示承認がまだ無い**    |
| `confirmed`    | 対象の `revisions` の必要項目が**すべて明示的に承認された** |
| `not-required` | 要否の述語の除外側に当たる。**理由と `revisions` が要る**   |

**沈黙は承認ではない**。指摘が返らなかった項目は `confirmed` に数えない。**部分承認は全体を `pending` のまま**にし、項目ごとの状況を本文に残す。

`not-required` を書くのは当人でよい。要否は製品判断ではなく、工程表の述語を diff に当てる技術判断。ただし**自由記述にしない** —— 除外側に明確に当たるときだけで、「UI 変更だが小さい」「既存仕様の延長」「たぶん期待どおり」は理由にならない。迷ったら `pending`。

**記録があること自体は、判定が正しい保証にはならない**。防げるのは無記録・沈黙・状態消失による素通りで、誤判定まで機械的には防げない（防ぐには全変更を人が承認するしかなく、除外の述語を持つこと自体と両立しない）。

## 人待ちの記録との順序

別軸だが、遷移の順を固定すると途中状態が必ず着地を止める側へ倒れる。

| 局面         | 順序                                                                                                                     |
| ------------ | ------------------------------------------------------------------------------------------------------------------------ |
| 確認を求める | 人待ちを `waiting` にして質問を書く → **この記録を `pending`** にして人待ちのコメントを指す → 見せる                     |
| 回答を得た   | 回答を解釈して **`confirmed` にする** → 人待ちを `cleared` にする（**枠を待つ variant はそのあと渡し直されるのを待つ**） |

**`pending` なのに人待ちが `cleared` か欠落しているのは、証跡の矛盾**。上位は着地させずに報告する。

## 失効

**確認の対象になった面をまた変えたら失効する**（判定は要否と同じ述語）。

戻すのは当人で、契機は工程を問わない。書き換えたその場で、**人待ちを `waiting` にしてから記録を `pending` へ戻す**（順序は上の表と同じ。逆にすると証跡の矛盾として観測される）。確認は提出の後に置いてあるので、この窓は CI の赤を直すときだけに狭まっている。

**rebase や無関係な追随では失効しない**。SHA の一致で判定すると、統合先へ追随するたびに確認し直すことになり、確認そのものが形骸化する。`revisions` は何を見せたかを後から辿るために置いてあるだけで、失効の述語ではない。

## 着地の前に確かめる

**有効な `confirmed` か `not-required` が無いなら着地しない。**

**枠を待つ variant にだけ任せない**。人が直接走らせた課題はキュー管理を通らずに着地できるので、着地する操作そのものが最後の砦になる。判定するのは記録の状態と必須の欄だけで、承認の中身は解釈しない。

**`issues` が現在の対象集合と一致していることも見る**。照合は `issues` で行う ——加入で対象集合が増えたら増えた分は確認されていないので、一致しないなら着地させない（加入させた側が `issues` を更新し、増えた分に確認が要るなら `pending` へ戻す）。
