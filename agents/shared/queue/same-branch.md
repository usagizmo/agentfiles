# `Same branch as #N`

Issue 本文の先頭区画に書く宣言。「この課題は #N と 1 本のブランチで直す」という意味を持つ。気づいた側が、関係する全 Issue の本文へ相互に書く。

この宣言で結ばれた Issue の集合を **group** と呼ぶ。group は**推移的に閉じる** —— A↔B と B↔C が書かれていれば A・C も同じ group。相互記載が漏れていても、辿れる限りを 1 つとして扱う。

## 書く条件

**片方だけ直すと、もう片方が同じ場所を二度触る**とき。テーマが近いだけでは書か**ない**。

## 隣接する記法との違い

| 記法                | 意味                                  | 作業単位 |
| ------------------- | ------------------------------------- | -------- |
| `Same branch as #N` | **同居** — 1 本のブランチで一緒に直す | 同じ     |
| `Depends on #N`     | **順序** — #N を先に片付ける          | 別       |
| `Refs #N`           | 関連するだけ                          | 別       |

**`Lands in <owner>/<repo>` はこの表に入らない**。あれは場所の宣言で、他の課題を指さない（意味論は `landing-surface.md`）。

## 宣言の形と置き場所

**本文の先頭区画（最初の見出しより前）で、行頭が `Depends on #N` / `Same branch as #N` / `Lands in <owner>/<repo>` である行だけが宣言**。他の場所に現れた同じ文字列は散文の言及であって、関係としては読まれない。

**3 つとも同じ規則に相乗りする**（置き場所の規則を宣言ごとに分けない）。

| 条件         | 何を担うか                                         | これだけだと                                   |
| ------------ | -------------------------------------------------- | ---------------------------------------------- |
| **行頭**     | 誤検出を塞ぐ                                       | セクション外の散文が行頭から始まったときに通る |
| **先頭区画** | 置き場所の一意化と、場所を外れた宣言を検知する基準 | 塞げない —— 誤検出は散文の**行中**で起きる     |

- 行頭の `**` 装飾は許容する（`**Depends on #N**`）
- **1 行 1 宣言。理由は宣言に書かない**（理由は本文の該当節へ、番号を伴わない語で書く）
- **`Refs #N` は宣言に含めない**。置き場所も限定しない
- 先頭区画は宣言専用では**ない**。保留バナー・仕様変更の注記・判断材料の URL・課題の要約は追い出さない
- **本文全体の文字列一致で辿らない**

**宣言に見えるのに読まれない出現は、検知して人へ出す**（先頭区画の外に現れた一致）。**行頭かどうかで絞らない** —— バッククォートに包まれた本物の宣言が読まれず、検知にも掛からない。出す先は上位のキュー管理。

**書かないと決めたものを、先頭区画へ宣言記法で残さない**。否定形（「`Same branch as #N` は書かない」）でも、行頭にあれば宣言として読まれる。理由は番号や repo 名を伴わない語で書く（「同居宣言は書かない」「依存は張らない」「着地面は既定のまま」）。

## 他人の本文を触ってよいか

**軸は「その本文をいま誰が所有しているか」。**`ledger` の値で場合分けし**ない**。

この表が向いているのは計画工程。上位のキュー管理は宣言行の記入だけを行い、digest を持つ記録がある本文には触ら**ない**。

| 相手の状態                       | 相手の本文                                              | 自分の本文 |
| -------------------------------- | ------------------------------------------------------- | ---------- |
| 未計画で、計画セッションが無い   | 書く                                                    | 書く       |
| **計画セッションが生存している** | **触らない**                                            | 書く       |
| 計画済み                         | 書く ＋ 相手の在庫の鮮度を取り直す（`ready-record.md`） | 書く       |
| claim 済み                       | **触らない**（加入は下記の手順）                        | —          |

- 「生存している」に `retired-` へ rename されたものも含む
- **譲っても機能は失われない**。宣言は片方向でも group が成立するので、自分の本文にだけ書けば観測される。**この 1 行を落とさない**
- 両者が同時に譲ったときは group が形成されず、独立した 2 件の計画済みになる。**再形成の経路は残る**（譲った側が終われば、相手は「計画済み」の行に当たって書ける）
- **人が直接起こした計画セッションが二重になる経路は塞がない**（解決工程が同じ状況を裁定している）

## 本文に書く理由

Issue 本文はセッションより先に存在する。着手する側は、最初の 1 手で group 全体を 1 本として取れる。

**計画に書いた同居の宣言だけでは足りない**。claim してから計画コメントを書くまでの窓で、同じ group の別 Issue は未 claim に見える。本文の宣言はその窓を持た**ない**。

## 共有するもの

group は 1 セッション = 1 計画で進み、**着地面ごとに 1 branch = 1 worktree** を持つ。**共有している成果物は group の全 Issue に帰属する。**

| 共有するもの          | 帰属                                                 |
| --------------------- | ---------------------------------------------------- |
| **着地面**            | 全員（**全員が同じ集合。違えば claim しない**）      |
| remote branch / PR    | 全員                                                 |
| 固定 marker の記録    | 全員（書き先は下記）                                 |
| worktree / セッション | 全員                                                 |
| Status                | **claim 時に全員を進行中にする**（代表だけにしない） |
| 譜面                  | 全員（規則は `score.md`）                            |

固定 marker の記録の書き先:

- **claim 後は代表の Issue に 1 つ**（復旧時に 1 回で読める）
- claim 前の人待ちは、渡された Issue に書く（代表がまだ決まっていない）
- **在庫の鮮度だけ Issue 単位**（claim 前にしか書かれない）
- **セッションまとめ（`report` / `halt`）はこの規則の外**。置き場は `session-report.md`

**着地面の宣言が成員間で食い違う group は claim しない**。食い違いは同居宣言の側の誤りとして扱う。

## どちらの集合を見るか

| 状況                         | 見る集合                                                                  |
| ---------------------------- | ------------------------------------------------------------------------- |
| **claim 済み**（記録がある） | **対象集合**（記録の `members`）。正規化・選出・資源はすべてこれ          |
| **未 claim**                 | group（本文の `Same branch as` の推移閉包）。claim してよいかの判定に使う |

**group の `Depends on` は成員の和集合**。1 人でも未解決なら group ごと待つ。`Depends on` を引くすべての箇所でこの集合を使う（**用途を列挙しない**）。

## 代表

**最小番号。ただし claim した時点で固定する**（毎回本文から引き直さない）。claim 済みなら、記録の `representative` が代表。

本文にだけ足された番号は次の着地まで別扱い。加入させれば対象集合に入り、本隊と同じ `progress` になる。

## 対象集合

**対象集合は claim の記録が定める**。Status や assignee から推し量ら**ない**。

branch を作った直後に、代表の Issue へ固定 marker で記録する。

````markdown
<!-- claim -->

```yaml
representative: <代表の Issue 番号>
members: [<Issue 番号>] # 代表を含む全員
landing: [<owner>/<repo>] # 着地面
```

<!-- /claim -->
````

- **`landing` は claim の時点で書き、以後は動かさない**（意味論は `landing-surface.md`）。本文の宣言は入力で、**記録が SSOT**
- **宣言順を保って書く**（実行面は claim 後この順の先頭で決まる）
- **記録では省略できない**。既定（制御面 1 面）が効くのは本文の宣言が無いときだけ
- **記録の `landing` が欠落・空・不正なら `Conflict`**。既定へ丸め**ない**
- Status と assignee は台帳であって集合の定義では**ない**。記録にあるのに揃っていない成員は、埋める対象になる
- 本文の `Same branch as` に後から足されただけの番号は含まれ**ない**

**後から気づいて同じブランチで直したものは、加入させてから足す。**

1. Issue 契約が揃っているか確認する（欠けていれば加入させない）。**着地面の宣言が記録の `landing` と同じかも見る**
2. **claim の記録の `members` に番号を足す**（これで対象集合に入る）
3. Status を進行中にし、assignee を揃える
4. 計画の `alsoResolves` に番号を足す

2 が加入の実体。3 と 4 が途中で落ちても、記録にあれば埋められる。

記録が無いとき（人が直接渡したセッション）は、本文へ `Same branch as` を相互に書くのが加入。

## 実体を触るとき

**単位は group、1 回だけ**。片付け・起こし直し・資源の受け渡し・branch の削除は、代表の番号で 1 回行う。

- 着地面が複数ある実体は、面ごとに 1 回（branch と worktree がそれ）。「代表の番号で 1 回」を「1 つの実体につき 1 回」と読み替え**ない**
- セッションと資源の受け渡しは面をまたいで 1 つのまま
- 消す条件の実体は conductor の「片付ける」。終端が混ざっている group は `Conflict`
