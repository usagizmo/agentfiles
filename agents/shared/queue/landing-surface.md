# 着地面

課題の成果物が生まれる repo。**Issue が置かれた repo と同じとは限らない。**

宣言と帰属は `same-branch.md`（形・claim の記録・group の扱い）、面ごとの座標は project 差分が持つ。ここが持つのは**意味論** —— どの面が何を持つか、終端をどう判定するか、live checkout に何をしてよいか。

## 3 つの面

| 面         | 何を持つか                                                                          | 値                          |
| ---------- | ----------------------------------------------------------------------------------- | --------------------------- |
| **制御面** | Issue・Status・固定 marker の全記録・**claim の remote branch**・project 差分 skill | Issue が置かれた repo       |
| **着地面** | branch・worktree・commit・統合先・`progress` の成果物側・容量・検証・integration    | **集合**。既定は `{制御面}` |
| **実行面** | セッションが実際に書く木                                                            | 着地面ごとの worktree       |

**「作業ディレクトリを移す」と読まない**。単一 repo の前提は観測・容量・失効判定・片付けの所有判定にも入っている。

### 着地面は集合

- **単数にしない**。1 つの課題が 2 つの repo へ commit を作ることは通常運用
- **既定は `{制御面}`**。宣言があればそれが全体で、制御面は自動では入ら**ない**
- **claim より前に決まり、claim の記録へ固定する**（形は `same-branch.md`）。**以後は本文が変わっても動かない**
- 既定が効くのは本文の宣言が無いときだけ。claim の記録に欠けていたら `Conflict`。**「無ければ制御面」を記録の側にも当てない**

## claim の branch は制御面に置く

着地面が複数ありうるので、「どこで一意なら claim できたか」が決まらない。制御面 1 箇所に固定して、面の数に依らず防壁を 1 つにする。

**着地面の branch は同名のローカル branch**で、origin への push を要求し**ない**（push が人の領分である面がある）。

`progress` のラダーがどちらを引くかは、段で分かれる。

| 段                      | 引く先                                  |
| ----------------------- | --------------------------------------- |
| `準備中`（branch あり） | **制御面の claim branch**               |
| `実装中` 以降           | **着地面**の commit / worktree の dirty |

**`準備中` を着地面で引かない**（着地面の worktree は claim の後に作るので、claim 直後の窓で `未着手` に落ちる）。

## 統合先

**面ごとに 1 つ**。その面の base と追随の基準になる ref。PR を使わない面では終端の判定にも使う。

| 面           | 統合先                                                 |
| ------------ | ------------------------------------------------------ |
| 制御面       | `origin/<default branch>`                              |
| 宣言された面 | **project 差分の座標表が定める ref**（ローカルでよい） |

- **座標表に無い面は着地面として宣言できない**（fail-closed）
- **1 つの着地面を複数の制御面で共有しない**（branch 名に制御面が入らないので、同名 branch が別課題の成果として観測される）
- **PR を使えるのは制御面だけ**。必要になったら観測の側から広げる。座標だけ先に許さ**ない**
- 端末ごとに違う checkout path は座標表に置か**ない**。呼び出し側が `--surface-path <名前>=<checkout>` で渡す（`src/config.ts` の `resolveSurfaces`）

### 面を外す

**外してよいのは、その面を `landing` に持つ未終端の claim 済みの課題が 0 件のとき**だけ。

claim の記録の `landing` は claim の時点で固定され、以後は本文が変わっても動かない。**表を直しても、走っている claim は追随しない** —— 外した面を指したままの課題は終端に到達できず、`着地面が解決できない` で固定される。

0 件でないなら、外す前にその課題を片付ける。

| その課題の成果物 | 外す前に行うこと                   |
| ---------------- | ---------------------------------- |
| 無い             | claim を解いて `未計画` へ差し戻す |
| ある             | 新しい面で計画し直す               |

**面の移設もこれに当たる**（repo を分ける・統合する）。移設先を表へ足すことと移設元を外すことは別の手順で、条件が掛かるのは後者。

## 終端

**2 段で判定する。面ごとに判定し、課題として畳む。**

| 単位     | 終端の条件                                                                                                                     |
| -------- | ------------------------------------------------------------------------------------------------------------------------------ |
| **面**   | **座標表が定める着地の条件**を満たす（下記。**commit が 0 の面は透過**）                                                       |
| **課題** | **全着地面が終端または透過**、かつ **全着地面が dirty でない**（`0` のみ。読めなかった `-` は不可）、かつ **提出の証跡がある** |

**着地の条件は面の型で決まる。**

| 面の型          | 着地した                                                          | 着地してよい（`着地待ち`）       |
| --------------- | ----------------------------------------------------------------- | -------------------------------- |
| PR を使う面     | PR が `merged`                                                    | open PR があり、checks が緑      |
| PR を使わない面 | **提出済みの成果がいまの統合先に含まれる**（`session-report.md`） | 提出済み（終端している面を含む） |

- **PR を使わない面は、統合先への merge を終端条件にする**。commit と提出の証跡だけでは終端しない
- 面の状態（提出済み / 透過 / 統合済み）は `session-report.md`
- **連言にする**。観測できない面が 1 つでもあれば終端に達し**ない**
- `着地待ち` も同じ 3 つを要求する。違うのは面ごとの条件だけで、そちらは「**終端している、または着地してよい**」
- **dirty を面の行へ書かない**。「全面が dirty でない」は面の述語ではなく課題の述語
- **面ごとの条件に「終端している」を含める**。含めないと、先に着地させた面が条件を壊す
- **終端の判定は origin への push を要求しない**

## live checkout

**人と走っているセッションが読む checkout**（skill の symlink 先がこれ）。着地面の repo に 1 つある。

**読み取り専用の面として扱う**。行ってよい git 操作は 2 つ**だけ**。

| してよい                          | してはいけない                                                 |
| --------------------------------- | -------------------------------------------------------------- |
| fetch                             | 課題の実装で編集する                                           |
| 統合先への merge（`merge` skill） | dirty / 分岐を自動で解消する（`checkout` / `stash` / `reset`） |

- **dirty か、HEAD が統合先の branch でない状態は、報告して止まる**（fail-closed）。自動で直さ**ない**
- **統合先が upstream より先行していることは含めない**（push が人の領分の面ではそれが常態）
- **この検査が掛かるのは、実際に live へ merge するときだけ**（`merge` skill）。**課題の状態としては見ない**
- **容量に数えない**。どの課題の branch も持たないので帰属先が無い（repo の本体 checkout も同じ）
- 「編集しても走っている自分自身に反映されない」は制約では**ない**。正しい意味論として採る

## 実行面

**面ごとに 1 worktree**。「1 課題 = 1 branch = 1 worktree」は面の中で崩さ**ない**。

**cwd は、制御面が着地面に含まれるならその worktree、含まれないなら claim の記録の `landing` の先頭の面**（claim 前に決めるなら本文の宣言順の先頭）。

- **claim 後に本文を引き直さない**（人が `Lands in` を足したり並べ替えたりすると、worktree の無い面へセッションを置こうとする）
- **claim は宣言順を保って記録する**
- **project 差分 skill は制御面 checkout の絶対 path から読む。cwd で引かない**。読めなければ `interactive` に落ちて lease を一度も待たずに着地まで走る

## 面をまたぐ path の突き合わせ

`invalidationScope` と `expectedWrites` は面をまたぐので `<owner>/<repo>: <path>` の形を取りうるが、**git の diff が返す path は常に repo 相対**。素の文字列一致で比べると、接頭辞のぶん永久に非交差になる。

**面 S の変更を評価するときは、こう読む。**

| scope の書き方        | 面 S の評価で                                     |
| --------------------- | ------------------------------------------------- |
| `S: <path>`           | 接頭辞を外し、`<path>` として使う                 |
| 接頭辞の無い path     | 制御面の path とみなす（既定が制御面 1 面だから） |
| `T: <path>`（S 以外） | 使わない                                          |

- **制御面は着地面に含まれなくても、base と失効の判定からは外さない**（project 差分と共有ファイルがそこにある）
- **着地面に制御面以外がある課題では、scope の全要素に接頭辞を書く**。欠けていたら判定不能として交差扱い（読む側の fail-closed）
- **解釈できない形が混ざったら交差扱い**（fail-closed）

## 資源キーは着地面をまたがない

資源キーの path は repo 相対なので、別 repo の path は写像の定義域の外に落ちてキーを生まない（規則は project 差分）。**これは穴ではない** —— 同じファイルを別 worktree で書く 2 つの課題がぶつかるのは merge のテキスト衝突で、そこは integration lease と rebase が担当する。

**面ごとに write 資源キーを足さない。**
