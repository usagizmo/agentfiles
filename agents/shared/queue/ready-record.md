# 在庫の鮮度の記録

計画済みへ進めるときに書き、着手されるまでのあいだ鮮度を持つ記録。`refine` が書き、上位のキュー管理が読む。**書式と判定を別々の skill に置かない**（片方だけ直すと、書いた記録が永久に不正と判定されるか、不正な記録が永久に通る）。

`resolve` が書く計画（`plan`）は claim 後にしか存在しないので、在庫のあいだの鮮度を持つものが他に無い。記録が無いと、別の実装が着地して前提が崩れても誰も気づかず、claim してから作り直すことになる（そのときは既に容量 1 枠と write を握った後）。

## 形式

````markdown
<!-- ready -->

```yaml
readySha: <計画時点の制御面の default の SHA>
landingReadyShas: # 制御面以外の着地面がある課題では必須。面ごとの統合先の SHA
  <owner>/<repo>: <SHA>
issueDigest: <この Issue の本文のハッシュ>
invalidationScope: # 変わると結論が崩れる範囲。空にしない
  - <path / 契約> # 制御面以外の着地面がある課題では `<owner>/<repo>: <path>`
```

<!-- /ready -->
````

ハッシュの取り方は `body-digest.md`（`plan` と同じ規則。ここに書き写さない）。

同じ marker のコメントを複数作らない。更新するときは既存コメントを書き換える。

## 記録するのは自分の Issue 1 件だけ

**`plan` は対象集合の全件を持つが、`ready` は持たない**。単位が違う ——`plan` は claim 後で group が確定し 1 セッションが全員を持つ。`ready` は claim 前で、group の成員は 1 件ずつ別々に計画される。

ここで全件を書くと、後から成員 B を計画して本文を更新した瞬間に、先に計画済みだった A が失効する。A は未計画へ戻り、また計画され、B を触るとまた戻る —— 収束しない。

**group が揃っているかは、ここでは見ない**。何を評価し、どの単位で戻すかを決めるのは差し戻し側で、この記録が Issue 単位なのは、成員が 1 件ずつ別々に計画されるからでしかない。

## 書くときの順序

**この順でないと、自分の本文更新で即座に不一致になる。**

1. 本文を更新する
2. **更新後の本文を取り直して** digest を計算する
3. marker を upsert する
4. Status を計画済みへ進める

- **着地面に制御面以外があるなら、各要素へ面の接頭辞を書く**（書き方と読み方は `landing-surface.md`）。素の path は制御面のものとして読まれるので、**その面の統合先が進んでも永久に失効しない**
- **`invalidationScope` は空にできない**。空だと何にも交差せず、永久に失効しない（それでは記録を書いた意味が無い）。読んだ全ファイルではなく、変わると結論が崩れる範囲だけを書く。**広すぎ側の損失は作り直しの時間、狭すぎ側は検知漏れ**なので、迷ったら広く取る
- **`resourceKeys` / `expectedWrites` は書かない。**「どう作るか」は着手時に決まるので、ここでは書けない（書けないことは欠落ではない）
- **claim 後も消さない**。読むのは在庫のあいだだけと限定されている。消す操作を増やさず、差し戻しで計画済みへ戻ったときに鮮度情報が残る
- **他人の本文を触ったら、その Issue の記録も upsert する。**`Same branch as` の相互記載のように既に計画済みの Issue の本文を書き換えると、相手の digest が合わなくなって陳腐化する。書き換えた側がその場で digest を取り直せば、無関係な再計画を起こさずに済む。**触ってよいのは `issueDigest` だけ** —— `readySha` と `invalidationScope` は相手の計画結論に紐づく値で、自分の値へ差し替えると相手の失効検知が別の範囲を見にいく（陳腐化しないまま検知漏れになるので誰も気づかない）

## 読むときの判定

読む局面は差し戻し表（「在庫が陳腐化した」の行）が決める。ここに述語を書き写さない。それ以外の局面で読まないのは、`plan` が鮮度を持つため。

次のいずれかなら**陳腐化**（戻し先と後始末は差し戻し表の列が持つ）。

- `readySha..default` の変更が `invalidationScope` に交差する（**面をまたぐ path の突き合わせ方は `landing-surface.md`**。素の文字列一致で比べると、接頭辞の付いた scope が永久に非交差になって一度も効かない）
- **`landingReadyShas` のどれかから、その面の統合先までの変更が `invalidationScope` に交差する**
- **着地面に制御面以外があるのに、その面のキーが `landingReadyShas` に無い**（判定不能）
- `issueDigest` が現在の本文と一致しない
- 記録が無い

**判定できないものは陳腐化として扱う**（fail-closed）。個別の壊れ方を数え上げない —— block が読めない、キーが欠けている、SHA が解決できない、`invalidationScope` が空か文字列の配列でないなど、「交差を評価できない」はすべて同じ扱いにする。列挙すると、次の壊れ方が漏れたときに永久に失効しない在庫が残る。

**制御面だけで判定しない**。`invalidationScope` は着地面の path を持ちうるので（`<repo>: <path>` の形）、制御面の default しか見ないと**その範囲が動いても永久に失効しない** —— 交差を書いたのに検知されない在庫は、記録が無い在庫より悪い（陳腐化していないと積極的に主張する）。**制御面は着地面に含まれなくても必ず見る**（`landing-surface.md`）。
