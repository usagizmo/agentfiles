# Issue 契約

**Status を計画済みへ進める = 「この 6 つが本文に揃っている」という宣言**。1 つでも欠けたら移さない。
`refine` が書き、キュー管理が揃っているかを確認する。

## 項目と見出し

**見出しの字面が契約の実体**。本文に完全一致で在り、直下に中身があることが「揃っている」の定義。

| 見出し（完全一致）      | 中身                                    | 埋める人                                 |
| ----------------------- | --------------------------------------- | ---------------------------------------- |
| `## 目的と期待する結果` | 何を達成したら終わりか                  | エージェント（ユーザーの意図を確認して） |
| `## 受入条件`           | 真偽が言える文                          | エージェント                             |
| `## 非目標`             | やらないと決めたこと（理由ごと）        | エージェント                             |
| `## 確定済みの製品判断` | 「A を採用、B はしない」                | **ユーザー**                             |
| `## リスク`             | 配信・migration・security・外部サービス | エージェント                             |
| `## 依存`               | 理由だけ（無ければ「なし」）            | エージェント                             |

- **この表が字面の SSOT**。読む側（`conductor` の `src/contract.ts`）は一致を検査していて、片方だけ変えると `bun test` が落ちる
- **「中身がある」は空でないことまで**。項目の質は機械では測れないので、そこは工程の責任として残す
- **`## 依存` に番号を伴う宣言を書かない**。関係の宣言は本文の先頭区画へ、行頭に 1 行 1 件（形と置き場は `same-branch.md`）。ここに書くのは理由だけで、番号を伴わない語を使う

## 書き方

- **未決の判断を「エージェントが決めて」埋めない**。埋まっていない = まだ計画済みではない、が正しい
- **受入条件は原則で書く。識別子や箇所の列挙にしない**。主文は「〜という性質のものを残さない」と書き、列挙はその時点の実測として添えるだけにする。**列挙を直しきったことを完了条件にしない**
- **非目標が落ちると、着手後にスコープが際限なく広がる**。書かれていない不在は「漏れ」として読まれる
- **互換の扱いは必ず書く** —— 互換 shim / deprecated alias / feature flag / migration を持つか持たないかを、理由ごと。既定は「持たない」（`~/.agents/AGENTS.md`）
- **実行メタデータは本文に書かない**（base・worktree path・セッション ID・候補 SHA）。Project field・branch・PR に置く

## 入場を止める宣言

**「既存側だけで、これから来るどの候補とも非互換だと証明できる」ときに置く印**。置くと claim と write の新規貸し出しが止まる。いつ外すかは読む側（conductor 本文「入場を止める宣言」）。

**運ぶのは固定 marker のコメント**（着手後に本文へ書き足せない規約があるため）。**指紋に入る形でなければならない**。

````markdown
<!-- entry-block -->

```yaml
issues: [<Issue 番号>] # 対象集合の全番号
reason: <なぜ、これから来るどの候補とも非互換か。1 行>
```

<!-- /entry-block -->
````

**いつ置くかは project の領分。運び方はここが固定する**（形まで project に委ねると、読む側が観測する手段を持てない）。

**時間切れで解除しない**。
