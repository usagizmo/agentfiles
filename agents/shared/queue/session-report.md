# セッションまとめ

**全着地面の検証が終わり、PR を使う面では CI が緑になってから出す**。PR があればそこへコメントし、無ければ Issue コメントへ。同じものを枚へ載せて人に見せる。落ちている間に出すと、直すたびに書き直すことになり、人は古い版を読んだまま可否を決める。

**「CI が緑」を唯一の契機にしない**。CI を持たない着地面があり（面ごとの検証は project 差分）、そこだけの課題では契機が決まらなくなる —— **まとめの公開はその課題の `着地待ち` の gate なので、契機が決まらないと終端へ進めない。**

## 固定 marker を付ける

**本文の先頭と末尾に marker を置く**（`<!--` と `-->` で囲む形。PR へ出すときも Issue へ出すときも同じ）。中身は人が読む文章で、**機械可読な `yaml` block を持つのは `report` だけ**（下記の `heads` / `bases`）。`halt` は目印だけで、突き合わせる相手が無い。

**marker は 2 つあり、出た理由で使い分ける。**

| marker   | いつ                                                                                                     | 意味                   |
| -------- | -------------------------------------------------------------------------------------------------------- | ---------------------- |
| `report` | **少なくとも 1 面に統合先へ入っていない commit があり**、全着地面の検証が終わり、PR を使う面では CI が緑 | **提出した**           |
| `halt`   | 着地まで進めずに終える（下記の「止まるときも出す」）                                                     | 止まった。提出ではない |

**`report` には、提出した時点の面ごとの head と統合先の tip を書く。**

````markdown
<!-- report -->

```yaml
heads: # 着地面ごとに、提出した時点の branch の head。1 面でも欠けたら提出ではない
  <owner>/<repo>: <SHA>
bases: # 同じ面ごとに、提出した時点の統合先の tip
  <owner>/<repo>: <SHA>
```

（以下、人が読む本文）

<!-- /report -->
````

**成果が無いまま `report` を出さない。**課題側の終端は提出の証跡だけを見るので**、1 行も書いて
いない課題が `report` を出せば `着地済み` になり、実装せずに close されて実体ごと消える**。

**`bases` は、それを読む側でも確かめられるようにするためにある**。書く側の規約だけを防波堤に
すると、marker を 1 回誤って出すだけで成果ゼロの課題が枠を返して消える。

**読む側は、記録が妥当かを課題単位で見てから、面ごとに状態を引く。**

**記録が妥当（これを満たさない `report` は何にも使えない）**

- `heads` と `bases` のキーが**着地面の集合と完全に一致**する
- **全着地面で `bases` が `heads` の祖先か同一**（逆向き・無関係は無効）
- **どれかの面で厳密な祖先**（`bases..heads` が非空。提出の時点で少なくとも 1 面が先行していた）

**面ごとの状態**（`T` = その面の branch の現在の tip、`M` = その面の現在の統合先 tip）

| 面の状態     | 条件                                                                          |
| ------------ | ----------------------------------------------------------------------------- |
| **提出済み** | `heads = T`（記録した head が、いまの branch tip と一致する）                 |
| **透過**     | `heads = T` かつ `heads = bases` かつ **いまも `M..T` が空**（現在 0 commit） |

**どちらも `heads = T` を要求する**。落とすと、branch を統合先へ `reset` した後の古い `report` や、
履歴上の祖先 SHA を書いた偽の `report` が通る —— どちらも「記録した成果が実際にその branch に
在る」ことを確かめていない。**branch を消した後は引けない**が、そのときは既に片付けが済んでいる。

**透過だけ外さない。**外すと**、提出のあとで「書かないつもりだった面」へ commit した課題が滞留する**
—— その面は記録上ずっと透過なので課題は終端のまま、`実装中` に落ちてこず、write も非保持、
周回の記録も終端を数えない。再提出も退避も発火しない場所で止まる（**2 面に書く課題では通常運用の経路**）。

**透過は「記録上 0 commit」ではなく「いまも 0 commit」**。記録だけで決めると、上と同じ滞留が
別の入口から戻る。

**`bases` を現在の統合先と突き合わせない**。突き合わせると、**別の課題がその面へ着地して統合先が
動くたびに提出が無効になり、追随のたびに検証と提出をやり直すことになる**。`bases` が要るのは
妥当性の側（提出の時点で少なくとも 1 面が先行していたこと）だけ。

**解決できない SHA・欠けたキー・逆向きの祖先関係は無効に倒す**（fail-closed）。証跡が読めないことを
「証跡がある」と読むと、確かめずに着地する。

**引く側が要求するもの。**

| 誰が                 | 要求するもの                                                  |
| -------------------- | ------------------------------------------------------------- |
| 着地の直前（面ごと） | 記録が妥当 + **その面が「提出済み」**（他の面の状態は見ない） |

**課題全体がどの状態かは、ここでは決めない**。`progress` の述語（`着地待ち` / `着地済み` に何が要るか）は
`landing-surface.md` が SSOT で、そちらが必要に応じて上の面ごとの状態を引く。**両方に書くと、PR しか
持たない課題に有効な `report` を要求する読みと、merged PR で足りる読みが同時に成り立つ**（同じ観測から
`片付ける` と `提出中` の両方が導ける）。

**現在の git から range を測り直さない**。着地すると `統合先..head` は空になり、追随しただけでも
非空になる（どちらの向きにも壊れる）。記録した 2 つの SHA の祖先関係なら、object が残る限り
着地の前後で答えが変わらない。

**`heads` と `bases` には着地面を全部書く**。キーの集合が `landing` と完全に一致しないものは無効 ——
**載っているキーだけ照合する読み方を許すと、書かなかった面の後続 commit が検証されないまま merge される**し、
欠けたキーを「不一致」として数える実装も通ってしまう。

**存在だけで「提出済み」と読ませない**。まとめを出したあとに commit を積む・amend する・衝突を
解いて rebase する経路はどれも通常運用で、**worktree はまた clean に戻る** —— head を持たないと、
検証も報告もしていない変更が「提出済み + clean」として `着地待ち` に上がり、そのまま merge される。
**head が現在と食い違うまとめは提出を表さない**（読む側は `着地待ち` から落とし、書いた側は出し直す）。

`halt` は head を持たない。提出を表さないので、突き合わせる相手が無い。

**畳んで 1 つにしない**。`report` は PR を持たない面での「提出した」の唯一の観測材料なので（`landing-surface.md`）、**止まったまとめが同じ marker で出ると、検証に失敗した課題が `着地待ち` に化ける** —— clean な worktree とまとめが揃うだけで着地してよいと読まれる。理由が違うものを同じ目印にすると、読む側に区別する手段が無い。

| 誰が引くか            | 見るもの                                                                                                                        |
| --------------------- | ------------------------------------------------------------------------------------------------------------------------------- |
| 片付ける工程          | **どちらでもよい**（要るのは成果が残っていること）。**PR が無い課題では Issue コメントを探す**ので、marker が無いと推測になる   |
| `progress` を引く工程 | **有効な `report` だけ**（妥当性と面ごとの状態は上記）。`halt` と、古くなった `report` と、成果の無い `report` は提出を表さない |

**PR がある課題でも省かない。**省いてよい条件を作ると、面ごとに探し方が変わる**。同じ marker のコメントを複数作らない** —— 書き直すときは既存を書き換える（`halt` で出した後に提出まで進んだら、`report` へ書き換える）。

**出すのは全件。ただし提示は着地の gate ではない** —— 出したあと答えを待つのは意図の確認が要る変更だけで（要否は `intent-record.md`）、要らない課題はそのまま着地へ進む。全件を待たせると、人が居ない間はどれも着地しない。

応答は流れて消えるが、PR は変更と一緒に残る（閉じる Issue と違い、後から `git blame` → PR で辿れる）。日常的に読まれる場所ではなく、必要になったときに引ける場所として置く。

**読まれる場所は別に要る。**積み残しが無くても必ず Artifact にする —— 人が「何が起きたか」を読む唯一の面で、言うことが無いセッションほど、人は中身を知らないまま着地を迎える（計画の段階で必ず作るのと同じ理由）。**この課題の枚を書き直す**（引き当て・節の作り方は `artifact.md`）**。原本は PR があれば PR のコメント、無ければ Issue のコメント** —— PR を使う着地面が無い課題では PR が存在しないので、そこを原本にすると枚も片付け時の回収も置き場を失う。PR 本文へ枚の URL を併記するのは、PR があるときだけ。着地すると worktree ごと消えるので、引ける場所しか無いと積み残しはそのまま忘れられる。

**着地まで進めずに終えるときも出す**（CI が詰まって進まない・着地の前提が満たせない・人待ちのまま終える）。出さない条件にすると、着地しなかったセッションほど何も残らない。**そのときの marker は `halt`**。PR が無ければ同じものを Issue コメントへ残し、そちらを SSOT にする —— 原本の置き場が無いと枚も作れない。

- 変更の要点
- 変動した Issue すべて（作成・クローズ・更新。番号 + 一言）
- 積み残し・懸念点（下記の形式）
- **skill / docs へ反映したもの**と、**しなかったものとその理由**

**懸念は 1 件につき次を埋める。**「懸念がある」だけでは放置してよいか判断できない。埋まらない項目があるなら、その項目自体を「不明」と書く。

| 項目       | 中身                                                                |
| ---------- | ------------------------------------------------------------------- |
| 何が       | 観測した事実（推測と分ける）                                        |
| 影響範囲   | 誰の・どの操作が・どれくらいの頻度で当たるか                        |
| 放置すると | 次に何が起きるか。起きないなら「起きない」                          |
| 判断材料   | 選ぶために必要な事実（コスト・代替案・前例）                        |
| 推奨       | このブランチで続けて着手 / 対応不要 / 別 worktree へ切り出し + 理由 |

推奨を決める情報が足りなければユーザーに質問する。
