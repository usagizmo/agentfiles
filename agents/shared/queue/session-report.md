# セッションまとめ

**全着地面の検証が終わり、PR を使う面では CI が緑になってから出す**。PR があればそこへコメントし、無ければ Issue コメントへ。同じものを譜面へ載せて人に見せる。

**「CI が緑」を唯一の契機にしない**。CI を持たない着地面があるので、そこだけの課題では契機が決まらなくなる（まとめの公開はその課題の `着地待ち` の gate）。

## 固定 marker を付ける

**本文の先頭と末尾に marker を置く**（`<!--` と `-->` で囲む形。PR へ出すときも Issue へ出すときも同じ）。中身は人が読む文章で、**機械可読な `yaml` block を持つのは `report` だけ**。

**marker は 2 つあり、出た理由で使い分ける。**

| marker   | いつ                                                        | 意味                   |
| -------- | ----------------------------------------------------------- | ---------------------- |
| `report` | 記録が妥当。全着地面の検証が終わり、PR を使う面では CI が緑 | **提出した**           |
| `halt`   | 着地まで進めずに終える（下記）                              | 止まった。提出ではない |

**畳んで 1 つにしない。**`report` は PR を持たない面での「提出した」の唯一の観測材料なので、止まったまとめが同じ marker で出ると、**検証に失敗した課題が `着地待ち` に化ける**。

**`report` には、提出した時点の面ごとの head と統合先の tip を書く。**

````markdown
<!-- report -->

```yaml
heads: # 着地面ごとに、提出した時点の branch の head。1 面でも欠けたら提出ではない
  <owner>/<repo>: <SHA>
bases: # 同じ面ごとに、提出した時点の統合先の tip
  <owner>/<repo>: <SHA>
written: # この claim が書いた commit。`heads = bases` のときの証明。任意
  <owner>/<repo>:
    - <SHA>
```

（以下、人が読む本文）

<!-- /report -->
````

- **成果が無いまま `report` を出さない**（1 行も書いていない課題が出せば `着地済み` になり、実装せずに close されて実体ごと消える）
- **`heads` と `bases` には着地面を全部書く**。載っているキーだけ照合する読み方を許さ**ない**
- **`written` は、この claim が書いた SHA を面ごとに書く**。解決できない SHA は載せない
- **既存の妥当な `report`（`bases..heads` が非空）は、0-ahead になっても書き直さない**
- `halt` は head を持た**ない**（提出を表さないので、突き合わせる相手が無い）

## 読む側

**記録が妥当かを課題単位で見てから、面ごとに状態を引く。**`bases` は読む側でも確かめられるようにするためにある。

読み対象は Issue コメントと、紐づく制御面 PR（open または merged）の Issue コメント。closed-unmerged の PR は読み対象にしない。PR 一覧が読めないときは提出証跡を「無い」に倒さない。

`report` と `halt` だけを PR コメントから読む。claim / plan / wait / ready / intent / yield / integration / entry-block / written は PR コメントからは読まない。`halt` は提出証跡にしない。

記録が妥当（これを満たさない `report` は何にも使えない）:

- `heads` と `bases` のキーが**着地面の集合と完全に一致**する
- **全着地面で `bases` が `heads` の祖先か同一**（逆向き・無関係は無効）
- どれかの面で、`bases..heads` が非空 **または** `written` の SHA がいまの統合先 tip の祖先か同一

`written` は任意。無くても `bases..heads` が非空なら妥当。YAML の存在だけでは提出証跡にしない。

`bases..heads` は記録の値だけ見る。`written` だけ、いまの統合先 tip と突き合わせる。

面ごとの状態（`T` = その面の branch の現在の tip、`M` = その面の現在の統合先 tip）:

| 面の状態     | 条件                                                                          |
| ------------ | ----------------------------------------------------------------------------- |
| **提出済み** | `heads = T`（記録した head が、いまの branch tip と一致する）                 |
| **透過**     | `heads = T` かつ `heads = bases` かつ **いまも `M..T` が空**（現在 0 commit） |
| **統合済み** | `heads = T` かつ `heads ≠ bases` かつ **いまも `M..T` が空**                  |

- **どちらも `heads = T` を要求する**（落とすと `reset` 後の古い `report` や偽の `report` が通る）
- **例外は** head が無い（branch 削除）ときだけ。記録にその面のキーがあれば提出済み
- **透過だけ外さない**。外すと、提出のあとで「書かないつもりだった面」へ commit した課題が滞留する
- **透過は「記録上 0 commit」ではなく「いまも 0 commit」**
- **透過と統合済みを `M..T` が空であることだけで同一視しない**。差は `heads` と `bases` が同じかどうか
- **`bases` を現在の統合先と突き合わせない**（突き合わせると、追随のたびに検証と提出をやり直すことになる）
- **`bases..heads` を現在の git から測り直さない**（着地すると `統合先..head` は空になり、追随しただけでも非空になる）
- `heads` / `bases` の欠けたキー・逆向きの祖先関係・解決できない SHA は記録ごと無効
- `written` の SHA が解決できない、またはいまの tip の祖先でも同一でもないときは、その SHA を証明に使わない。`bases..heads` が非空なら記録は妥当のまま
- 統合先 tip が読めない、または祖先判定が `unobservable` のときは、記録を無効に倒さず `unobservable`
- **存在だけで「提出済み」と読ませない**。head が現在と食い違うまとめは提出を表さ**ない**

引く側が要求するもの:

| 誰が                  | 要求するもの                                                                                         |
| --------------------- | ---------------------------------------------------------------------------------------------------- |
| 着地の直前（面ごと）  | 記録が妥当 + **その面が「提出済み」**（他の面の状態は見ない）                                        |
| 片付ける工程          | **どちらの marker でもよい**（要るのは成果が残っていること）。PR が無い課題では Issue コメントを探す |
| `progress` を引く工程 | **有効な `report` だけ**。`halt` と、古くなった `report` と、成果の無い `report` は提出を表さない    |

**課題全体がどの状態かは、ここでは決めない**。`progress` の述語は `landing-surface.md` が SSOT。**両方に書かない。**

**PR がある課題でも marker を省かない**（省いてよい条件を作ると、面ごとに探し方が変わる）。**同じ marker のコメントを複数作らない** —— 書き直すときは既存を書き換える（`halt` の後に提出まで進んだら `report` へ）。

## 何を書くか

**出すのは全件。ただし提示は着地の gate ではない** —— 出したあと答えを待つのは意図の確認が要る変更だけで（要否は `intent-record.md`）、要らない課題はそのまま着地へ進む。

**着地まで進めずに終えるときも出す**（CI が詰まって進まない・着地の前提が満たせない・人待ちのまま終える）。**そのときの marker は `halt`**。PR が無ければ同じものを Issue コメントへ残し、そちらを SSOT にする。

- 変更の要点
- 変動した Issue すべて（作成・クローズ・更新。番号 + 一言）
- 積み残し・懸念点（下記の形式）
- **skill / docs へ反映したもの**と、**しなかったものとその理由**

**読まれる場所は別に要る**。積み残しが無くても必ず譜面にする（引き当て・節の作り方は `score.md`）。**原本は PR があれば PR のコメント、無ければ Issue のコメント**。Issue / PR に譜面のパスも URL も書か**ない**。

**懸念は 1 件につき次を埋める**。埋まらない項目があるなら、その項目自体を「不明」と書く。

| 項目       | 中身                                                                |
| ---------- | ------------------------------------------------------------------- |
| 何が       | 観測した事実（推測と分ける）                                        |
| 影響範囲   | 誰の・どの操作が・どれくらいの頻度で当たるか                        |
| 放置すると | 次に何が起きるか。起きないなら「起きない」                          |
| 判断材料   | 選ぶために必要な事実（コスト・代替案・前例）                        |
| 推奨       | このブランチで続けて着手 / 対応不要 / 別 worktree へ切り出し + 理由 |

推奨を決める情報が足りなければユーザーに質問する。
