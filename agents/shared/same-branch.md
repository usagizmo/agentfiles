# `Same branch as #N`

Issue 本文の先頭区画に書く宣言。「この課題は #N と 1 本のブランチで直す」という意味を持つ。気づいた側が、関係する全 Issue の本文へ相互に書く（形と置き場所は下記。`Depends on #N` と共通）。

この宣言で結ばれた Issue の集合を **group** と呼ぶ。group は推移的に閉じる — A↔B と B↔C が書かれていれば A・C も同じ group。相互記載が漏れていても、辿れる限りを 1 つとして扱う（閉じないと 1 つの group が 2 本のブランチに割れる）。

## 書く条件

**片方だけ直すと、もう片方が同じ場所を二度触る**とき。テーマが近いだけでは書かない。

## 隣接する記法との違い

| 記法                | 意味                                  | 作業単位 |
| ------------------- | ------------------------------------- | -------- |
| `Same branch as #N` | **同居** — 1 本のブランチで一緒に直す | 同じ     |
| `Depends on #N`     | **順序** — #N を先に片付ける          | 別       |
| `Refs #N`           | 関連するだけ                          | 別       |

**`Lands in <owner>/<repo>` はこの表に入らない**。上の 3 つは課題どうしの関係で作業単位を決める記法だが、あれは**場所**の宣言で、他の課題を指さない。軸が違うものを同じ表に並べると、同居宣言の付随物として読まれる（意味論は `landing-surface.md`）。

## 宣言の形と置き場所

**本文の先頭区画（最初の見出しより前）で、行頭が `Depends on #N` / `Same branch as #N` / `Lands in <owner>/<repo>` である行だけが宣言**。他の場所に現れた同じ文字列は散文の言及であって、関係としては読まれない。書く側の規則であると同時に読む側の定義でもあり、これらを引くすべての箇所がこの定義で観測する。

**3 つとも同じ規則に相乗りする**。置き場所の規則を宣言ごとに分けると、後から足した宣言だけが行中の誤検出を通す。

| 条件         | 何を担うか                                         | これだけだと                                   |
| ------------ | -------------------------------------------------- | ---------------------------------------------- |
| **行頭**     | 誤検出を塞ぐ                                       | セクション外の散文が行頭から始まったときに通る |
| **先頭区画** | 置き場所の一意化と、場所を外れた宣言を検知する基準 | 塞げない —— 誤検出は散文の**行中**で起きる     |

**2 つとも要る**。実際に、宣言記法に番号を続けた句が散文の行中に 2 つ現れ、その Issue が自分自身に依存していた（`Backlog` に居れば永久に解けない依存だった）。

- 行頭の `**` 装飾は許容する（`**Depends on #N**`）。既存の宣言の多くがこの形
- **1 行 1 宣言。理由は宣言に書かない** —— 理由は本文の該当節へ、番号を伴わない語で書く
- **`Refs #N` は宣言に含めない**。読み手が居ないものを宣言の集合へ混ぜると、機械が読む集合と読まない集合の区別が本文から消える。置き場所も限定しない（限定しても得るものが無い。先頭区画の行頭に実在する）
- 先頭区画は宣言専用ではない。保留バナー・仕様変更の注記・判断材料の URL・課題の要約が実際に置かれており、追い出さない（人が最初に読むべきものがそこにある）。共存できるのは、前書きの散文が行頭から宣言記法で始まらないため

**本文全体の文字列一致で辿らない**。両方を見る状態を残すと、どちらの読み手に当たったかで結果が変わる期間ができ、塞いだはずの誤検出がその期間だけ生き残る。

**宣言に見えるのに読まれない出現は、検知して人へ出す**（先頭区画の外に現れた `Depends on #N` / `Same branch as #N` / `Lands in <owner>/<repo>` の一致。**行頭かどうかで絞らない** —— バッククォートに包まれて別の節に書かれた本物の宣言が実在し、それは新しい読み手では読まれず、行頭で絞った検知にも掛からない。依存が黙って消える）。出す先は上位のキュー管理。

**書かないと決めたものを、先頭区画へ宣言記法で残さない。**否定形（「`Same branch as #N` は書かない」）でも、行頭にあれば宣言として読まれる。`Same branch as #N` なら相互記載の無い片肺 group を、`Depends on #N` なら永久に解けない依存を作る（claim もされず・在庫にも数えられず・陳腐化もせず、ボードには着地しない前提が並び続けるので、誰も異常と気づけない）**。`Lands in` なら着地面が制御面から動き、worktree も終端判定も別 repo を見にいく**。ここでも理由は番号や repo 名を伴わない語で書く（「同居宣言は書かない」「依存は張らない」「着地面は既定のまま」）。

## 他人の本文を触ってよいか

**軸は「その本文をいま誰が所有しているか」**。`ledger` の値で場合分けすると、計画セッションが走っている最中が表から抜ける。

この表が向いているのは計画工程（本文を書くのはそこ）。上位のキュー管理は宣言行の記入だけを行い、digest を持つ記録がある本文には触らない —— そちらの規約は上位側が持つ。

| 相手の状態                       | 相手の本文                                              | 自分の本文 |
| -------------------------------- | ------------------------------------------------------- | ---------- |
| 未計画で、計画セッションが無い   | 書く                                                    | 書く       |
| **計画セッションが生存している** | **触らない**                                            | 書く       |
| 計画済み                         | 書く ＋ 相手の在庫の鮮度を取り直す（`ready-record.md`） | 書く       |
| claim 済み                       | **触らない**（加入は下記の手順）                        | —          |

「生存している」に `retired-` へ rename されたものも含む（人が入力を書いている最中なので、所有者は生きている）。

触らない理由は、生きた書き手の本文を上書きすると相手が書いた宣言行が黙って消えるから。digest のずれは在庫の鮮度が 1 往復で自己修復するが、**消えた行と、1 つの group に 2 つできた独立な計画は戻らない**。

**譲っても機能は失われない**。宣言は片方向でも group が成立する（上記のとおり推移閉包は辿れる限りを 1 つとして扱う）ので、自分の本文にだけ書けば観測されるようになる。**この 1 行を落とさない** —— 落とすと、次の読み手が「相互記載しないと壊れる」と読んで譲れなくなる。

両者が同時に譲ったときは group が形成されず、独立した 2 件の計画済みになる。これは「誰も関係に気づかなかった」場合と同じ結末で、壊れた group より安全な倒し方。しかも再形成の経路が残る —— 譲った側が終われば、相手は「計画済み」の行に当たって書ける。

**人が直接起こした計画セッションが二重になる経路は塞がない**。解決工程が同じ状況を既に裁定しており（直接頼んだ側が引き受ける）、コードを書く側で意図的に開けている穴を、本文しか書かない側で塞ぐのは整合しない。

## 本文に書く理由

Issue 本文はセッションより先に存在する。だから着手する側は、最初の 1 手で group 全体を 1 本として取れる。

## 共有するもの

group は 1 セッション = 1 計画で進み、**着地面ごとに 1 branch = 1 worktree** を持つ（着地面が 1 面なら 1 本ずつ）。**共有している成果物は group の全 Issue に帰属する** — branch 名に入るのは代表番号だけなので、Issue ごとに引くと非代表が永久に「何も無い」ように見える。

| 共有するもの                                                     | 帰属                                                                                                                           | 書き先                                                                                                                                                                                                                                                                                                                                                                   |
| ---------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------ | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| **着地面**                                                       | 全員（**全員が同じ集合。違えば claim しない**。下記）                                                                          | claim の記録に 1 つ                                                                                                                                                                                                                                                                                                                                                      |
| remote branch / PR                                               | 全員                                                                                                                           | —                                                                                                                                                                                                                                                                                                                                                                        |
| 固定 marker の記録（**在庫の鮮度とセッションまとめを除く全部**） | 全員                                                                                                                           | **claim 後は代表の Issue に 1 つ**（復旧時に 1 回で読める）。claim 前の人待ちは、渡された Issue に書く（代表がまだ決まっておらず、2 人が同じコメントを書き換え合う）。**在庫の鮮度だけ Issue 単位** —— claim 前にしか書かれず、代表がまだ無い。**セッションまとめ（`report` / `halt`）はこの規則の外**で、置き場は `session-report.md` が持つ（PR があれば PR コメント） |
| worktree / セッション                                            | 全員                                                                                                                           | —                                                                                                                                                                                                                                                                                                                                                                        |
| Status                                                           | **claim 時に全員を進行中にする**（代表だけだと、非代表を渡された側が「claim されていない」と読み、資源を待たずに着地まで走る） | —                                                                                                                                                                                                                                                                                                                                                                        |
| 読ませる面（Artifact）                                           | 全員                                                                                                                           | **自分の本文にだけ書く。成員間で食い違ったら代表の本文が現行**（規則は `artifact.md`）                                                                                                                                                                                                                                                                                   |

**着地面の宣言が成員間で食い違う group は claim しない。**1 セッションが 1 計画で別々の面へ書くことになり、branch と worktree の対応が付かない**。食い違いは同居宣言の側の誤りとして扱う** —— 書く先が違うなら「片方だけ直すともう片方が同じ場所を二度触る」に当たらないので、そもそも同居の条件を満たしていない。

## どちらの集合を見るか

| 状況                         | 見る集合                                                                  |
| ---------------------------- | ------------------------------------------------------------------------- |
| **claim 済み**（記録がある） | **対象集合**（記録の `members`）。正規化・選出・資源はすべてこれ          |
| **未 claim**                 | group（本文の `Same branch as` の推移閉包）。claim してよいかの判定に使う |

**group の `Depends on` は成員の和集合**。1 人でも未解決なら group ごと待つ —— 1 branch で一緒に直すので、片方だけ先に着手できない。`Depends on` を引くすべての箇所でこの集合を使う（用途を列挙しない —— 挙げ漏らした箇所だけが成員単位で評価され、group が永久に揃わなくなる）。

## 代表

**最小番号。ただし claim した時点で固定する**。毎回本文から引き直すと、後から小さい番号が `Same branch as` に加わったときに代表が変わり、既にある branch を見失う。claim 済みなら、記録の `representative` が代表（引き直さない）。

本文にだけ足された番号は次の着地まで別扱い。台帳が揃っていないので共有成果物を継承させない。加入させれば対象集合に入り、本隊と同じ `progress` になる（下記）。

## 対象集合

**対象集合は claim の記録が定める**。Status や assignee から推し量らない — 更新が両方失敗した成員は集合から消えてしまい、誰も直しに来なくなる（集合の外なので不足を検知できない）。逆に、人が自分で担当に付けただけの Issue を誤って引き込む。

branch を作った直後に、代表の Issue へ固定 marker で記録する。

````markdown
<!-- claim -->

```yaml
representative: <代表の Issue 番号>
members: [<Issue 番号>] # 代表を含む全員
landing: [<owner>/<repo>] # 着地面
```

<!-- /claim -->
````

**`landing` は claim の時点で書き、以後は動かさない**（意味論は `landing-surface.md`）。本文の宣言は入力で、**記録が SSOT** —— 本文から毎回引き直すと、着手後に宣言が足された課題の worktree と終端判定が途中で別 repo へ移る。

**宣言順を保って書く**。実行面（セッションを置く面）は claim 後この順の先頭で決まるので、並べ替えると置き場だけがぶれる（`landing-surface.md`）。

**記録では省略できない**。既定（制御面 1 面）が効くのは**本文の宣言が無いとき**だけで、claim はそれを解決した結果を必ず書く。**記録の `landing` が欠落・空・不正なら `Conflict`** —— そこを既定へ丸めると、壊れた記録が着地面を黙って 1 面落とし、**その面の worktree も終端も観測されないまま進む**（この機構が直そうとしている状態そのもの）。読み替えは互換であって既定値ではない。

Status と assignee は台帳であって集合の定義ではない。記録にあるのに揃っていない成員は、「揃えるべきもの」として埋める対象になる。

本文の `Same branch as` に後から足されただけの番号は含まれない（記録に無いため）。

**後から気づいて同じブランチで直したものは、加入させてから足す。**

1. Issue 契約が揃っているか確認する（欠けていれば加入させない）。**着地面の宣言が記録の `landing` と同じかも見る** —— 違うものを入れると、記録は 1 つなのに書く先が 2 通りになる
2. **claim の記録の `members` に番号を足す**（これで対象集合に入る）
3. Status を進行中にし、assignee を揃える
4. 計画の `alsoResolves` に番号を足す

2 が加入の実体。3 と 4 が途中で落ちても、記録にあれば「揃えるべきもの」として埋められる。

記録が無いとき（人が直接渡したセッション）は、本文へ `Same branch as` を相互に書くのが加入。資源も台帳も使わないので、それで足りる。

## 実体を触るとき

**単位は group、1 回だけ**。片付け・起こし直し・資源の受け渡し・branch の削除は、代表の番号で 1 回行う。Issue ごとに走らせると、同じ実体を別の成員が壊す — 非代表から起こすとそちらの名前でセッションが生え、孤児が増え続ける。

**着地面が複数ある実体は、面ごとに 1 回**（branch と worktree がそれ）。**「代表の番号で 1 回」を「1 つの実体につき 1 回」と読み替えない** —— 面の数だけ実体があるので、1 面ぶんだけ片付けて残りが漏れる。セッションと資源の受け渡しは面をまたいで 1 つのまま。

**消すのは全員が終端のときだけ**。1 件だけ閉じた group で片付けると、まだ実装中の成員の worktree ごと消える。終端が混ざっている group は、判断を人へ返す。
