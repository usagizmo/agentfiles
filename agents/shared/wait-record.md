# 人に聞くとき

**人の答えを待って応答を終えるなら、聞く前に Issue コメントへ固定 marker で記録を残す。**
**質問の本文は記録側に置く**。選択 UI や応答へ出すのは、記録を指す短い問いだけにする。

セッションは消える。**セッション文脈はキャッシュ、外部化した記録が復旧契約**という原則は、計画と
同じく人待ちにも効く。multiplexer が返す「人待ちの印」は即時観測用のキャッシュであって、
セッションが死ぬと印も最後の応答も失われ、**まだ答え待ちなのかを誰も復元できなくなる**。

## 発動点は「聞くこと」であって、止まる理由ではない

**述語は「人に聞いて、答えを待って応答を終えるか」の 1 つ**。各 skill の停止条件の表に
当たったかどうかでは判定しない。

**発動点は聞くたびに立つ**。一度 `cleared` にした記録でも、**もう一度聞くなら同じ記録を `waiting` へ
戻す**。「記録はもう書いた」で済ませない —— 上位は記録だけを見るので、`cleared` のままだとその課題は
**答えを待っていないもの**として扱われる。

- **枠が渡ってくる**。渡し直されたら書き始める契約なので、**人の答えを待っている最中に書き出す**。
  これがいちばん重い
- **止まっている理由が別の原因に誤診される**（実測: CI が落ちて人へ聞き直した課題が `cleared` の
  ままだったため、上位から「PR はあるが誰も動いていない」と読まれ、checks の引き直しが 2 度
  通知されて失敗の記録まで積まれた）

**理由は、表に無い問いが実際に多いから**。実測では、`refine` が 4 件、`resolve` が 2 件、
記録を書かずに選択 UI だけで聞いていた。`resolve` の 2 件は**どちらも停止条件の 5 つに当たらない**
（片方は「意図の確認」という通常工程、もう片方は「検証を回すか省くか」というその場の問い）。
**発動点が停止条件表の外にあった**ことが、規約があるのに守られなかった原因。

書かないと、外からはこう見える。

- 人待ちの SSOT は記録なので、**印はあるが記録が無い = `Conflict`** にしか見えない
- **詰まりの経過時間を出せない**（記録の更新時刻が無い）。投げたばかりか返事が遅れているのかで
  人の動きが変わるのに、その材料が消える
- fail-closed なので上位のキュー管理は触れず、**pane を読まないと何を聞かれているか人に伝えられない**
- `resolve` が **write を保持したまま止まっているのに、待ちの理由も経過時間も観測できない**

## 書かないもの

**実行資源待ちは人待ちではない**。lease が空くのを待つ・休止を伝えられて止まる・CI や別セッションの
完了を待つのは、**答える人が居ない**待ちなので、この記録を書かない。**実行資源待ちの永続記録は
キュー管理側が持つ休止の記録だけ**で、待つ側は何も書かない。

**「待って応答を終えるときは 1 行書く」と取り違えない**。その 1 行は最後の応答に出すものであって、
記録ではない。

書くと、機械側でこう転がる。

- `waiting` は実行器の状態ラダーの**最上段**（`人待ち`）に写るので、その課題は `休止` にも
  `待機` にも降りられない
- 枠を渡す経路は `待機` / `休止` にしか当たらないため、**二度と自動再開されない**。
  起こし直す経路はセッションが生きていれば不発、計画の通知は人待ち中は送らないので、
  **どの遷移にも当たらないまま滞留する**
- 人には「答えれば進む詰まり」として表示されるが、**答える質問が無い**。経過時間だけが伸びる

**実測で、休止を伝えられた解決工程が `reason: 資源キーが交差し、後発として休止（実行資源待ち）` と
書いた**。理由の欄に「人待ちではない」と書いてあっても、**読む側は `state` しか見ない。**

## 記録が有効かどうか

**質問の本文があることが、人待ちである証拠**（書式が本文を必須にしている）。`waiting` なのに
本文が無い記録は、人待ちを表していない。次の 3 分類で扱う。

| 観測                                                  | 扱い                                                         |
| ----------------------------------------------------- | ------------------------------------------------------------ |
| `waiting` + 質問の本文あり                            | 人待ち                                                       |
| `waiting` + 本文なし + **同じ対象に休止の記録がある** | **人待ちではない**。`cleared` にして、実行資源待ちとして扱う |
| `waiting` + 本文なし + 実行資源待ちの証跡なし         | **壊れた記録**。自動で解除せず、**証跡の矛盾として報告する** |

**本文の欠落だけで解除しない**。本物の質問を選択 UI にだけ出して本文を書き損ねた経路が実在するので、
**証跡の無い欠落を解除へ倒すと、製品判断を待たないまま書き始める。**

**この述語を共有側に置くのは、書く側と読む側の両方が引くから**。書く側（計画工程・解決工程）は
起こし直されたときにこれで自己修復し、読む側（キュー管理）は無効な記録を `人待ち` に写さない。
**片方だけに置くと、直せる主体が居ないまま滞留する** —— 読む側だけなら記録が `waiting` のまま残り、
書く側だけならセッションが生きているあいだ誰も気づかない。

## 手順

1. **記録を upsert する**（下の形式。質問の本文まで書ききる）
2. **upsert が成功したことを確かめる**。失敗したら**聞かずに「記録不能」として報告して終える** ——
   記録の無い人待ちは、上から見ると壊れた証跡と区別がつかない
3. 読ませる面へ**判断待ちを書き足すのは、成功を確かめた後**（条件は `artifact.md`）。
   **記録が質問の SSOT で、そちらは projection** —— 先に質問を載せると、upsert が落ちたときに
   **問われた形跡だけが人の面に残る**。**枚そのものを作る順序は縛らない**（計画工程は本文更新より
   先に作る）
4. 記録を指す短い問いだけを選択 UI / 応答に出す。**本文を二重に書かない**（片方だけ直ると食い違う）

**複数件をまとめて聞くときは、全対象の記録を書いてからまとめて聞く**。1 件ずつ「記録 → 質問」を
繰り返すと人の待ち時間が伸び、途中で落ちたときに記録の無い対象が残る。

## 形式

````markdown
<!-- wait -->

```yaml
state: waiting | cleared
issues: [<Issue 番号>] # group なら全番号
phase: <止まった工程の名前>
reason: <何が決まらないか。1 行>
```

<!-- /wait -->

質問の本文をここに書く（聞き方は `~/.agents/AGENTS.md` —— 前提 / 選択肢と各案の帰結 / 推奨 /
判断が変わる条件）。**ここが質問の SSOT**で、選択 UI はこれを指すだけ。
````

同じ marker のコメントを複数作らない。状態が変わるときは既存コメントを書き換える。

**`cleared` にするときも質問の本文は残す**。何を聞いて何が決まったかが、後から読む唯一の材料になる。

**聞き直して `waiting` へ戻すときは、新しい問いを先頭に置き、決着した問答はその下に残す**。
**差し替えない** —— 差し替えると、上の行が守っている唯一の履歴材料が消える。詰まりの表示は
先頭しか読まないので、下に積んでも読みにくくならない。

## 誰が書き、誰が消すか

| 操作                     | 主体                                                                                                                                                    |
| ------------------------ | ------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `waiting` にする         | 聞く当人（計画工程・解決工程のどちらも）                                                                                                                |
| `waiting` へ戻す         | **同じく当人**。聞き直すたびに戻す（上の「発動点は聞くたびに立つ」）                                                                                    |
| `cleared` にする         | **同じく当人**。答えを解釈してから消す                                                                                                                  |
| `cleared` にする（例外） | **人待ちではないと判定した側**（上の 3 分類の 2 行目）。書く側・読む側のどちらでもよく、先に観測した方が閉じる                                          |
| `cleared` にする（例外） | **着地済み / 取り下げに達したら、片付ける側**。当人のセッションは既に無く、閉じないと片付けが毎回空振りする                                             |
| `cleared` にする（例外） | **退避先へ移して終えるとき、当人。答えを待たずに閉じる**。`waiting` のままだと実行器を片付ける側が「人待ち」と読んで降り、pane が閉じられず枠が空かない |
| 読む                     | 上位のキュー管理（人待ちの数え上げ・詰まりの表示）                                                                                                      |

**人のコメントが付いただけで消さない**。それが答えなのか、関係のない補足なのかの解釈は
課題の中身の判断であって、キューを回す側の領分ではない。

**`cleared` にしてから再開する**。記録が `waiting` のままだと、外からは止まったままに見える。

## 起こし直されたら

**起動したらまず記録を読む**。`waiting` のまま起こされたなら、前のセッションが死んでいる。

1. **まず「これは人待ちか」を見る**（上の 3 分類）。人待ちでないなら `cleared` にして、
   実行資源待ちとして待つ側の手順へ移る。壊れているなら解除せずに報告する
2. 人がまだ答えていない → **質問を出し直して待つ**。**計画工程だけ例外があり、待たずに終える
   経路を持つ**（述語と手順はそちらの skill）
3. 人が既に答えている → 解釈して `cleared` にしてから続ける

記録を書いた当人が居なくても、ここで復帰経路が閉じる。**中身の解釈は起こされた側が行う**ので、
起こす側が答えを仲介しなくてよい。
