# 人に聞くとき

**人の答えを待って応答を終えるなら、聞く前に Issue コメントへ固定 marker で記録を残す。**
**質問の本文は記録側に置く**。選択 UI や応答へ出すのは、記録を指す短い問いだけにする。

セッションは消える。**セッション文脈はキャッシュ、外部化した記録が復旧契約**という原則は、計画と
同じく人待ちにも効く。multiplexer が返す「人待ちの印」は即時観測用のキャッシュであって、
セッションが死ぬと印も最後の応答も失われ、**まだ答え待ちなのかを誰も復元できなくなる**。

## 発動点は「聞くこと」であって、止まる理由ではない

**述語は「人に聞いて、答えを待って応答を終えるか」の 1 つ**。各 skill の停止条件の表に
当たったかどうかでは判定しない。

**理由は、表に無い問いが実際に多いから**。実測では、`refine` が 4 件、`resolve` が 2 件、
記録を書かずに選択 UI だけで聞いていた。`resolve` の 2 件は**どちらも停止条件の 5 つに当たらない**
（片方は「意図の確認」という通常工程、もう片方は「検証を回すか省くか」というその場の問い）。
**発動点が停止条件表の外にあった**ことが、規約があるのに守られなかった原因。

書かないと、外からはこう見える。

- 人待ちの SSOT は記録なので、**印はあるが記録が無い = `Conflict`** にしか見えない
- **詰まりの経過時間を出せない**（記録の更新時刻が無い）。投げたばかりか返事が遅れているのかで
  人の動きが変わるのに、その材料が消える
- fail-closed なので上位のキュー管理は触れず、**pane を読まないと何を聞かれているか人に伝えられない**
- `resolve` が **write を保持したまま止まっているのに、待ちの理由も経過時間も観測できない**

## 手順

1. **記録を upsert する**（下の形式。質問の本文まで書ききる）
2. **upsert が成功したことを確かめる**。失敗したら**聞かずに「記録不能」として報告して終える** ——
   記録の無い人待ちは、上から見ると壊れた証跡と区別がつかない
3. 読ませる面へ**判断待ちを書き足すのは、成功を確かめた後**（条件は `artifact.md`）。
   **記録が質問の SSOT で、そちらは projection** —— 先に質問を載せると、upsert が落ちたときに
   **問われた形跡だけが人の面に残る**。**枚そのものを作る順序は縛らない**（計画工程は本文更新より
   先に作る）
4. 記録を指す短い問いだけを選択 UI / 応答に出す。**本文を二重に書かない**（片方だけ直ると食い違う）

**複数件をまとめて聞くときは、全対象の記録を書いてからまとめて聞く**。1 件ずつ「記録 → 質問」を
繰り返すと人の待ち時間が伸び、途中で落ちたときに記録の無い対象が残る。

## 形式

````markdown
<!-- wait -->

```yaml
state: waiting | cleared
issues: [<Issue 番号>] # group なら全番号
phase: <止まった工程の名前>
reason: <何が決まらないか。1 行>
```

<!-- /wait -->

質問の本文をここに書く（聞き方は `~/.agents/AGENTS.md` —— 前提 / 選択肢と各案の帰結 / 推奨 /
判断が変わる条件）。**ここが質問の SSOT**で、選択 UI はこれを指すだけ。
````

同じ marker のコメントを複数作らない。状態が変わるときは既存コメントを書き換える。

**`cleared` にするときも質問の本文は残す**。何を聞いて何が決まったかが、後から読む唯一の材料になる。

## 誰が書き、誰が消すか

| 操作                     | 主体                                                                                                                                                    |
| ------------------------ | ------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `waiting` にする         | 聞く当人（計画工程・解決工程のどちらも）                                                                                                                |
| `cleared` にする         | **同じく当人**。答えを解釈してから消す                                                                                                                  |
| `cleared` にする（例外） | **着地済み / 取り下げに達したら、片付ける側**。当人のセッションは既に無く、閉じないと片付けが毎回空振りする                                             |
| `cleared` にする（例外） | **退避先へ移して終えるとき、当人。答えを待たずに閉じる**。`waiting` のままだと実行器を片付ける側が「人待ち」と読んで降り、pane が閉じられず枠が空かない |
| 読む                     | 上位のキュー管理（人待ちの数え上げ・詰まりの表示）                                                                                                      |

**人のコメントが付いただけで消さない**。それが答えなのか、関係のない補足なのかの解釈は
課題の中身の判断であって、キューを回す側の領分ではない。

**`cleared` にしてから再開する**。記録が `waiting` のままだと、外からは止まったままに見える。

## 起こし直されたら

**起動したらまず記録を読む**。`waiting` のまま起こされたなら、前のセッションが死んでいる。

1. 人がまだ答えていない → **質問を出し直して待つ**。**計画工程だけ例外があり、待たずに終える
   経路を持つ**（述語と手順はそちらの skill）
2. 人が既に答えている → 解釈して `cleared` にしてから続ける

記録を書いた当人が居なくても、ここで復帰経路が閉じる。**中身の解釈は起こされた側が行う**ので、
起こす側が答えを仲介しなくてよい。
