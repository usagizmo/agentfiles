# Issue 契約

**Status を計画済みへ進める = 「この 6 つが本文に揃っている」という宣言。**1 つでも欠けたら移さない。
`refine` が書き、キュー管理が揃っているかを確認する。

## 項目と見出し

**見出しの字面が契約の実体**。本文に完全一致で在り、直下に中身があることが「揃っている」の定義。

| 見出し（完全一致）      | 中身                                    | 埋める人                                 |
| ----------------------- | --------------------------------------- | ---------------------------------------- |
| `## 目的`               | 目的と期待する結果                      | エージェント（ユーザーの意図を確認して） |
| `## 受入条件`           | 真偽が言える文                          | エージェント                             |
| `## 非目標`             | やらないと決めたこと（理由ごと）        | エージェント                             |
| `## 確定済みの製品判断` | 「A を採用、B はしない」                | **ユーザー**                             |
| `## リスク`             | 配信・migration・security・外部サービス | エージェント                             |
| `## 依存`               | 理由だけ（無ければ「なし」）            | エージェント                             |

**見出しを固定するのは、充足を機械で判定できるようにするため。**散文のままだと「揃っているかを確認する」
工程がどこにも実装できず、確認が省かれる（実測で、契約の充足だけが観測できず fail-closed で選出が
止まった）。**見出しの字面を変えるときは、読む側の実装と同時に変える** —— 片方だけ変えると、
契約は揃っているのに永久に不足と判定される。

**「中身がある」は空でないことまで**。項目の質は機械では測れないので、そこは工程の責任として残す。

**`## 依存` に番号を伴う宣言を書かない**。関係の宣言（`Depends on #N` / `Same branch as #N`）は
本文の先頭区画へ、行頭に 1 行 1 件。ここに書くのは理由だけで、番号を伴わない語を使う。同じ場所に
両方書くと、理由の散文が宣言として読まれる（形と置き場は `same-branch.md`）。

## 書き方

**未決の判断を「エージェントが決めて」埋めない**。埋まっていない = まだ計画済みではない、が正しい。
無理に埋めても、着手後に「本文に無い判断が必要」で止まるだけで、待ちが後ろへずれる。

**受入条件は原則で書く。識別子や箇所の列挙にしない。**「この N 個の名前を直す」と書くと、そのとき
検索で拾えた分だけがチェックリストになり、同じ原則の対象なのに拾えなかったものが、受入条件にも
再発防止の仕掛けにも現れないまま残る。主文は「〜という性質のものを残さない」と書き、列挙はその
時点の実測として添えるだけにする。**列挙を直しきったことを完了条件にしない。**

**非目標が落ちると、着手後にスコープが際限なく広がる。**書かれていない不在は、後続から
「判断して残した」ではなく「漏れ」として読まれる。**互換の扱いは必ず書く** —— 互換 shim /
deprecated alias / feature flag / migration を持つか持たないかを、理由ごと。既定は「持たない」
（`~/.agents/AGENTS.md`「最終形に不要なコードは初手から書かない」）。書かれていないと、着手側は
安全側に倒れて温存コードを足す。

**実行メタデータは本文に書かない**（base・worktree path・セッション ID・候補 SHA）。時間で変わるので、
Project field・branch・PR に置く。本文に書くと着手時には必ず古い。

## 入場を止める宣言

**「既存側だけで、これから来るどの候補とも非互換だと証明できる」ときに置く印**。置くと、その課題が
終端に達するまで claim と write の新規貸し出しが止まる。

**運ぶのは固定 marker のコメント**。本文ではなくコメントに置くのは、着手後に本文へ書き足せない
規約があるため。**指紋に入る形でなければならない** —— 入らない置き場だと、解除しても誰も tick を
起こさず、止まったままの窓が最も長く残る。

````markdown
<!-- entry-block -->

```yaml
issues: [<Issue 番号>] # 対象集合の全番号
reason: <なぜ、これから来るどの候補とも非互換か。1 行>
```

<!-- /entry-block -->
````

**いつ置くかは project の領分**（何が「どの候補とも非互換」に当たるかは製品の構造で決まる）。
**運び方はここが固定する** —— 形まで project に委ねると、読む側が観測する手段を持てない。

**時間切れで解除しない**。経過時間で安全性が変わると fail-closed が壊れる。解除するのは人か、
その課題が終端に達したとき。
