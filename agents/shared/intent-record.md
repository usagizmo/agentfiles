# 意図の確認の記録

**「実物を見せて、明示的な承認を得た」ことを外部化したもの**。

**人待ちの記録では代用できない**。あれは「**いま回答を待っているか**」を表すので、`cleared` は
「もう待っていない」しか意味しない。**待つのをやめた理由が「前提が崩れたから」でも同じ値になる**ので、
**要求が果たされたかは復元できない**（実測: 「dev app を起こせない」という前提を自分で取り下げて
`cleared` にしたところ、**「実物を見せる」という要求ごと消えて、そのまま着地した**）。

**セッションまとめでも代用できない**。あれは報告者の推奨であって、人の承認ではない。
**PR 本文も、意図の確認より後に作られる projection。**

````markdown
<!-- intent -->

```yaml
state: pending | confirmed | not-required
issues: [<Issue 番号>] # 対象集合の全番号
revision: <見せた時点の SHA> # 何を見せたかを固定する
reason: <要らないと判定した根拠> # not-required のときだけ
```

<!-- /intent -->

## 見せたもの

<何を、どうやって見せたか>

## 項目ごとの状況

| 項目 | 状況 | 誰が何を承認したか |
| ---- | ---- | ------------------ |
````

**同じ marker のコメントを複数作らない**。**代表の Issue に 1 つ**（帰属は `same-branch.md`）。

## 3 つの状態

| 状態           | 意味                                                     |
| -------------- | -------------------------------------------------------- |
| `pending`      | 確認が要るのに、**必要な項目すべての明示承認がまだ無い** |
| `confirmed`    | 対象 revision の必要項目が**すべて明示的に承認された**   |
| `not-required` | 要否の述語の除外側に当たる。**理由と revision が要る**   |

**沈黙は承認ではない**。**指摘が返らなかった項目は `confirmed` に数えない** —— 実測で、7 項目のうち
明示承認は 3 項目だけなのに「対応不要」として着地した。**部分承認は全体を `pending` のまま**にし、
項目ごとの状況を本文に残す。

**`not-required` を書くのは当人でよい**。要否は製品判断ではなく、工程表の述語を diff に当てる
技術判断。ただし**自由記述にしない** —— 除外側に**明確に当たる**ときだけで、
**「UI 変更だが小さい」「既存仕様の延長」「たぶん期待どおり」は理由にならない**。迷ったら `pending`。

**記録があること自体は、判定が正しい保証にはならない**。防げるのは**無記録・沈黙・状態消失に
よる素通り**で、誤判定まで機械的には防げない（防ぐには全変更を人が承認するしかなく、
除外の述語を持つこと自体と両立しない）。

## 人待ちの記録との順序

**別軸だが、遷移の順を固定すると途中状態が必ず着地を止める側へ倒れる。**

| 局面         | 順序                                                                                                 |
| ------------ | ---------------------------------------------------------------------------------------------------- |
| 確認を求める | 人待ちを `waiting` にして質問を書く → **この記録を `pending`** にして人待ちのコメントを指す → 見せる |
| 回答を得た   | 回答を解釈して **`confirmed` にする** → 人待ちを `cleared` にする → 枠を渡し直されるのを待つ         |

**`pending` なのに人待ちが `cleared` か欠落しているのは、証跡の矛盾**。上の実測がそのまま
この形になるので、**上位は着地させずに報告する**。

## 失効

**確認の対象になった面をまた変えたら失効する**（判定は要否と同じ述語）。失効したら `pending` へ戻す。

**rebase や無関係な追随では失効しない**。SHA の一致で判定すると、**latest default へ追随するたびに
確認し直す**ことになり、確認そのものが形骸化する。`revision` は**何を見せたかを後から辿るため**に
置いてあるだけで、失効の述語ではない。

## 着地の前に確かめる

**有効な `confirmed` か `not-required` が無いなら着地しない。**

**枠を待つ variant にだけ任せない**。人が直接走らせた課題はキュー管理を通らずに着地できるので、
**着地する操作そのものが最後の砦**になる。**判定するのは記録の状態と必須の欄だけ**で、
承認の中身は解釈しない。
