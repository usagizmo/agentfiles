# 実行器が尽きたとき

**いまの実行器では続けられない状態で応答を終えるなら、終える前に固定 marker で記録を残す。** context 予算の使い切りがこれに当たる。

**外から観測できない資源はこれだけ**。セッション一覧が返す状態値は「終えた」と「使い切った」を区別しないので、当人が申告しなければ上位からは区切りよく終えたターンと同じ観測になる。休止や人待ちと違い、証跡を作れるのは当人しか居ない。

## ほかの記録と混ぜない

**人待ちの記録には書かない**（`wait-record.md`「書かないもの」）。答える人が居ない待ちなので、`waiting` に写すと実行器の状態ラダーの最上段（`人待ち`）に上がり、起こし直す経路にも枠を渡す経路にも当たらないまま滞留する。

| 記録   | 表す事実                     | 書き手         | 解除する主体       |
| ------ | ---------------------------- | -------------- | ------------------ |
| 人待ち | 人の回答が要る               | 聞いた当人     | 答えを解釈する当人 |
| 休止   | 資源キーが交差して書けない   | キュー管理     | キュー管理         |
| 枯渇   | いまの実行器では続けられない | **尽きた当人** | **キュー管理**     |

## 形式

````markdown
<!-- exhaust -->

```yaml
state: exhausted | cleared
issues: [<Issue 番号>] # group なら全番号。Issue を持たない課題は [] にする
phase: <止まった工程の名前>
```

<!-- /exhaust -->
````

同じ marker のコメントを複数作らない。状態が変わるときは既存コメントを書き換える。帰属は `same-branch.md`。**Issue を持たない課題は PR のコメントに置き、`issues` は `[]` にする**（置き場の述語は人待ちの記録と同じ）。そのときの対象はコメント先の PR —— `issues` で照合できないのはこの形だけ。どちらも無いうちは記録を作れないので、そのときは応答に書いて終える —— 外部化できないことを黙って進まない。

**判定に使うのは `state` と `issues` だけ**。理由を書き添えてよいが、読む側は解釈しない —— 文面で判定させると、書き手が正しく書いても機械的判定が別の結論へ落ちる（実測で、`reason` に「人の判断待ちではない」と明記した人待ちの記録が、証跡が無いために壊れた記録として扱われた）。

**継続メモの置き場にしない**。どこまでやったかは Issue・計画コメント・branch・worktree が既に持っている。ここへ置くと「新しい実行器が読む前に誰が消したか」という別の状態機械が要る。

## 誰が書き、誰が消すか

| 操作               | 主体                                                                                     |
| ------------------ | ---------------------------------------------------------------------------------------- |
| `exhausted` にする | 尽きた当人（計画工程・解決工程のどちらも）                                               |
| `cleared` にする   | **キュー管理**。新しい実行器を起こす前。`exhausted` のまま起こされたときだけ当人（下記） |
| コメントごと消す   | **キュー管理**。課題が終端に達して実体を片付けるときだけ                                 |
| 読む               | キュー管理（実行器を入れ替える発火条件）・起こされた当人                                 |

**当人は消さない**。消してから次を起こす形にすると、消した直後にまた尽きたときに記録が残らない。

**例外は、`exhausted` のまま起こされたとき**。キュー管理が消し損ねているので、起動した当人が報告のうえ `cleared` にしてから続ける（下記）。

**書いても write は手放さない**。枯渇は資源の譲渡ではないので `休止` にも `人待ち` にも写さない —— 写すと、資源キーが交差する課題へ枠が渡る。

## 起こし直されたら

**まず `state` を読む。`cleared` なら、そのまま続ける。**

**`exhausted` のまま起こされたなら、その事実を報告したうえで、自分で `cleared` にして書けたことを確かめてから続ける。** キュー管理が消し損ねた証拠なので黙って進まない。**止まらない** —— 止めると、消す主体が居ない課題（キュー管理が動いていない・キュー管理の管理対象でない）が起動と終了を往復し続ける。

**起こし手では分岐しない** —— 同じ入力で起こされるので誰が送ったかは残らず、キュー管理の生存で引くにも実名と引き方が harness 側にしかない。**自分で消せることが「起こす前に確かめる」を弱めるわけではない** —— キュー管理は起こす前に必ず `cleared` にするので、当人が `exhausted` を見た時点でその手順は既に踏まれていない。
