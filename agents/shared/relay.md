# 転記

**人が決めた伝言を、解釈を挟まずに宛先へ打つ操作。**渡す側が複数いるので、条件を 1 箇所に置く
（片方だけ緩むと、緩んだ側から解釈が入る）。

**どの局面で転記が起きるかは、各 skill が持つ**（自分宛に答えが来た / 宛先を名指しで頼まれた）。
ここは**満たすべき条件だけ**を定める。

## 条件

**3 つ全部を満たすときだけ運ぶ。**

| 条件 | 外れたら |
| --- | --- |
| **解釈の余地が無い** —— 提示済みの選択肢の採否・yes / no のように、**参照先が外部化されていて 1 対 1 で対応が付く** | 割れうるものは運ばず、**当のセッションへ返してもらう** |
| **宛先が決まっている** —— 人が名指ししたか、答えを待っている当人が一意に決まる | 自分で選んだ時点で**導出**になる。それは転記ではない |
| **再開の許可を書かない**（「実装に入ってよい」等） | 枠の付与は自動消化ループの action。**起こしただけでは枠を渡したことにならない**前提の上に立っている |

**転記であることを明示し、要約・言い換え・補足をしない。**入口（解釈の余地が無いものだけ）と
出口（言い換えない）の両方が要る —— **入口だけだと、運ぶ途中で解釈が混ざる。**

## 導出ではない

**誰に何を渡すかを決めたのは人で、こちらは打つだけ。**自分で宛先や中身を選んでいないので、
判断を上書きしたことにならない（**会計上どう扱うかは、tick を持つ側が自分の節で決める**）。

**「別の経路で打ち直してください」と返さない。**原則の目的（解釈を混ぜない・導出を人手で
上書きしない）は上の条件で守られており、**打ち直しを求めるのは形だけ守って人の手を止める動き**。

## 3 つ目が効く前提

`resolve` の `managed` は **write lease が来るまで実装を始めない**。だから起こす・話しかけるだけでは
枠を渡したことにならず、転記が資源の制御を壊さない。**この前提が変わったら閉じ直す。**
