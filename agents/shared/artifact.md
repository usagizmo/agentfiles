# Artifact

**人に読ませる面を、1 つの URL として持たせる操作**。作る skill が複数あるので、条件を 1 箇所に置く
（片方だけ緩むと、緩んだ側から根拠が消える）。

**SSOT にしない**。消える前提の面で、**原本は必ず別にある**（Issue 本文 / PR 本文 / skill・docs /
観測から作り直せる盤面）。

**2 種ある**。**課題の枚**（計画から着地まで、複数の工程が同じ 1 枚を書き直す）と、
**単独の書き手が持つ枚**（状況ボードのように、1 つの実行器だけが更新し続ける）。
**条件は共通で、引き当てだけが違う。**

**どの局面で作るかは、各 skill が持つ**（計画を出す / 判断を仰ぐ / 積み残しの行き先を諮る）。
ここは**満たすべき条件だけ**を定める。

## なぜ要るか

**提示文は流れて消える**。選択肢を並べた画面には結論しか残らないので、**後から根拠を辿れない** ——
決めた本人も、しばらく経つと「なぜその案にしたか」を再構成できない。

**それでも原本にはしない**。読みやすさのための面と、消えては困る記録は、別の要求。
**片方で両方を満たそうとすると、消えたときに気づけない。**

## 条件

| 条件                                                                                        | 外れたら                                                     |
| ------------------------------------------------------------------------------------------- | ------------------------------------------------------------ |
| **中身は永続する場所にも残す**                                                              | Artifact が消えた時点で根拠ごと失われる                      |
| **残す先が無いなら作らない**。その場で消えてよい話か、Issue にすべき話のどちらか            | 置き場の無いものが増え、**どれが生きているか分からなくなる** |
| **1 課題につき 1 枚**。工程で割らない                                                       | 同じ課題の面が 2 つ生え、**人は古い方を開く**                |
| **判断だけを別の枚に切り出さない**。根拠と結論、判断材料と計画で割らない                    | 別 URL に分かれた瞬間、片方しか読まれない                    |
| **次に開くときの引き当て先を決めておく**（課題の枚は URL の置き場、単独の枚は固定した題名） | 会話は流れる。人待ちの記録は `cleared` で書き換わるので不可  |
| **その時点の SSOT から全体を書き直す。前の版を読み直さない**                                | Artifact が履歴の原本になる                                  |

## 課題の枚

**課題（1 branch で着地する 1 まとまり）につき 1 枚**。工程をまたいで同じ枚を更新し続ける ——
計画を書いた枚に、判断の提示とセッションまとめが重なる。**時点も関心も違うが、読む人は同じ**。
分けると、着手前に読んだ人が着地後の積み残しに辿り着けない。

### 現在状態だけを載せる

**枚は原本の projection**。書くたびに**そのときの SSOT から全体を作り直す**。

| 節               | 再生成元                                       |
| ---------------- | ---------------------------------------------- |
| 計画             | Issue 本文（契約の項目）                       |
| 実装計画         | 着手側の計画の記録（人が読む文の部分）         |
| 判断待ち         | 人待ちの記録の「いま待っている問い」           |
| 意図の確認       | 意図の確認の記録（見せたものと項目ごとの状況） |
| セッションまとめ | その回の事実（PR へコメントするのと同じ内容）  |

**履歴を積まない**。一覧から取れるのは題名・URL・更新時刻だけで**既存の本文は取れない**ので、
前の版を残そうとすると**枚そのものを原本として読むことになる**。**失効した計画も残さない** ——
読む側が**どれが現行か判定できない**。

古い版が要るなら、それは Issue コメントか git の仕事。

### 出すことと、待つことは別

**枚を出しても人待ちにはならない**。人待ちの記録を書くのは**答えを待って応答を終えるとき**だけで
（`wait-record.md`）、**読ませる面を更新しただけなら書かない**。書くと、**答えるべき問いが無いのに
詰まりとして表示され**、枠を渡す経路にも当たらなくなる。

**逆に、待つなら記録が要る**。同じ枚に判断待ちの節を載せて応答を終えるなら、それは人待ちで、
順序は `wait-record.md`。

### 引き当て

**別セッションから更新するには URL を渡す必要がある**（渡さないと新規 URL が発行される）。
セッションは記憶を持たないので、**URL は外部化した場所から引き直す**。

1. **Issue 本文の先頭区画の `Artifact: <URL>` 行**。**group なら成員全員の本文を見る**
   （代表以外にしか行が無いのが通常。下記）
2. 無ければ**題名から一覧で引き当てる**（下記）
3. それも無ければ新規に作り、**書ける立場なら URL を書く**（下記）

**どちらの手でも、当たったのが複数なら代表の本文が指す方**（代表の決め方は `same-branch.md`）。
**代表の本文にも無ければ最後に更新されたもの。**

**本文の行を先に見るのは、一覧が有限だから**。一覧は新しい順に有限件しか返さず、
**依存待ちの在庫は最も長く留まる集合**なので、題名だけに頼ると**待たされたものから順に
引き当てられなくなる** —— 落ちたことは観測できないまま、静かに 2 枚目が生える。

### 誰が URL を書くか

| 場所                 | 書く工程   | 理由                                                                   |
| -------------------- | ---------- | ---------------------------------------------------------------------- |
| Issue 本文の先頭区画 | 計画する側 | 本文を確定する工程なので、**同じ書き込みに入れれば digest を壊さない** |
| PR 本文              | 着地する側 | 着地後も残る導線                                                       |

**着手後に Issue 本文へ書き足さない**。本文が変わると digest が動き、**自分の計画を自分で
陳腐化させる**（キュー管理側は「本文の変更を伝える」を発火させ、台帳前進も枠渡しも止まる）。
本文に行が無いまま着手したなら、題名から引き当てるか、新規に作って PR 本文へ書く。

**`Artifact:` は宣言ではない**。番号を伴わないので `Depends on` / `Same branch as` の読み手には
当たらない。先頭区画に置くのは、**人が最初に読むべきものがそこにあるから**
（`same-branch.md`「宣言の形と置き場所」）。

**URL の行は Issue 契約の項目ではない**。欠けていても計画済みへ進めてよい —— 引き当ては題名へ
落ちるだけで、着手はできる。**契約に数えると、Artifact を作れない harness で全 Issue が
差し戻され、キューが止まる。**

### 題名

`#<番号> <短い要約>`。**先頭は `#<番号>` + 半角スペース**で固定する。

- **工程名を題名に入れない**（`計画` / `セッションまとめ`）。1 枚が工程をまたぐので、
  **どの名前を選んでも中身の一部しか指さない**
- **要約は可変**。Issue のタイトルが変わったら差し替える。**先頭だけが引き当てに効く**ので、
  半角スペースまで含めて一致を見る（`#83` の前方一致は `#838` にも当たる）
- **group の番号は、最初に作った成員のもので固定する**。代表は claim まで変わりうるので追随
  させられない。**引くときは成員の全番号を試す**（自分の番号だけでは当たらない）
- **Issue 番号を持たない課題は引き当てない**（人がタスク説明だけで渡したとき）。題名は自由で、
  **そのセッションの中で作って更新する**。外部化先は PR 本文しか無いので、**PR を作る前に
  セッションが落ちたら、次は新しく作る**

### group

**group（`Same branch as` で結ばれた集合。定義は `same-branch.md`）は 1 課題なので 1 枚**。

**作る前に、自分と成員の本文の行を見て、あれば再利用する**（計画は Issue 単位で走るので、
**先に別の番号で生えていることがある**）。**書くのは自分の本文だけ** —— 相手の本文は相手の
計画工程が書くので、足しても同じ URL を 2 度書くだけになる。

**成員の本文に違う URL が並んだら、代表の本文が指す方が現行**。もう一方は孤児として放置する
（消す手段は無く、現行の枚には計画もまとめも揃っている）。**後から加入した Issue は自分の枚を
持っている**ので、これは同時に走ったときだけの話ではなく、**通常の合流でも起きる**。

## 単独の書き手が持つ枚

**題名を固定し、完全一致で引き当てる**。書き手が 1 つなので、外部化した URL の置き場は要らない。
**`#` で始めない** —— 課題の枚と取り違えると、盤面が課題の面を上書きする。

## 迷ったら作る

**製品判断を伴わなくても作る**。ターミナルに流れるテキストより読みやすく、後から開き直せる。
**出し惜しみしない** —— 作らないでよいのは**残す先が無いとき**だけ。

## 作れない harness では

**提示文だけを出して、作れないことを言う。**黙って省くと、読む側は**「まだ作っていない」と
「この harness では作れない」を区別できない。**
