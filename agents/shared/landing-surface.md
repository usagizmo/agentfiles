# 着地面

課題の成果物が生まれる repo。**Issue が置かれた repo と同じとは限らない。**

宣言と帰属は `same-branch.md`（形・claim の記録・group の扱い）、面ごとの座標は project 差分が持つ。
ここが持つのは**意味論** —— どの面が何を持つか、終端をどう判定するか、live checkout に何をしてよいか。

計画工程・解決工程・キューを回す工程の 3 つが読むので共有側に置く。**片方にしか無いと、書く側と
読む側で「どの repo の git を見るか」が割れる。**

## 3 つの面

| 面         | 何を持つか                                                                          | 値                          |
| ---------- | ----------------------------------------------------------------------------------- | --------------------------- |
| **制御面** | Issue・Status・固定 marker の全記録・**claim の remote branch**・project 差分 skill | Issue が置かれた repo       |
| **着地面** | branch・worktree・commit・統合先・`progress` の成果物側・容量・検証・integration    | **集合**。既定は `{制御面}` |
| **実行面** | セッションが実際に書く木                                                            | 着地面ごとの worktree       |

**「作業ディレクトリを移す」と読まない**。単一 repo の前提は観測・容量・失効判定・片付けの所有判定にも
入っているので、木だけ移すと残りがずれたまま別の穴を作る。

### 着地面は集合

**単数にしない**。1 つの課題が 2 つの repo へ commit を作ることは通常運用で起きる —— 着地面の座標表は
project 差分なので制御面にしか置けず、その座標表を足す課題は必ず両方を書く。単数にすると、2 面目を
規約の外で手運びする経路が要る。

**既定は `{制御面}`**。宣言があればそれが全体で、制御面は自動では入らない。これは互換ではなく最終形の
既定値で、宣言が要るのは制御面と違う課題だけ。

**claim より前に決まり、claim の記録へ固定する**（形は `same-branch.md`）。claim は remote branch の
一意作成が二重着手の最後の防壁なので、その時点で確定していないと防壁が立たない。**以後は本文が
変わっても動かない。**

**既定が効くのは本文の宣言が無いときだけ**。claim の記録は解決した結果を必ず持つので、そこが
欠けていたら `Conflict`（`same-branch.md`）。**「無ければ制御面」を記録の側にも当てない** ——
壊れた記録が面を黙って落とす経路になる。

## claim の branch は制御面に置く

**着地面が複数ありうるので、「どこで一意なら claim できたか」が決まらない**。制御面 1 箇所に固定する
ことで、面の数に依らず防壁が 1 つになる。

**着地面の branch は同名のローカル branch**で、origin への push を要求しない。**要求すると、push が
人の領分である面（既定でそう扱う面がある）では claim も終端判定も成立しなくなる。**

`progress` のラダーがどちらを引くかは、段で分かれる。

| 段                      | 引く先                                  |
| ----------------------- | --------------------------------------- |
| `準備中`（branch あり） | **制御面の claim branch**               |
| `実装中` 以降           | **着地面**の commit / worktree の dirty |

**`準備中` を着地面で引かない** —— 着地面の worktree は claim の後に作るので、claim 直後の窓で
`未着手` に落ち、差し戻しの「claim だけ残っていた」が真になって claim の記録ごと消える。

## 統合先

**面ごとに 1 つ**。その面の base と追随の基準になる ref。**終端の判定には使わない**（下記の「終端」）。

| 面           | 統合先                                                 |
| ------------ | ------------------------------------------------------ |
| 制御面       | `origin/<default branch>`                              |
| 宣言された面 | **project 差分の座標表が定める ref**（ローカルでよい） |

**座標表に無い面は着地面として宣言できない**（fail-closed）。統合先が決まらない面は base も追随も
決まらず、計画の失効を判定できない。

**1 つの着地面を複数の制御面で共有しない**。branch 名は `{prefix}/{Issue 番号}-{slug}` で、
**制御面が違えば同じ番号が別の課題を指す** —— 共有すると、同名 branch が別課題の成果として
観測され、片付けで消される。名前に制御面を含めて一意化する手もあるが、claim・片付け・容量の
帰属がすべて名前で引いているので、**実際に共有する必要が出るまで足さない**（座標表を持つ制御面が
1 つなら起きない）。

**PR を使えるのは制御面だけ**。PR と checks の観測は制御面に対してしか行われていないので、
他の面を「PR を使う面」と宣言すると、`提出中` / `着地待ち` / `着地済み` のどれも導出できない
（観測材料が無いまま述語だけが在る状態になる）。**必要になったら観測の側から広げる** ——
座標だけ先に許すと、宣言できるのに一生進まない面ができる。

**端末ごとに違う checkout path は座標表に置かない**。呼び出し側が渡す（観測スクリプトの `--repo` と
同じ扱い）。

## 終端

**2 段で判定する。面ごとに判定し、課題として畳む。**

| 単位     | 終端の条件                                                                                                           |
| -------- | -------------------------------------------------------------------------------------------------------------------- |
| **面**   | **座標表が定める着地の条件**を満たす（下記。**commit が 0 の面は透過**）                                             |
| **課題** | **全着地面が終端**、かつ **全着地面が dirty でない**（`0` のみ。読めなかった `-` は不可）、かつ **提出の証跡がある** |

**着地の条件は面の型で決まる。**

| 面の型          | 着地した                                                                 | 着地してよい（`着地待ち`）        |
| --------------- | ------------------------------------------------------------------------ | --------------------------------- |
| PR を使う面     | PR が `merged`                                                           | open PR があり、checks が緑       |
| PR を使わない面 | **branch に commit があり、その面が「提出済み」**（`session-report.md`） | 同じ（この型では 2 つが一致する） |

**PR を使わない面では、統合先への merge を着地の条件にしない。**push も merge も人の領分なので
（座標表がそう定める面がある）、merge を条件にすると**人が動かすまで終端に到達せず、worktree が枠を
焼き続ける** —— それがこの機構の直している欠陥そのもの。**統合先は残る**が、役割は base と追随の
基準だけで、終端の判定には入らない。

**代わりに「commit + 提出の証跡」で見る**。まとめの記録は、セッションが検証を終えて提出したときに
だけ作られ、**追随や rebase では生まれない**（妥当性は `session-report.md` が定める）。commit だけを
条件にすると実装の途中と区別できず、まとめだけだと成果ゼロを弾けないので、両方を要求する。

**`着地待ち` と `着地済み` が一致する型があってよい**。PR を使わない面には CI も merge も無いので、
「着地してよい」と「着地した」を分ける観測が存在しない。**分けるために merge を持ち込まない。**

**連言にする**。観測できない面が 1 つでもあれば終端に達しない —— 片付けは実体を消すので、倒す向きは
「完了と判定しない」側でなければならない。

**`着地待ち` も同じ 3 つを要求する**（面ごとの条件・全面が dirty でないこと・提出の証跡）。違うのは面ごとの条件だけで、そちらは「**終端している、または着地してよい**」。

**dirty を面の行へ書かない**。「全面が dirty でない」は面の述語ではなく課題の述語で、面の注記に埋めると**課題の連言から落ちる** —— 落ちると、書かなかった面が dirty のまま透過して終端が成立し、片付けがその面の未コミットごと消す。

**面ごとの条件に「終端している」を含める**。含めないと、**先に着地させた面が条件を壊す** —— PR は `merged` になって open ではなくなるので、PR 面を先に着地させた瞬間に `着地待ち` から落ちる。落ちると integration の受け手条件を外れ、**残りの PR 面の merge が二度と発行されない**（人待ちを挟むと渡しの記録も回収される）。

**終端の判定は origin への push も merge も要求しない**。PR を持つ面は `merged` で、持たない面は
commit と提出の証跡で引く。

## live checkout

**人と走っているセッションが読む checkout**（skill の symlink 先がこれ）。着地面の repo に 1 つある。

**読み取り専用の面として扱う**。行ってよい git 操作は 2 つだけ。

| してよい                     | してはいけない                                                 |
| ---------------------------- | -------------------------------------------------------------- |
| fetch                        | 課題の実装で編集する                                           |
| 統合先への merge（人が行う） | dirty / 分岐を自動で解消する（`checkout` / `stash` / `reset`） |

**dirty か、HEAD が統合先の branch でない状態は、報告して止まる**（fail-closed）。**統合先が upstream より先行していることは含めない** —— push が人の領分の面ではそれが常態で、含めるとその面へ一度も着地できない。
自動で直すと、**誰の作業か分からない未コミットの変更を消す** —— 共有面なので、消えたことに気づく
経路が持ち主の側にしか無い。

**この検査が掛かるのは、実際に live へ merge するときだけ**（`merge` skill）。**課題の状態としては見ない** —— 着地は commit までで live を触らないので、人が live を編集していることは課題の異常ではない。掛けると、**関係のない課題まで含めてキュー全体が人待ちになる。**

**容量に数えない**。どの課題の branch も持たないので帰属先が無い（repo の本体 checkout も同じ）。
数えるのは着地面の linked worktree だけ。

**「編集しても走っている自分自身に反映されない」は制約ではない**。正しい意味論として採る —— 走って
いるプロセスが古い binary で動き続けるのと同型で、**実行中に手順書が書き換わるほうが事故**（実測で、
中間状態の skill が全セッションへ配られ、別セッションがそれを commit した）。

## 実行面

**面ごとに 1 worktree**。「1 課題 = 1 branch = 1 worktree」は面の中で崩さない。

**cwd は、制御面が着地面に含まれるならその worktree、含まれないなら claim の記録の `landing` の
先頭の面**（claim 前に決めるなら本文の宣言順の先頭）。**claim 後に本文を引き直さない** ——
着地面そのものは claim で凍っているのに実行面だけ本文へ戻すと、**claim 後に人が `Lands in` を
足したり並べ替えたりしたときに、worktree の無い面へセッションを置こうとする**（面の集合は正しい
のに、置き場だけがぶれる）。**claim は宣言順を保って記録する。**

**project 差分 skill は制御面 checkout の絶対 path から読む。cwd で引かない**。cwd が制御面の外にある
セッションでも、Status の対応表・停止条件・資源キーの規則を読めなければ `interactive` に落ちて
lease を一度も待たずに着地まで走る。**「読めなくてよい」で済ませない。**

## 面をまたぐ path の突き合わせ

`invalidationScope` と `expectedWrites` は面をまたぐので `<owner>/<repo>: <path>` の形を取りうるが、
**git の diff が返す path は常に repo 相対**。ここを素の文字列一致で比べると、接頭辞のぶん永久に
非交差になり、**書いてある scope が一度も効かない**（fail-open）。

**面 S の変更を評価するときは、こう読む。**

| scope の書き方        | 面 S の評価で                                     |
| --------------------- | ------------------------------------------------- |
| `S: <path>`           | 接頭辞を外し、`<path>` として使う                 |
| 接頭辞の無い path     | 制御面の path とみなす（既定が制御面 1 面だから） |
| `T: <path>`（S 以外） | 使わない                                          |

**制御面は着地面に含まれなくても、base と失効の判定からは外さない**。project 差分と共有ファイルは
そこにあり、**どの課題もそれを読んで計画を立てている** —— 外すと、規約が変わったのに気づかないまま
古い前提で実装が続く。

**着地面に制御面以外がある課題では、scope の全要素に接頭辞を書く。**書く側の規則で、**欠けていたら
判定不能として交差扱い**（読む側の fail-closed）。git が返す path は常に repo 相対なので、**素の path を
書くのが自然な手つき** —— そのまま置くと制御面の path として読まれ**、その面の統合先が進んでも永久に
非交差になる**（scope を書いたのに一度も効かない。記録が無いより悪い）。

**解釈できない形が混ざったら交差扱い**（fail-closed）。scope は「変わると結論が崩れる範囲」なので、
読めないものを非交差へ倒すと、崩れたことに誰も気づかない。

## 資源キーは着地面をまたがない

**資源キーの path は repo 相対**なので、別 repo の path は写像の定義域の外に落ちてキーを生まない
（規則は project 差分）。**これは穴ではない** —— 隔離が済んでいれば、同じファイルを別 worktree で
書く 2 つの課題がぶつかるのは merge のテキスト衝突で、そこは integration lease と rebase が担当する。

**面ごとに write 資源キーを足さない**。足しても守るものが増えず、キーの空間が repo の数だけ増える。
