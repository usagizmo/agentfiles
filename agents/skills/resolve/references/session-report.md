# セッションまとめ

**CI が緑になってから出す**。PR へコメントし、同じものを枚へ載せて人に見せる。
落ちている間に出すと、直すたびに書き直すことになり、人は古い版を読んだまま可否を決める。

**出すのは全件。ただし提示は着地の gate ではない** —— 出したあと答えを待つのは意図の確認が
要る変更だけで（要否は `intent-record.md`）、要らない課題はそのまま着地へ進む。
全件を待たせると、人が居ない間はどれも着地しない。

応答は流れて消えるが、PR は変更と一緒に残る（閉じる Issue と違い、後から `git blame` → PR で
辿れる）。日常的に読まれる場所ではなく、必要になったときに引ける場所として置く。

**読まれる場所は別に要る**。積み残しが無くても必ず Artifact にする —— 人が「何が起きたか」を
読む唯一の面で、言うことが無いセッションほど、人は中身を知らないまま着地を迎える
（計画の段階で必ず作るのと同じ理由）。**この課題の枚を書き直す**（引き当て・節の作り方は
`artifact.md`）。原本は PR のコメントで、PR 本文には枚の URL だけを併記する。着地すると
worktree ごと消えるので、引ける場所しか無いと積み残しはそのまま忘れられる。

**PR が無いまま止まるときも出す**（CI が詰まって進まない・着地の前提が満たせない・人待ちのまま
終える）。PR を条件にすると、着地しなかったセッションほど何も残らない。
そのときは同じものを Issue コメントへ残し、そちらを SSOT にする —— 原本の置き場が無いと
枚も作れない。

- 変更の要点
- 変動した Issue すべて（作成・クローズ・更新。番号 + 一言）
- 積み残し・懸念点（下記の形式）
- **skill / docs へ反映したもの**と、**しなかったものとその理由**

**懸念は 1 件につき次を埋める。**「懸念がある」だけでは放置してよいか判断できない。
埋まらない項目があるなら、その項目自体を「不明」と書く。

| 項目       | 中身                                                                |
| ---------- | ------------------------------------------------------------------- |
| 何が       | 観測した事実（推測と分ける）                                        |
| 影響範囲   | 誰の・どの操作が・どれくらいの頻度で当たるか                        |
| 放置すると | 次に何が起きるか。起きないなら「起きない」                          |
| 判断材料   | 選ぶために必要な事実（コスト・代替案・前例）                        |
| 推奨       | このブランチで続けて着手 / 対応不要 / 別 worktree へ切り出し + 理由 |

推奨を決める情報が足りなければユーザーに質問する。
