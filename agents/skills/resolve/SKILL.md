# 課題解決

課題 1 件の状態機械。各ステップの中身は各 skill が SSOT。

工程は名前で呼ぶ（番号は増減する）。**外部から工程を指すときも名前で指す。**

**その工程に入るときだけ reference を読む。**起動時に全部読まない**。計画を作り直す瞬間だけは工程を問わない** — 失効通知・前提誤り・未宣言の資源が出たら、その場で `references/replan.md`（base を先に更新しないと失効通知が収束しない）。

**着地面の解決だけは起動時に済ませる**（下記）。どの repo を読み書きするかが決まらないと、どの工程も座標を持てない。

| 工程                 | 中身                                                                                                                                                                                                                                                                                                                                                                        | 入る前に読む                                                                                                               |
| -------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------- |
| **prepare**          | 読み取りのみで方針を決め、**計画を外部化する**。**枚を更新して提示し、答えは待たずに進む**（下記）                                                                                                                                                                                                                                                                          | `references/artifact.md`・`references/landing-surface.md`                                                                  |
| **write 待ち**       | managed のみ。待つ間は idle                                                                                                                                                                                                                                                                                                                                                 | —                                                                                                                          |
| **実装**             | —                                                                                                                                                                                                                                                                                                                                                                           | **予定範囲を超えた・新しい資源に触った・別 Issue まで片付けた**ら `references/scope.md`。迷ったら `references/judgment.md` |
| **仕上げ**           | **編集した着地面ごとに** `finish`（規模別）。**1 面でも残さない**（下記）                                                                                                                                                                                                                                                                                                   | —                                                                                                                          |
| **検証**             | プロジェクトの検証 skill（例: `verify-app`）。**レポートを提示する**（まとめは緑になってから）                                                                                                                                                                                                                                                                              | —                                                                                                                          |
| **提出**             | **着地面ごとに**統合先へ追随し、**資源キーの宣言を実体に合わせてから、**PR を使う面で `pr`**。`managed` は base を統合先以外にしない**（積み上げると着地の前提を満たせず、integration を握ったまま渡され続ける。順序は `Depends on` と選出が持つ）。**全着地面の検証が終わり、PR を使う面では CI が緑になるまでここ**。揃ったらセッションまとめを出し、枚を更新して提示する | `references/session-report.md`。残ったものの振り分けは `references/scope.md`                                               |
| **意図の確認**       | 要否の述語と要否・結果の残し方は `references/intent-record.md`。要るなら実物を見せて明示承認を待つ。**要否を決めたら枚を書き直す**（要らないと判定したときも）                                                                                                                                                                                                              | `references/intent-record.md`。見せ方は `references/intent.md`                                                             |
| **integration 待ち** | managed のみ。**merge だけが直列化点**                                                                                                                                                                                                                                                                                                                                      | —                                                                                                                          |
| **着地**             | **PR を使う面だけ** `ship`。**PR を使わない面は commit までで着地している**（統合先への merge は人が行う）。**`managed` は渡しの記録が自分の対象集合を指していることを先に確かめる**（意図の確認は variant を問わず見る）                                                                                                                                                   | `references/integration-record.md`（`managed` のみ）・`references/landing-surface.md`                                      |

**仕上げは面ごとに通す**。`finish` とその先の `commit` は 1 つの木しか見ないので、**編集した面の数だけ
回す**（規模の判定は課題全体で 1 回、通すのは面ごと）。1 面でも残すと、その面は dirty のままなので
`着地待ち` に到達せず、**write を渡し直されては同じ所で止まる**。**面ごとに規約が違う**（検証も
commit の作法も project 差分が持つ）ので、その面の規約を読んでから通す。

**回すときは、その面の worktree を作業ディレクトリにする**（`cd`）。`finish` とその先の `commit` は
cwd の木しか見ず、`git -C` に当たる受け口を持たない —— **絶対 path で書けるのは編集までで、
commit を作る操作は cwd に縛られる**。着地の `merge` だけは操作台を引数で受ける（あちらは統合先が
出ている別の木を触るため）。

**セッションまとめの契機と置き場は `references/session-report.md` が SSOT。**面の型ではなく **PR が実在するか**で決まる —— PR を使う面が 0 commit で透過した課題には PR が無いので、面の型で分岐すると存在しない PR へ書こうとして出せなくなる**。PR を持たない面では、まとめの公開が「提出した」の唯一の観測材料**なので、出すまで integration の受け手にならない。

**PR を merge する直前に、その面が「提出済み」として妥当かを確かめる**（`references/session-report.md`）。
integration を渡されてから merge するまでのあいだに、追随・amend・追加の commit で `heads` は
簡単に古くなる —— 古いまま merge すると、**検証も報告もしていない変更がそのまま default へ入る**。
食い違っていたら着地せず、検証と提出からやり直す。

**PR を使う面が無い課題は、integration lease を待たない**。merge が無いので直列化する対象が無く、待つと**誰も渡しに来ない枠を待って止まる**（枠は merge のためだけに在る）。

**PR を使わない面は、commit を積んだ時点で着地している**。統合先への merge は人が行うので、そこを待たない —— 待つと、**人が動かすまで終端に到達せず worktree が枠を焼き続ける**。

**PR 作成と CI は integration lease の外側**。CI はブランチごとに独立して回るので直列化しても速くならず、先に lease を要求すると「PR があること」を条件に出す側と待ち合って止まる。

## 着地面を先に解決する

**どの repo へ書くかは、実装を始める前に決まっていなければならない**。既定は Issue が置かれた repo（制御面）1 面で、違う課題は claim の記録の `landing` が持つ（意味論は `references/landing-surface.md`、形は `references/same-branch.md`）。

**cwd で引かない**。着地面が制御面と違うセッションは制御面の外に居るので、cwd から辿ると自分の repo の規約だけを読むことになる。**次の 2 つは常に制御面 checkout の絶対 path から読む。**

| 読むもの                                | 置き場                                              |
| --------------------------------------- | --------------------------------------------------- |
| project 差分 skill（`<skill>-project`） | 制御面 checkout の `.agents/skills/<name>-project/` |
| project が持つ共有ファイル              | 制御面 checkout の `.agents/shared/`                |

**harness の skill 一覧に出ないことを「無い」と読まない**（一覧は cwd から作られる）。出ていなければ、上の path を直接読む。**読めないまま進めない** —— Status の対応表を落とすと `interactive` に落ち、lease を一度も待たずに着地まで走る。

**実行面は着地面ごとに 1 つ。**セッションが居るのは 1 面だけで、残りの面は絶対 path で書く（どの面に居るかは `references/landing-surface.md`。claim 後は記録の順で決まり、本文からは引き直さない）**。面ごとにセッションを分けない。**

## variant

**起動したら `references/wait-record.md` の「起こし直されたら」を実行し、あわせて休止の記録（`yield`）を読む** —— 記録が残ったまま起こし直されたなら、交差する先発がまだ書いている。**渡し直されるまで書き始めない**（記録を消すのはキュー管理側で、交差が自分の側で解けたときにも消される。記録が無いことは「書いてよい」ではなく「休止は解けている」だけで、`managed` が書き始めてよいのは write を渡し直されたときに変わりはない）。

渡された課題が **claim 済み**（Status が進行中 + assignee が自分 + 渡された番号のいずれかの **制御面の** remote branch）なら `managed`。それ以外は `interactive`。

**remote branch は制御面 checkout の絶対 path から引く。cwd で引かない** —— 着地面の branch は push しないので、cwd が着地面の worktree にあると `origin/*` に何も無く、**Status も assignee も揃っているのに `interactive` へ落ちる**。lease を待たない variant なので、そのまま着地まで走って共有面での並行着地が戻る。

**「進行中」に当たる Status 名は project 差分の対応表から引く**（複数の名前が写ることがある）。推測で判定しない —— 外すと `interactive` に落ち、下記のとおり lease を一度も待たずに着地まで走る。

**対応表が無いときは Status を使わず、claim の証跡で決める** —— claim の記録の `members` に自分が居る・渡された番号の **制御面の** remote branch がある・assignee が自分、のどれかがあれば `managed`、1 つも無ければ `interactive`。**`managed` へ倒さない** —— 対応表が無い環境では lease を出す側も起動できないので、待っても誰も渡しに来ない。

**「無い」と「読めない」を同じに扱わない。**

| 観測                                                                   | 扱い                                         |
| ---------------------------------------------------------------------- | -------------------------------------------- |
| project 差分が**存在しないことを確かめられた**                         | 上の証跡で決める（`interactive` へ落ちうる） |
| 存在するはずなのに**読めない**（制御面を解決できない・取得に失敗した） | **止めて報告する。決めない**                 |

後者を「無い」へ丸めると、**読み取りに 1 回失敗しただけで `interactive` に落ち、lease を待たずに着地まで走る** —— この機構が守っている直列化が、観測の失敗で外れることになる。Status は claim から着地まで単調に進むので、人待ちで止まっている間も `managed` のまま（巻き戻さないのはこの判定を壊さないため）。

**複数番号を渡されたら、そのどれか 1 つで branch が見つかれば claim 済み**（理由は `references/same-branch.md`）。全番号に branch を求めると `interactive` に落ちる。

**見るのは「進行中」であって「計画済み」ではない**。claim はセッションを起こす前に Status を進行中へ移すので、渡された時点で計画済みは残っていない。計画済みで判定すると全部 `interactive` に落ち、lease を一度も待たないまま着地まで走る。

| variant       | lease                            |
| ------------- | -------------------------------- |
| `interactive` | 要らない                         |
| `managed`     | write / integration lease が要る |

**`interactive` が lease を待たないのは意図**。人が 1 件を直接頼んだときに、キューの都合で断らない・止まらないための設計で、単独で最後まで走りきる。同じ課題をキューが同時に取りうるが、それは直接頼んだ側が引き受ける。「二重着手の穴」として塞がない。

**variant で着地の可否は変わらない**。違うのは lease を待つかどうかだけ。lease を誰が出すかは知らない。空くまで idle で待ち、渡されたら続きを進める。

**人を待って止まったときは write も integration も返っている**。答えを受け取ったらまず記録を `cleared` にし、`managed` は**渡し直されるまで書き始めないし、着地もしない**（停止条件・意図の確認のどちらも同じ）。止まっている間に枠は別の課題へ回っているので、勝手に進めると交差する 2 つが同時に書くか、2 件が同時に merge へ進む。

**休止を伝えられたら、次の不可逆操作の前まで書いてから応答を終える**（commit できる地点まで）。`interactive` にも効く —— lease を待たない variant でも、交差する先発が居ることは外からしか分からないので、伝えられた時点で従う。

1. **worktree と未コミットの変更は保持する**（破棄しない）
2. **渡し直されるまで再開しない**（先行の着地は自分からは観測できない。ポーリングもしない）
3. 渡し直されたら **各着地面の統合先へ追随し、`references/replan.md` の表で判定する** ——「休止していたから再 plan」ではない。先行が着地したとは限らず（`着地待ち` へ進んだだけ・人待ちに落ちた・資源キーを描き直した、のどれでもありうる）、先行が着地するまで統合先は動かない（PR を使う面では、先行の push は default を動かさない）。統合先が無関係な場所だけ進んでいるなら rebase だけで、計画は再利用する。休止と再開は繰り返し起きるので、ここを一律の再 plan にすると往復のたびに費用が乗る
4. **人待ちの記録は書かない**（`references/wait-record.md`「書かないもの」）。待っていることは次項の 1 行だけで表す

**待つ = 応答を終えて idle になること**。ポーリングも sleep もしない。再開は外から渡される。

**待って応答を終えるときは常に、何を待っているかを最後の応答に 1 行書く**。lease 待ちも人待ちも同じ（何が空けば・誰が何を答えれば進むのかが、外から見える唯一の手掛かりになる）。

**そのうち人の答えを待つなら、聞く前に記録を書く**。述語は「人に聞いて応答を終えるか」であって、下の停止条件に当たったかではない —— 手順と理由は `references/wait-record.md`。

## prepare

**書き込まない**。全着地面の最新の統合先を読んで、実装計画を Issue コメントに残す。実装を始めるのは、`managed` なら write lease が来てから（`interactive` は待たない）。

**「書き込まない」を手順で担保する**。文章の約束だけだと、破れたことに誰も気づかない。

1. **始める前に、全着地面の worktree が clean であることを確かめる**。汚れているなら、その事実を報告してから始める
2. **計画を投稿する直前にもう一度確かめる**（全着地面の worktree）。差分が出ていたら投稿せずに止まり、変わった面と path を報告する —— 調べるだけのはずの工程が書いているので、原因を潰さずに進めない

   **live checkout は見ない**。人が触っているのは正常で、prepare が書いた証拠にならない —— 見ると、制御面の本体を人が編集しているだけで着手できなくなる（live の異常を扱うのは、そこへ merge して着地する面の着地工程だけ）

3. **投稿が成功したことを確かめてから**次の工程へ移る
4. **実装を始める直前に、計画コメントがあることを確かめる**

破れると外からは「計画の無い実装中」に見える。**1 ファイル汚すだけで、資源キーが観測できないまま write 保持者になり、キューがそこで止まる**（人が直すまで解けない）。

**原則 `consult` を回さない。**「何を作るか」は Status が計画済みへ進んだ時点で決着している。ここで出すのは「どう作るか」— 触る範囲・資源キー・無効化条件だけ。回すのは、読んだ結果 Issue の前提が崩れていたとき（骨格が変わる新事実）に限る。

計画を外部化するのは、**セッション文脈がキャッシュ、外部化した計画が復旧契約**だから。セッションが失われても、別セッションがこのコメントから続きを組み立てられる状態にする。

固定 marker と機械可読 block で書く。scheduler は自然言語を再解釈せず block だけを読む。

````markdown
<!-- plan -->

```yaml
baseSha: <prepare 時点の制御面の default の SHA>
landingBaseShas: # 制御面以外の着地面があるときだけ。面ごとの統合先の SHA
  <owner>/<repo>: <SHA>
issueDigests: # 対象集合の全件。本文が変わったことの検知に使う
  <Issue 番号>: <本文のハッシュ>
size: 軽微 | 中規模 | 大規模
expectedWrites: # 書く予定。advisory であって契約ではない
  - <path / module>
invalidationScope: # ここが変わったら計画が無効になる。読んで前提にした範囲
  - <path / 契約> # 制御面以外の着地面がある課題では `<owner>/<repo>: <path>`
resourceKeys: # 同時に触ると壊れるものの名前。並列判定に使われる
  - <key>
dependsOn: [<Issue 番号>]
alsoResolves: [<Issue 番号>] # このブランチで一緒に片付ける Issue。二重着手の防止に使われる
```

<!-- /plan -->

方針 / リスク / 検証方針を人が読む文で続ける。
````

ハッシュの取り方は `references/body-digest.md`。

**base は面ごとに要る**。失効の判定は面ごとに「base から統合先まで」を見るので、制御面の SHA だけだと、同じ面へ別の課題が着地しても誰も気づかない。**制御面は着地面に含まれなくても書く**（理由は `references/landing-surface.md`）。

**面のキーが欠けている計画は再 plan 対象**（読む側は判定不能として扱う）。任意キーとして読み飛ばすと、**その面の統合先が進んでも永久に失効しない** —— 交差を書いたのに検知されない計画は、計画が無いより悪い（陳腐化していないと積極的に主張する）。

**外部化したら、枚を更新して提示する**（引き当ては `references/artifact.md`）。着手前に「これから何をするか」を見せるためのもので、**答えは待たない** —— そのまま `managed` は write 待ちへ、`interactive` は実装へ進み、人待ちの記録も書かない（答えを待たないので発動点に当たらない）。

**待たない理由は、ここで待つと計画が最も陳腐化しやすいから**。prepare 直後は統合先が最も動く時期で、返事を待つあいだに `invalidationScope` が交差すれば、見せた計画ごと作り直しになる。見せるのは着手を止めるためではなく、人が違和感に気づいたときに割り込める状態を作るため。

**group は 1 計画なので、単一の値では非代表の変更を検知できない** — 番号ごとに持つ。

**`expectedWrites` と `invalidationScope` は別物**。前者は書く範囲、後者は変わったらやり直しになる範囲で、後者が無いと再 plan の判定ができない。

同じ marker のコメントを複数作らない。更新するときは既存コメントを書き換える。

## 宣言を実体に合わせる

**資源キーの宣言は、広げるのと狭めるので契機が違う。**

| 向き       | 契機                                                                                         |
| ---------- | -------------------------------------------------------------------------------------------- |
| 広げる     | **予定になかった面を触ると決めた時点**（最初の write より前）                                |
| 列挙不能へ | **着手前に触る面を列挙できないと判断した時点**（形は project 差分）                          |
| 狭める     | **提出の直前 1 回だけ**（各面が統合先へ追随し、**全着地面の** worktree が clean になった後） |

**狭めるのは、宣言が着手前の予定だから**。予定したが書かなかった面・途中で revert した面が残ると、着地まで実体の無い交差が続き、交差する課題を休止させ続ける。

**測るのは、追随で確定した統合先と HEAD の差分を、着地面ごとに取った和集合**。「直近の commit が何を触ったか」で測らない —— まだ着地する変更が残っている面を落とすことになり、同時書き込みの検出をすり抜ける。clean が前提なのはこのため。汚れているなら狭めない。

**1 面でも測り落とさない**。落とした面の書き込みが宣言から消え、その面で交差する課題と並列に走る。

**書く予定の範囲も同じ書き込みで揃える**。宣言だけ狭めると被覆の検査が成立しなくなり、毎 tick 再 plan を促され続ける（導出と被覆の中身は project 側）。

**読んで前提にした範囲は狭めない。**書かなかったからといって、読んだ前提が消えるわけではない**。base も、狭めただけでは更新しない**（`baseSha` と `landingBaseShas` のどちらも）。

**狭めるのは再 plan ではない**。既に失効を伝えられているなら、先に通常の再 plan を済ませてから狭める —— 狭めることで失効の通知を握りつぶさない。

**CI が落ちて、狭めた面をまた書くことになったら広げ直す**。**`managed` は、広げ直したらその面に書かずに応答を終え、渡し直しを待つ** —— 宣言を更新した直後に書くと、外側が交差に気づくまでの窓で 2 つが同時に書く。収束したかは自分では観測できないので、待ち方を決めておく。

**列挙できないと宣言した課題は狭めない**。終端まで宣言のまま置く —— 狭めて新しい課題を入場させたあと、また列挙不能へ戻す経路が無い。

## 着地を先延ばししない

**スコープは広げる。期間は延ばさない**。受入条件を満たして検証が pass したら着地する。「まだ直せるところがある」で伸ばさない。

| 状況                           | 判断                                           |
| ------------------------------ | ---------------------------------------------- |
| 受入条件を満たし、検証 pass    | **着地する**（他に直したいものが残っていても） |
| 今回変更由来の回帰が残っている | 着地しない。直しきる                           |

着地が遅れると、他の作業が古い base の上で動き、rebase と衝突が増える。**気づきを捨てるのではなく、着地を待たせない**。残ったものの行き先は `references/scope.md`。

## 停止条件（managed）

**この表が決めるのは「工程を止めてよいか」だ**。記録を書くかどうかではない（そちらは上の「聞く前に記録を書く」が持つ）。工程を止めて人を待つのは次の 5 つだけで、当たったら記録を `waiting` にして止まる。**Status は進行中のまま動かさない。**

確認の出し方は `references/judgment.md`（判断軸・Artifact・consult 委譲）。

| 事象                                                                           | 扱い                 |
| ------------------------------------------------------------------------------ | -------------------- |
| Issue 本文に無い判断が必要になった                                             | 停止して確認する     |
| 承認された製品境界を越える                                                     | 停止して確認する     |
| CI が詰まって進まない                                                          | 停止して報告する     |
| 実装中に Issue 本文が変わった                                                  | 停止して再承認を待つ |
| **着地の前提が満たせない**（base がその面の統合先でない等で merge へ進めない） | 停止して報告する     |

製品境界とは、**機能の追加・削除** / 新しいユーザー可視挙動 / 非目標への侵入 / 新たな永続形式・migration / 認証・決済・外部送信・公開・破壊的操作の追加 / 設計骨格が変わる新事実。テーマ違いや分量では判定しない。

**判定表があればそれで引く**。path と生成 artifact の変化で機械的に引ける形にしておくと、散文の解釈より速く正確になる。

**表は先に用意するものではなく、育てるもの**。無いうちは上の性質で判定し、迷った path が出るたびに project 差分の表へ足す。表が育つほど人を呼ぶ回数が減る。最初から網羅しようとすると、当たらない行が並ぶだけで判定は速くならない。

判定の chokepoint は **`finish` の commit 直前に diff 全体で 1 回**。実装中に気づいた時点でも判定するが、そこで漏れても commit 前で捕まる。

**使われていなさそうな機能を消すのも越境**。dead code の削除（到達不能なコード）とは別で、ユーザーが使える機能を減らすのは製品判断。

**lease 待ちはここに含めない**。資源が空くのを待つのは実行待ちであって、人の判断待ちではない。
