# 選んだ後の手順

tick の分岐そのものではなく、**その action を選んだ後に何をどう書くか**。選ぶ条件は本文「action の優先順」が SSOT。

**記録の marker を散文で引用しない**。読む側は marker の形だけで拾うので（`harness.md` の起床監視も同じ）、まとめや経緯のコメントに `<!--` と `-->` で挟んだ名前を書くと、**そのコメントが記録として数えられる**。名前だけを書く（周回の記録・人待ちの記録）。

## claim する

**remote branch の一意作成が二重着手の最後の防壁**なので、順序を守る。

1. Issue 契約を検証する（group なら全員分）
2. **着地面を解決する**（本文の宣言 → 座標表。解決できなければ候補を捨てて次へ。規則は `landing-surface.md`）
3. **制御面の** remote branch を代表の番号で一意に作成する。失敗したら候補を捨てて次へ
4. **claim の記録を代表の Issue へ書く**（代表と全員の番号、および解決した着地面。形式は `same-branch.md`）
5. **記録した全員**の Status を進行中にし、assignee を自分にする（group でも代表だけにしない）
6. **着地面ごとに** branch と worktree を作る（同じ branch 名。その時点の統合先から切る）
7. セッションを起こす（`harness.md`）

**4 が書けなければ、3 で作った remote branch を消してから終える。**branch だけが残ると、次の tick は
「claim 済み」と読む一方で `landing` が無いので `Conflict` になり、**再 claim は branch の一意作成で
失敗し続ける**（人が消すまで解けない）**。branch を作るのは記録を書く直前で、書けたことを確かめる
までが 1 手。**

**5 が誰か 1 人でも失敗したらセッションを起こさない**。`resolve` は Status が進行中であることで `managed` と判定するので、台帳がずれたまま起こすと lease を一度も待たない `interactive` として着地まで走る（`integration` が常に 1 という唯一の直列化点が破れる）。branch は残し、次の tick へ返す。

**Project の更新失敗で claim をロールバックしない**。branch が真実で、Status は台帳。ずれは次の tick が直す。

**base は常にその面の統合先から切る** —— 他 branch から切ると、着地判定の commit 包含と計画の base からの失効判定が両方壊れる。制御面では統合先が default branch。

**branch を新しく作ってよいのは、その面に branch が無いときだけ**（claim の初回と、部分 claim で
欠けた面を埋めるとき）。**在る branch は上書きしない** —— 統合先から切り直すと、その面の commit が
ぶら下がった branch を捨てる。起こし直しで worktree を作り直すときも同じ述語で、在れば checkout、
無ければ統合先から作る。**「claim の 1 回だけ」と読まない** —— 部分 claim から復旧する手が無くなる。

**着地面を解決してから branch を作る**。順序を逆にすると、座標表に無い面を宣言した候補で claim branch だけが残り、その branch が `準備中` を立てるので、人が座標表を直すまで `Conflict` のまま滞留する。

## 失敗の記録

**retry budget をセッションの記憶に置かない**（tick は前回の続きを仮定しない）。Issue コメントへ固定 marker で外部化し、正規化と起床スナップショットの入力に含める。

````markdown
<!-- retry -->

```yaml
count: <連続失敗回数>
lastAction: <失敗した action の名前>
```

<!-- /retry -->
````

同じコメントを書き換える（`count` を +1 して upsert する。コメントを増やさない）。**何を数え、何を数えず、いつリセットするかは本文「1 tick」が SSOT。** ここは書式だけ。

## 周回の記録

**実行器を 1 周回して何も出なかった周**を数える。失敗の記録とは別の marker にする —— あちらは操作の失敗、こちらは成功した周の空振りで、解除条件も上限も別（同じコメントに載せると、`lastAction` の対応・成功時のリセット・操作失敗との二重計上が一度に絡む）。

````markdown
<!-- cycle -->

```yaml
mark: <成果の指紋>
count: <成果ゼロで回った周の数>
```

<!-- /cycle -->
````

同じコメントを書き換える（増やさない）。帰属は `same-branch.md`。**当たる action と上限は本文「1 tick」が SSOT。**

**更新の順序を守る。**

1. **action を選ぶ前に**（回す action かどうかに関わらず）`runtime` を撮り、現在の指紋と `mark` を突き合わせる。違えば `count` を 0 にして `mark` を更新する（前の周に成果があった）
2. action を選ぶ
3. **1 で指紋が一致していて、回すことに成功し、かつ 1 で撮った `runtime` が本文の加算条件を満たす周の後でだけ** `count` を +1 する。**`mark` を新しく書いた周は加算しない** —— 前の周に成果があった（または初回）という意味なので、そこで +1 すると許容回数が実質 1 周減る

**3 を回す前に置かない** —— 更新してから dispatch までのあいだに落ちると、回していない周が数えられて tick が冪等でなくなる。後に置けば、落ちたぶんは 1 少なく数えるだけで済む（安全側）。

**回せなかった周はここで数えない**。それは操作の失敗なので失敗の記録が数える。同じ周を両方で数えると budget を 2 消費する。

### 指紋は `scripts/cycle-mark.py` が作る

**この実装が符号化の SSOT**。成分の名前・順序・区切り・長さの数え方・出力表現・git の取り方はすべてそこにあり、**ここへ同等物を書き写さない** —— 散文と実装が割れた瞬間、読んだ側がどちらかを自分で決め直すことになる。

**手で連結しない**。同じ観測から必ず同じ値になることが、action が一意に決まる条件で、conductor は交代する前提の常駐工程だから。作り方が実行器ごとに変わると照合は毎回不一致になり、`count` は 0 に戻り続けて「成果ゼロの周が続いた」は永久に発火しない。

**python3 が要る**。持てない環境では指紋を計算できないので、その tick は照合へ到達しない。**散文から手計算を再発明しない** —— 再現できない値を書くくらいなら、照合を進めない方が安全側。

渡すのは conductor が既に正規化している値だけ。**曖昧さを引数境界へ移さない** —— 呼び出し側に成分の名前を並べさせると、名前を決める自由度が境界へ移るだけになる。

| 引数                                                 | 中身                                                                            |
| ---------------------------------------------------- | ------------------------------------------------------------------------------- |
| `--ledger <値>`                                      | **どちらの式を使うかを決める**（`未計画` なら計画の周、他は解決）               |
| `--progress <値>`                                    | 解決の周のみ                                                                    |
| `--landing <repo>:<path>`                            | 解決の周のみ。**着地面ごとに 1 つ**（面の名前と checkout path）                 |
| `--host <host>`                                      | 解決の周のみ。全着地面の remote が在るべき host（制御面の origin から取る）     |
| `--branch <repo>:<名前>` \| `--no-branch <repo>`     | 解決の周のみ。**着地面ごとにどちらかを 1 回**（**ローカル branch も解決する**） |
| `--worktree <repo>:<path>` \| `--no-worktree <repo>` | 解決の周のみ。**着地面ごとにどちらかを 1 回**（省いた面は成果が指紋に出ない）   |
| `--plan-comment <file>` \| `--no-plan-comment`       | 解決の周のみ。計画コメントの本文                                                |
| `--wait-record <file>` \| `--no-wait-record`         | **有効なときだけ file を渡す**（有効の判定は `wait-record.md`）                 |
| `--issue-body <番号>:<file>`                         | 計画の周のみ。対象集合の全件（並べ替えは実装が行う）                            |

**式を `ledger` で決めるのは、action 名では切れないから** —— 照合は action を選ぶ前に走る。

**着地面を 1 つでも落とさない**。落とした面の成果は指紋に出ないので、そこで書き進んでいる周が成果ゼロとして数えられる —— **直そうとしている欠陥そのものが、引数の渡し漏れとして戻る**。

**「無い」は明示して渡す。**省略は usage error で、指紋は返らない**。取得に失敗した周と本当に無い周を同じ指紋にしない**ためで、失敗した周は指紋そのものが返らず、照合を進めない（`count` も `mark` も触らない）。

**照合できない周でも action の選択は続ける**。照合は周回の記録のためだけにあるので、そこで tick を終えると**着地面を解決できない課題の `Conflict` を報告する経路まで塞ぐ** —— 指紋の入力が揃わない原因がまさにその `Conflict` なので、報告できないまま毎 tick 黙って止まる。飛ばすのは照合だけ。

検査は `scripts/cycle-mark.test.py`。**符号化を変えたら通してから使う。**

### 何を成果と見なすか

**成果物の側だけから作る。**

| 周の種類 | 入れるもの                                                                                                                                                                                                     |
| -------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 解決     | `progress` の値 / **着地面ごとの** branch の head SHA と `git status` が変更として出す tracked（path・index の状態・種別・worktree の中身）と untracked（path・種別・中身）/ 計画コメントの本文 / 人待ちの記録 |
| 計画     | Issue 本文 / `ledger` の値 / 人待ちの記録                                                                                                                                                                      |

- **`runtime` とセッションの状態は入れない**。**commit 数でも引かない**（どちらの理由も `tick.md`）
- **変わったかどうかの判定は git に任せる** —— `core.autocrlf` や `text=auto` があると worktree の生バイトと HEAD の blob は一致しないので、自分で比べると clean な path が毎周 dirty に見える
- **中身まで入れる** —— path と状態だけにすると、既に dirty なファイルをさらに書いた周が成果ゼロになる。真偽値への丸めも同じ理由で不可
- **index の状態も入れる** —— worktree を HEAD に戻したまま staged の中身だけ差し替えた周が、落とすと成果ゼロになる
- **untracked に ignore 対象を混ぜない** —— build 成果物・OS ファイル・ログが毎周動くので、混ぜると指紋が常に変わって成果ゼロの上限が実質発火しない
- **untracked の symlink は参照先ではなく link target を見る** —— 辿ると、指す先が外部で変わっただけの周に成果があったことになる
- **`progress` と人待ちの記録を入れる** —— PR を出す・checks が緑になる・人に聞く・答えが返るはどれも前進だが、head SHA も worktree の中身も動かない。落とすと、`実装中` で育った `count` が `提出中` へ持ち越され、CI 待ちの課題が `退避先` へ落ちる
- **無効な人待ちの記録を数に入れない** —— 問いの空な `waiting` を自動で `cleared` にする経路があるので、入れると「閉じただけ」の周が成果ありに見え、空の人待ちを書いては止まる往復のあいだ `count` が 1 を超えない
- **着地面ごとの成分は面の名前と組にする** —— 名前を落として値だけ並べると、面が増減したときに別の面の値と入れ替わり、動いていない周が成果ありに見える
- **branch も worktree も無い段階でも作れる**（claim 前・checkout を作る前・終端で実体を消した後）。作れないと、照合が済むまで action を選べない。**段階で免除を分けない** —— 分けると、免除の側を広く読んだ実装が照合を飛ばす

### 見えないもの

**成果物が動いても指紋に出ない経路が 2 つある**。**`退避先` へ落ちた課題では、まずこの 2 つを疑う。**

- **`skip-worktree` / `assume-unchanged` を立てた path** —— git 自身が変化を見ないので、中身を書き換えても成果ゼロの周として数えられる。塞ぐには全 tracked を毎周読むことになり、費用が釣り合わない
- **untracked な nested repository の中身** —— git が `nested/` の 1 件に畳むので、出現と消滅は見えるが中の commit と編集は見えない
- **観測の途中で書かれた成果** —— 成分は別々の時点で撮るので、読んだ後にそこだけ書き換えられると取りこぼす。**commit だけは前後で HEAD を撮って閉じてある**（1 回で全成分を動かすぶん窓が最も広い）が、index と worktree の残りは開いたまま。全成分を撮り直しても窓は縮むだけで消えず、費用は倍になる

**tracked な submodule だけは畳まずに落ちる**。worktree の側からはディレクトリにしか見えず、指している commit が動いた周と動いていない周が同じ値になるので、符号化を決めるまでは観測の失敗にしてある（その周は照合を進めない）。**落ちるのは変化が観測されたときだけ** —— clean な submodule には表せない変化が無いので、そこでは止まらない。**untracked の nested repository を同じ扱いにしない** —— あちらは記録された状態の一部で tip が成果そのものだが、こちらは課題の成果物ではない外部の物体で、落とすと迷い込んだ clone 1 つで健全な課題の照合が毎周止まる。

**`mark` が無いときは壊れた記録にしない**。現在の指紋を書いて `count` を 0 にする（初回の周がここに当たる）。fail-closed へ倒すと、健全な課題が最初の周で止まる。

**符号化を変えたら旧 `mark` は捨てる**。変換も新旧の併用もしない —— 旧値に根拠が無ければ変換元として定義できず、OR 一致を許すと勝手な命名が残り続ける。全件が 1 度だけ不一致になって `count` が 0 に戻る（退避が最大 1 周遅れる安全側）。

## 休止の記録

後発に休止を伝えたことを外部化する。conductor が書き、conductor が消す。消す契機と、解除条件を足してよいかの判定は本文「action の優先順」が SSOT。ここは書式だけ —— **述語の実体を写すと片方だけ古くなる。**

````markdown
<!-- yield -->

```yaml
issues: [<Issue 番号>] # 対象集合の全番号
to: <先発の Issue 番号>
keys: [<交差した資源キー>]
```

<!-- /yield -->
````

同じコメントを書き換える（増やさない）。`runtime` への写り方は本文「正規化」が SSOT。

## 片付ける

**所有していないものは消さない**。手順は `harness.md`。`refine` は pane を閉じるだけ、`resolve` は **全着地面の worktree** を片付ける。

**途中で止まっても、台帳の `完了` から再開できる**。面ごとに消すので、1 面を消した時点で止まると
`progress` は終端から退行する（消した面ではまとめの `heads = T` が崩れる）—— だから 4 で先に
`完了` を書き、片付ける action はそこも入口にする。**記録を消すのは実体を消し終えてから**（順序が
逆だと、途中で止まったときに何が残っているか引けなくなる）。

**消す対象は `progress` で決まる。**

| `progress` | 消すもの                                                                                                    | 残すもの                      |
| ---------- | ----------------------------------------------------------------------------------------------------------- | ----------------------------- |
| `着地済み` | 全着地面の worktree・セッション・**merge 済みの** branch・制御面の claim branch・claim の記録・その他の記録 | **merge されていない branch** |
| `取り下げ` | worktree・セッション・記録                                                                                  | **branch と claim の記録**    |

**merge されていない branch を消さない**。PR を使わない面の着地は commit までなので、**統合先への
merge がまだでも `着地済み` になる** —— そこで branch を消すと、push していない commit が reflog 以外に
残らない。人が merge するまで branch を置き、worktree だけ返す（枠を握るのは worktree なので容量は返る）。
**片付けが再発火しないのは、その branch が消す対象に入っていないから。**

**1 面でも残したら片付いていない**。容量は worktree の本数で数えるので、漏れたぶんはそのまま枠として焼け続ける（`progress` は終端なので、片付ける action の条件から外れて二度と拾われない）。

**あわせて制御面の claim branch を消す**（着地面に制御面が含まれるかに依らず）。claim の防壁は常に制御面の remote branch なので、**そこを消さないと終端に達した課題が claim 済みのまま残る** —— Issue を開き直しても選出の「その番号の remote branch がある」に当たり、二度と claim できない。制御面が着地面でもある課題では、この branch は面の片付けで一緒に消える。

**live checkout は片付けの対象ではない**（`landing-surface.md`）。消しにいくと人と全セッションの読む面が消える。

### 片付ける前に成果を確認する

**worktree とセッションを消すと、セッションまとめが一緒に消える**。積み残し・懸念・気づきはそこにしか無く、git にも Issue にも残らない。着地の確認と片付けを続けて実行しない。

1. **セッションまとめの記録があるか確認し、`積み残し・懸念` を人へ渡す**（`resolve` は着地前に書く規約）。**固定 marker で引く。提出のものと止まったもののどちらでもよい**（要るのは成果が残っていること。形式は `session-report.md`）—— PR が無い課題では Issue コメントが原本なので、文字列一致で探すとどれがまとめか決まらない
2. 載っていなければ pane から回収する。pane も消えていれば harness の transcript を探す
3. **どこにも無ければ片付けず報告する**。消えたものは復元できない
4. **`着地済み` のときだけ、実体を消す前に台帳を `完了` へ寄せる**（下記）。**`取り下げ` では台帳を触らない** —— 手で close しただけの未着地が `完了` になると、`Depends on` の解消（`着地済み` または closed かつ `完了`）を満たして**失敗した前提の上で後続が着手する**
5. **`着地済み` で Issue がまだ open なら close する**。**1〜3 を通ってからでないと閉じない** —— まとめを回収する前に閉じると、片付ける action の条件から外れて報告ごと消える
   - **面の構成で分岐しない**。「PR を持つ面があるなら merge が閉じる」は、その面に commit があるときだけ成り立つ —— 0 commit で透過した面では PR が存在せず、**Issue が open のまま残って `未着手 × 完了` の `Conflict` へ退行する**（branch を消すと終端の証跡も消えるため）。既に closed なら何もしない
   - **`取り下げ` では閉じない**。PR が unmerged で closed になっただけの課題は、Issue を開けておくかどうかが製品判断
6. **`着地済み` なら claim の記録も消す**。branch だけ消して記録を残すと、Issue を開き直したときに「claim 済み」と読まれて**二度と claim できない**（判定材料は記録・branch・`alsoResolves` のどれか 1 つで足りる）
   - **`取り下げ` では記録も branch も残す**。未マージ branch を残すのは実装を守るためなので、記録だけ消すと**再 claim が同名 branch の衝突で落ちる**（作業も再開できない）。両方残せば、Issue を開き直したときに `準備中` として観測され、起こし直しが既存 branch を checkout して続きから進める
7. 片付けたら、人待ちの記録が `waiting` のままなら `cleared` にする（`wait-record.md` の例外行）。閉じ損ねると `runtime` が `人待ち` のまま残り、片付けが毎 tick 空振りする。**渡しの記録と周回の記録が残っていれば同じ手順で消す** —— 渡しを残すと merge の枠が空かず、周回を残すと片付ける条件に当たり続ける

**存在確認だけで済ませない**。まとめは「消えていないこと」を確かめる対象ではなく、人が読んで次のアクションを決める材料。`積み残し・懸念` は 5 項目（何が / 影響範囲 / 放置すると / 判断材料 / 推奨）で書かれているので、そのまま状況ボードと応答へ出す。

**「対応不要」と書いてあっても落とさない**。それは書いた側の推奨であって、人の判断ではない。実際に、非目標だと誤って整理された改名がまとめの `反映しなかったもの` に埋もれ、人が拾って Issue になった事例がある。判断の材料を渡すのが片付ける側の責務で、取捨は人が決める。

**報告先を混ぜない**。状況ボードには出続けるのが正しく、Issue コメントは同内容なら追記しない。分けないと「毎 tick 同じコメントを投稿する」実装が通る。

**台帳を先に寄せるのは、片付けると終端の証跡が消えるから**。PR がある課題は `merged` が残るので後から
「台帳を進める」で拾えるが、**PR を持たない面では branch を消した時点で commit の包含が引けなくなる** ——
`着地済み` が導出できなくなり、close 済みなら `取り下げ`（台帳を触らない行）に落ちて `進行中` のまま
固定される。実体を消す側が同じ手で寄せれば、証跡が在るうちに確定する。

**片付けた後に `取り下げ` と読まれるのは正常**。終端の 2 値はどちらも上 3 つの action しか受けず、
台帳は既に `完了` なので盤面も正しい。

**3 で止めたときは `cleared` にしない**。実体が既に消えている課題で閉じると、片付ける action の条件（`capacity` / セッション / 人待ちの記録）を全部外して二度と選ばれなくなり、報告だけが消える。毎 tick 報告が出続けるのが正しい。

経緯・報告のコメントは同内容が既にあれば追記しない（tick ごとに同じ報告を投稿しない）。失敗の記録は別で、上記のとおり同じコメントを upsert して `count` を伸ばす。

## 計画の失効

**action の 1 つ**（優先順の「計画の失効を伝える」）。他の action と同じく、1 tick に 1 つだけ実行して観測へ戻る。

**届け先が居ないなら伝えない**。セッションが死んでいるときは「起こし直す」が先に実体を戻し、起こされた側が計画コメントの `baseSha` を読み直す。伝えたことにして飛ばすと、前提が崩れたまま実装が続く。

**人待ち中と休止中は伝えない**。人の回答を待っている最中に別の指示を送ると質問が流れ、休止中に送ると休止が破れて（`稼働中` に戻って）促し直しの失敗が積まれる。休止した課題は再開時に再 plan する。`cleared` になって `待機` に落ちた時点で、**枠を渡すより先に**伝える（優先順が既にその形）。

「本文の変更」も同じ扱い。届け先が居ない・人待ち中は伝えず、起こし直しを先に通す。収束条件はその action の発火条件が偽になること（条件と例外の解除は本文「1 tick」が SSOT）。

伝えた後も発火条件は真のままなので、再 plan で計画が更新されるまで再発火しうる。**再送を止める状態を記憶に持たない** — 代わりに、伝えた側が計画コメントを更新するまでの間は `runtime` が `稼働中` なので、次の tick では優先順の上位（片付け・差し戻し）に当たらない限り同じ通知になる。同じ内容の再送は害が無い（受け手は冪等に再 plan する）。**繰り返しても更新されないままなら失敗として数える**（規則は本文「1 tick」）。

**統合先が進んだら、稼働中セッションの計画と突き合わせる**。実装セッションは統合先を監視できない（待つ間は待機で、ポーリングしない）ので、conductor が伝えないと誰も気づかない。

**面ごとに「base から統合先まで」の変更 path を取り、**計画の `invalidationScope` か `resourceKeys` に交差したら、そのセッションに伝えて再 plan させる（発火条件の実体は本文「action の優先順」が SSOT）**。交差しなければ何もしない** — 無関係な進行で実装を止めると、統合先が動くたびに全セッションが中断する。

**制御面だけで測らない**。同じ着地面へ別の課題が着地しても、制御面の default は動かない —— 見落とすと、同じ面で並行している課題が古い前提のまま最後まで走る。

伝えないと、着地直前の rebase まで前提の崩れに気づけない。検証も意図の確認も済ませた後なので、そこで判明すると手戻りが最大になる。
