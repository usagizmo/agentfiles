# 正規化と action の論証

読むのは、本文の正規化のラダーと action の優先順を書き換えるときだけ。tick では読ま**ない**。

ここが持つのは**なぜその順序・その条件なのか**だけ。述語も既定値も持たない（SKILL.md と `src/` が SSOT）。

## 正規化のラダー

group を 1 レコードに畳まない: 一部だけ計画済みの group は `ledger` が 1 つに決まらず、未計画側の refine が起きないか計画済み側を早期 claim するかになる。

終端を最上段に置く: `ship` は remote branch を消さないので、merge 直後は「branch あり + commit あり」も同時に真になる。終端を先に確定しないと、正常な着地のたびに `Conflict` で止まり、片付けに到達しない。

worktree の有無を見ない: 有無を入れると、着地待ちの worktree が消えた瞬間に `未着手` へ退行し、着地済みの課題を未着手として選び直す。dirty は別で、worktree ごと消えたならその実装は失われているので `準備済み` へ戻るのが正しい。

checks の緑は `classifyChecks` だけが出す: `statusCheckRollup` には結果の入る欄が違う 2 種類が混ざる（`CheckRun` は `conclusion` / `status`、外部サービスの `StatusContext` は `state` で `conclusion` は常に `null`）。`status` を落とすと実行中の CheckRun が空になり、`running === 0` に見える。条件付きで飛ばす check を未完了に倒すと、それが混ざる PR は永久に `着地待ち` へ上がらない。抽出は `scripts/pr-list.jq`、畳みと緑は `src/checks.ts`。

`mergeStateStatus` で代用しない: `CLEAN` は checks 以外（衝突・必須レビュー・default への追随）まで含むので、default が動くたびに `BEHIND` へ落ちて `着地待ち` から外れる。追随は渡された後にやる契約なので、渡す前に要求すると誰も受け手になれない。

着地を PR の `merged` で見る: 包含だけを主条件にすると、squash merge で着地済みが未着地に見える。PR を持たない面の着地は `landing-surface.md`。

終端の「空でない」を面ごとに要求しない: 要求すると、その面に書かなかった課題が終端に到達できない。**0 commit を「まだ着地していない」と読むか「着地するものが無い」と読むかの違いで、後者が正しい**（着地するものが無い面は、待っても永久に commit を持たない）。

成果ゼロを課題側でも git の範囲で測らない: `統合先..branch` は着地すると空になり、claim 時 SHA からの範囲は追随だけで非空になる（別の課題がその面へ着地したあと rebase すれば、1 行も書いていない課題が成果ありに化ける）。着地の前後で答えが変わらず、追随では生まれないものが提出の証跡しかない。

PR を持たない面の `着地待ち` に、まとめの記録と clean の両方を要求する: 記録だけだと、着地の直前に書き直し始めた課題が `着地待ち` のまま dirty になり、write を非保持のまま書く。clean だけだと、実装の途中で commit した瞬間に `着地待ち` へ上がり、まだ書く気の課題から write が離れる。**本体は PR を作る行為に当たる明示的な合図**で、clean はその合図が古くなったことの検出。

まとめの記録を `progress` の入力にする: PR を持たない面には「提出した」を表す観測材料が他に無い。無いままにすると、commit があることと実装の途中であることを区別できず、終端に到達できない（成果ゼロを弾く役目も同時に失う）。新しい記録を作らずに済むのは、まとめが既に着地前に必ず出る成果物だから。

`計画中` を `progress` に置かない: 計画セッションの有無は実行器の話で、成果物は進んでいない。セッションが消えただけで成果物の進捗が退行する形にしない。

`人待ち` を最上段に置き、セッションの有無を条件に入れない: 入れると「答えを解釈して `cleared` にした直後の idle」がどの値にも当たらず、人待ちからの復帰が `Conflict` で止まる。

`waiting` を無条件に `人待ち` へ写さない: 実行資源待ちを人待ちとして書いた記録があり、最上段に写すとその課題はどの遷移にも当たらないまま滞留する。

「分類できない」を丸めない: 実行器の側が「agent は居るが分類できない。完了の証明ではない」と定めている値なので、`稼働中` にも `待機` にも倒すと実体と食い違い、片付ける action か枠を渡す action のどちらかが誤って当たる。

「休止要求中」を `休止` に丸めない: 記録を書いた直後はまだ書き続けているので、丸めるとまだ書いている後発が非保持になり、交差する別の課題へ枠が渡って 2 つが実際に同時に書く。

印だけがあるときを `Conflict` にする: 書き手が記録を残す前に落ちた可能性がある。

`prunable` を畳まない: `無し` に畳むと掃除が漏れ、`あり` に畳むと存在しないものを消しにいく。

branch を `capacity` に入れない: 未マージ branch は意図的に残すので、入れると `取り下げ` の片付けが毎 tick 再発火して固定点に収束しない。

差し戻しを `Conflict` より先に見る: `進行中 × 未着手`（claim だけ残った）は字面では「期待より先」に見えるので、順序を決めないと `Conflict` に吸い込まれて差し戻しに到達しない。claim 直後に Status 更新が失敗した `準備中 × 計画済み` も同様。

`退避先` の置き手を数え上げない: 人も解決工程も conductor 自身も置くので、増えるたびに古くなる。人へ報告するために原因が要るときだけ差し戻しの経緯コメントで引く —— 記録で引けるのは retry budget 切れだけで、成果ゼロの周はそこに現れない。

差し戻し表を排他ラダーにする: 行は 2 つの軸で当たる —— `退避先` へ落とす行は `count`、Status を戻す行は状態。直交しているので同じ観測に同時に成立し（claim の残骸が budget も使い切っている形）、行内の優先が無いと戻し先が一意に決まらない。順序で解くのは `progress` / `runtime` と同じ device で、各行に「他の行に当たらない」を書き足すより短く、行が増えたときも追随する。

上限に達した行を上に置く: 下に置くと、差し戻しそのものが失敗し続ける課題で budget が消化されない —— 上の行が毎 tick 当たって失敗し、`退避先` へ落ちる経路に永久に到達しない。この順で払う代償は 1 周ぶん。

`ledger` の範囲を行ごとに持つ: `退避先` へ落とす行は `未計画` でも起こりうるので、全行共通の 1 文へ外出しするとその行の上限が空洞になる。一方で範囲を書かない行は、判定に台帳が入らないぶん字面が広い。**範囲は行ごとの述語にしか置けない。**

範囲の両端を決めているもの: 上端は `完了` の手前で切る —— 終端に達した課題は「片付ける」が上位で拾い、そこが失敗の記録も周回の記録も消す。`退避先` も入らない（人が見るまで拾わせない状態で、差し戻しがそもそも当たらない）。下端は行ごとに違い、`退避先` へ落とす行だけが `未計画` を含む —— 計画工程が Status を残さず閉じる往復と、計画の周の指紋がそこで回るため。

「claim だけ残っていた」が `計画済み` も見る: この行自身が部分的に失敗するから。Status を戻せても claim の記録を消せなかった周は `計画済み` × 記録あり で残るので、`進行中` 限定だと次の tick で当たらず、消えない記録がその課題を選出から永久に外す。**他のどの action にも当たらない** —— 台帳のずれは無く、選出は記録があるので拾わず、在庫の陳腐化は claim が構造的に止まっているので評価しない。

`ledger` が期待より先を Conflict にする: 前進で直せないので、落とすとどの action にも当たらない課題が `idle` として静かに滞留する。**正規化では立てない** —— ラダーは差し戻し（2 段目）を先に評価するので、そこで立てると `進行中 × 未着手` の差し戻しが全部 Conflict に食われる。

## 計画セッションの rename

`idle` で閉じない: 実行器の `idle` は「入力待ち **かつ** そのタブが focused UI で seen」で、`done`（未 seen のまま background 作業が終わった）とは別物。`idle` には人が入力を書いている最中が含まれる。送信は取り返しがつくが、pane を閉じたら戻せない。

rename しても再計画を塞ぐ: 塞がないと、次の tick で新しい `refine-<番号>` が起き、人が送信すると両方が本文・`ready`・Status を書いて digest が食い違う。**守ろうとした未送信入力が、守った結果として二重計画を生む。**

時間切れで解かない: 経過時間で未送信入力の価値が変わるわけではない。つまり `retired-refine-<番号>` は、それ自体が「人が動かすまでどの工程も起きない」滞留で、`退避先` と同じクラスに属する。

在庫の陳腐化と噛み合うと表に出る: 差し戻しは「次の `refine` が計画を作り直す」ことを期待した遷移だが、`retired-` が残っている番号ではその `refine` が永久に起きない —— 受け皿の最上段に居ながら選出の対象から外れ続ける。差し戻しの側では塞がない（Status を戻すこと自体は正しい）ので、**出口はボードしかない**。人は上から読むので、原因が下の行に沈むと計画枠の数字しか見えない。

`resolve` に rename を適用しない: worktree を持つので残すと容量が漏れる（着地まで進める工程なので、そもそも「入力待ちで放置」が正常状態ではない）。**計画工程だけの非対称であることを明示しておかないと、対称にすべきだと読まれて後から広げられる。**

## 往復を失敗として数える

`ledger` が `未計画` のまま片付けるとき: `refine` が Status も人待ちの記録も残さずに終わると `ledger` は `未計画` のままなので「計画を起こす」がまた当たる —— 閉じる → 起こす → 閉じる、を止めるものが無い。**往復はどちらの action も成功する**ので、失敗として数える場所がここ以外に無い。

「伝える」2 つ: 受け手が計画コメントを更新しない限り述語は毎 tick 真のままで、伝えるのは成功するので `count` が増えない。これらは台帳前進より上位なので、その課題は台帳前進も枠渡しも claim も永久に受け取れず、`稼働中` として表示され続けるだけで停止が観測できない。

結果を観測してから tick を終える: 確認しないと、まだ `待機` に見える課題へ同じ枠をもう一度渡せる。

上限に達したら順位を譲る: 「計画セッションを片付ける」は「差し戻す」より上位なので、上限に達しても選ばれ続けると差し戻しに永久に到達しない —— 入れ物を閉じられない harness では `count` だけが伸び、`退避先` にも状況ボードにも出ないまま計画枠が 1 つ永久に埋まる。

## 独立した行が要る理由

失効した記録を片付ける: 記録に失効条件が無いので、後発が自力で前へ進んで交差を解いた場合（`提出中` → `着地待ち` で write が空く）、休止の記録だけが残る。`runtime` は `稼働中` のままなので「枠を渡す」は当たらず、「交差を解消する」は交差が無いので当たらない。この行が無いと誰にも当たらないまま滞留する。

解除条件に `runtime` を入れない: `休止` は write の非保持を意味するので、「write を保持していないなら消す」と書くと記録を消した瞬間に保持者へ戻り、「交差を解消する」が再発火する。**`着地待ち` から checks が赤くなって `提出中` へ戻るのは往復ではない**（外部要因で実状態が動いているので、そこで交差が再検出されて新しい記録が書かれるのが正しい）。

意図の確認を促す: 受け手の条件に意図の確認を足したので、記録が無い課題はどれだけ緑でも受け手にならない。それ自体は fail-closed で正しいが、**記録が無いこと自体はどの action の発火条件にもならない** —— `Conflict` は `pending` のときしか当たらず、「失効した記録を片付ける」の 3 つはどれも記録があることを前提にし、「解決を起こし直す」はセッションがあると当たらない。この行が無いと、緑の PR が `着地待ち` × `待機` のまま誰にも当たらず、merge の枠は誰にも渡らない（保持者が居ないので、交差しない他の課題まで含めて着地が止まる）。規約を足した直後は全件がこの形になるので、移行の経路もこの行が兼ねる。

`枠を渡す` を claim へ譲る行: 1 tick 1 action の下では同じ write が毎 tick の唯一の actionになり、下位の claim が起きない。足りない実体は `report` であって merge ではない。`holdsWrite` の `提出中` を外すと、まだ書く課題から write が離れる。`report` を促す行は足さない。運ぶ受け口は `枠を渡す` の `missing`。譲位した周は回していないので上限の対象にしない。`休止` に掛けると交差の再開が後ろへ送られる。

計画の人待ちが落ちたときに「計画を起こし直す」が拾う: `refine` は成果物を進めないので `progress` は `未着手` のままで、「計画を起こす」の上限に阻まれると記録を `cleared` にする主体が二度と立ち上がらない。

## 成果ゼロの周を数える形

回した回数では数え**ない**: 数えると、1 周あたり commit 1 本で進む正当な長期実装が上限ぶんの周で `退避先` へ落ちる。往復そのものは異常ではなく設計どおりの駆動サイクル。

`着地待ち` と、実行中の checks がある `提出中` を外す: そこで成果物が動かないのが正常だから。数えると待っているだけの課題が落ち、integration では唯一の枠ごと巻き込む。**`提出中` を無条件では外さない** —— checks が 1 つも動いていない `提出中` は待ちではなく詰まりで、外すとそこで実行器を回し続けても上限に載らない。

除外は、数える側に在る段にしか掛けられない: `提出中` は write を渡す周と起こす周の両方に、`着地待ち` は起こす周だけに入る（write を渡す周が `着地待ち` に当たらないのは、そこで渡すのが integration だから）。条件表から段を落とすと除外条項は空回りし、外す条件を書いたのにその段が丸ごと落ちる。

write を渡す周の対象は、「枠を渡す」が write を渡す範囲であって、**write の保持者集合ではない**: `準備中` は保持しないが周には入る（根拠は `scenarios.md` の行 10q）。資源の側の集合に合わせて条件表から外すと、prepare の空回りだけが上限無しで回る。

起こす周を数える: 数えないと、セッションが死んでは起こされるだけの往復に上限が無くなる。起こし直しの成功は失敗の記録を 0 に戻すので、そちらでは止まらない。計画側も同じで、conductor が閉じていない形で `refine` が消え続ける周は失敗の記録が伸びない。**閉じる側では数えない** —— 閉じると起こすの両方で数えると、1 周が 2 回積まれる。

`人待ち` と `休止` を除外しない: 聞く・答えるは人待ちの記録として指紋に入っているので、人待ちへ入った周も明けた周も指紋が動いて `count` は自動で 0 に戻る。除外を重ねると、人待ちのまま毎 tick 起こし直しを繰り返す課題だけ上限が空洞になる。

加算の判定を回した後の `runtime` で引かない: 起こすことに成功していれば必ず `稼働中` なので、一度も加算されない。

照合を回す action の直前に閉じない: 「差し戻す」は実行器を回さないので、そこで閉じると `progress` が進んだ課題を照合前に落とす。逆に加算を回す前に出すと、回さずに落ちた tick が数えられて冪等でなくなる。

指紋に `runtime` とセッションの状態を入れない: 回した直後に必ず変わるので、入れると常に成果ありになる。**commit 数でも引かない** —— amend / squash / rebase で減るので、書き直した周が成果ゼロに見える。
