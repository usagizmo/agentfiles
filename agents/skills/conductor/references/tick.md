# 正規化と action の論証

**読むのは、本文の正規化のラダーと action の優先順を書き換えるときだけ**。tick では読まない（毎 tick 要る述語は本文が SSOT。ここは同じ条件を言い換えず、**なぜその順序・その条件なのか**だけを持つ）。

## 正規化のラダー

**group を 1 レコードに畳まない理由**: 一部だけ計画済みの group は `ledger` が 1 つに決まらず、未計画側の refine が起きないか計画済み側を早期 claim するかになる。

**終端（`着地済み` / `取り下げ`）を最上段に置く理由**: `ship` は remote branch を消さないので、merge 直後は「branch あり + commit あり」も同時に真になる。終端を先に確定しないと、正常な着地のたびに `Conflict` で止まり、片付けに到達しない。

**worktree の「有無」を見ない理由**: 有無を入れると、着地待ちの worktree が消えた瞬間に `未着手` へ退行し、着地済みの課題を未着手として選び直す。一方 dirty は「まだ commit していない実装がある」ことの証跡で、worktree ごと消えたならその実装は失われているので、`準備済み` へ戻るのが正しい。

**checks の緑を自前で畳まない理由**: `statusCheckRollup` には結果の入る欄が違う 2 種類が混ざり（`CheckRun` は `conclusion`、外部サービスの `StatusContext` は `state` で `conclusion` は常に `null`）、`conclusion` だけを見ると外部サービスの成功が「実行中」に化ける。実測で、緑の PR を `pending 1` と読み続けて integration の受け渡しが遅れた。

**`mergeStateStatus` で代用しない理由**: `CLEAN` は checks 以外（衝突・必須レビュー・default への追随）まで含むので、default が動くたびに `BEHIND` へ落ちて `着地待ち` から外れる —— 追随は渡された後にやる契約なので、渡す前に要求すると誰も受け手になれない。

**着地を PR の `merged` で見る理由**: `default..HEAD == 0` を主条件にすると、squash merge で着地済みが未着地に見え、逆に default から切っただけの空 branch が着地済みに見える。

**`計画中` を `progress` に置かない理由**: 計画セッションの有無は実行器の話で、成果物は進んでいない。セッションが消えただけで成果物の進捗が退行する形にしない。

**`人待ち` を最上段に置き、セッションの有無を条件に入れない理由**: 入れると「答えを解釈して `cleared` にした直後の idle」がどの値にも当たらず、人待ちからの復帰が `Conflict` で止まる。

**`waiting` を無条件に `人待ち` へ写さない理由**: 実行資源待ちを人待ちとして書いた記録があり、最上段に写すとその課題はどの遷移にも当たらないまま滞留する。

**「分類できない」を丸めない理由**: 実行器の側が「agent は居るが分類できない。完了の証明ではない」と定めている値なので、`稼働中` にも `待機` にも倒すと実体と食い違い、片付ける action か枠を渡す action のどちらかが誤って当たる。

**「休止要求中」を `休止` に丸めない理由**: 記録を書いた直後はまだ書き続けているので、丸めるとまだ書いている後発が非保持になり、交差する別の課題へ枠が渡って 2 つが実際に同時に書く。

**印だけがあるときを `Conflict` にする理由**: 書き手が記録を残す前に落ちた可能性がある。

**`prunable` を畳まない理由**: `無し` に畳むと掃除が漏れ、`あり` に畳むと存在しないものを消しにいく。

**branch を `capacity` に入れない理由**: 未マージ branch は意図的に残すので、入れると `取り下げ` の片付けが毎 tick 再発火して固定点に収束しない。

**差し戻しを `Conflict` より先に見る理由**: `進行中 × 未着手`（claim だけ残った）は字面では「期待より先」に見えるので、順序を決めないと `Conflict` に吸い込まれて差し戻しに到達しない。claim 直後に Status 更新が失敗した `準備中 × 計画済み` も同様。

**`退避先` の置き手を数え上げない理由**: 人も解決工程も conductor 自身も置くので、増えるたびに古くなる。**分岐には使わない**。人へ報告するために原因が要るときだけ差し戻しの経緯コメントで引く —— 記録で引けるのは retry budget 切れ（失敗の記録の `lastAction`）だけで、成果ゼロの周はそこに現れない。

## 計画セッションの rename

**`idle` で閉じない理由**: 実行器の `idle` は「入力待ち **かつ** そのタブが focused UI で seen」で、`done`（未 seen のまま background 作業が終わった）とは別物。`idle` には人が入力を書いている最中が含まれる —— 実測 2 件で、書きかけのプロンプトと、割り込み直後の書きかけの返信が載っていた。送信は取り返しがつくが、pane を閉じたら戻せない。

**rename しても再計画を塞ぐ理由**: 塞がないと、次の tick で新しい `refine-<番号>` が起き、人が送信すると両方が本文・`ready`・Status を書いて digest が食い違う。**守ろうとした未送信入力が、守った結果として二重計画を生む。**

**時間切れで解かない理由**: 経過時間で未送信入力の価値が変わるわけではない。つまり `retired-refine-<番号>` は、それ自体が「人が動かすまでどの工程も起きない」滞留で、`退避先` と同じクラスに属する。

**在庫の陳腐化と噛み合うと表に出る**: 差し戻しは「次の `refine` が計画を作り直す」ことを期待した遷移だが、`retired-` が残っている番号ではその `refine` が永久に起きない —— `Backlog` の最上段に居ながら選出の対象から外れ続ける（実測 1 件）。差し戻しの側では塞がない（Status を戻すこと自体は正しく、戻さなければ古い計画が残る）ので、**出口はボードしかない**。「表に載らない滞留」に置くだけでは足りない —— 人は上から読むので、原因が下の行に沈むと計画枠の数字しか見えない。

**`resolve` に rename を適用しない理由**: worktree を持つので残すと容量が漏れる（着地まで進める工程なので、そもそも「入力待ちで放置」が正常状態ではない）。**計画工程だけの非対称であることを明示しておかないと、対称にすべきだと読まれて後から広げられる。**

## 往復を失敗として数える

**`ledger` が `未計画` のまま片付けるとき**: `refine` が Status も人待ちの記録も残さずに終わると `ledger` は `未計画` のままなので「計画を起こす」がまた当たる —— 閉じる → 起こす → 閉じる、を止めるものが無い。**往復はどちらの action も成功する**ので、失敗として数える場所がここ以外に無い。

**「伝える」2 つ**: 受け手が計画コメントを更新しない限り述語は毎 tick 真のままで、**伝えるのは成功するので `count` が増えない**。5・6 は 7 以降より上位なので、その課題は台帳前進も枠渡しも claim も永久に受け取れず、`稼働中` として表示され続けるだけで停止が観測できない。

**結果を観測してから tick を終える理由**: 確認しないと、まだ `待機` に見える課題へ同じ枠をもう一度渡せる。

**上限に達したら順位を譲る理由**: 「計画セッションを片付ける」は「差し戻す」より上位なので、上限に達しても選ばれ続けると差し戻しに永久に到達しない —— 入れ物を閉じられない harness では `count` だけが伸び、`退避先` にも状況ボードにも出ないまま**計画枠が 1 つ永久に埋まる**。

## 独立した行が要る理由

**失効した記録を片付ける**: 記録に失効条件が無いので、後発が自力で前へ進んで交差を解いた場合（`提出中` → `着地待ち` で write が空く）、休止の記録だけが残る。そこでセッションが動いていると「休止を促し直す」が当たり、**緑になって着地できる課題にもう一度「止まれ」と送る**（そちらは失敗の記録を伸ばすので、繰り返せば `退避先` へ落ちる）。「枠を渡す」は交差が残っていれば当たらず、「交差を解消する」は記録があるので当たらないので、この行が無いと誰にも当たらないまま滞留する。実測で、着地目前の課題に対してこれが起き、規約を曲げて見送ることでしか避けられなかった。

**解除条件に `runtime` を入れない理由**: `休止` は write の非保持を意味するので、「write を保持していないなら消す」と書くと記録を消した瞬間に保持者へ戻り、「交差を解消する」が再発火する ——`protocols.md` が禁じている「交差する保持者が 1 以下で解除」と同型の往復になる。**`着地待ち` から checks が赤くなって `提出中` へ戻るのは往復ではない**（外部要因で実状態が動いているので、そこで交差が再検出されて新しい記録が書かれるのが正しい）。

**意図の確認を促す**: 受け手の条件に「意図の確認が `confirmed` か `not-required`」を足したので、記録が無い課題はどれだけ緑でも受け手にならない。それ自体は fail-closed で正しいが、**記録が無いこと自体はどの action の発火条件にもならない** —— `Conflict` は `pending` のときしか当たらず、「失効した記録を片付ける」の 3 つはどれも「記録がある」ことを前提にし、「解決を起こし直す」はセッションがあると当たらない。この行が無いと、緑の PR が`着地待ち` × `待機` のまま誰にも当たらず、merge の枠は誰にも渡らない（保持者が居ないので、交差しない他の課題まで含めて着地が止まる）。規約を足した直後は全件がこの形になるので、移行の経路もこの行が兼ねる。

**計画の人待ちが落ちたときに「計画を起こし直す」が拾う理由**: `refine` は成果物を進めないので `progress` は `未着手` のままで、「計画を起こす」の上限に阻まれると**記録を `cleared` にする主体が二度と立ち上がらない**。

## 成果ゼロの周を数える形

**回した回数では数えない。** 数えると、1 周あたり commit 1 本で進む正当な長期実装が上限ぶんの周で `退避先` へ落ちる。往復そのものは異常ではなく設計どおりの駆動サイクル。

**`着地待ち` と、実行中の checks がある `提出中` を外すのは、そこで成果物が動かないのが正常だから。** 数えると待っているだけの課題が落ち、integration では唯一の枠ごと巻き込む。

- **`提出中` を無条件で外さない** —— checks が 1 つも動いていない `提出中` は待ちではなく詰まり。外すと、そこで実行器を回し続けても上限に載らない

**起こす周を数えないと、セッションが死んでは起こされるだけの往復に上限が無くなる。** 起こし直しの成功は失敗の記録を 0 に戻すので、そちらでは止まらない。

- 計画側も同じで、`refine` が毎回尽きるだけなら閉じる ⇄ 起こすが永久に回る
- **閉じる側では数えない** —— 閉じると起こすの両方で数えると、1 周が 2 回積まれる

**`人待ち` と `休止` を除外しない。** 聞く・答えるは人待ちの記録として指紋に入っているので、人待ちへ入った周も明けた周も指紋が動いて `count` は自動で 0 に戻る。除外を重ねると、人待ちのまま毎 tick 入れ替えを繰り返す課題だけ上限が空洞になる。

**加算の判定を回した後の `runtime` で引かない。** 起こすことに成功していれば必ず `稼働中` なので、一度も加算されない。

**照合を回す action の直前に閉じない。**「差し戻す」は実行器を回さないので、そこで閉じると `progress` が進んだ課題を照合前に落とす。逆に加算を回す前に出すと、回さずに落ちた tick が数えられて冪等でなくなる。

**指紋に `runtime` とセッションの状態を入れない。** 回した直後に必ず変わるので、入れると常に成果ありになる。**commit 数でも引かない** —— amend / squash / rebase で減るので、書き直した周が成果ゼロに見える。
