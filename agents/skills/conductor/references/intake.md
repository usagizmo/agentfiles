# 人から渡されたものの扱い

読むのは、人が tick の外から何かを渡してきたときと、自分の規約の穴を起票すると決めたとき。**受け取るかどうかの判定と、action に数えるかどうかは本文が SSOT**。ここは振り方と書き方だけ。

## 断る軸

**「観測に混ぜれば済むか」を判定に足さない** —— 済まないが context も増えないもの（人が渡した回答の転記、指示された Issue の作成、宣言行の記入）を、事実に反して断ることになる。判定そのものは本文が SSOT。

## 振る

**pane を割り、材料を渡して起こす。完了を待たない**。入れ物と命名は `harness.md`。振ったことは応答に出す。

- **材料は「自分の tick で既に観測したもの」だけを渡す**。渡すために調べ直さ**ない**。手元に無いものは事実ではなく在り処を渡す（Issue 番号・file path・コマンド）
- **確認済みの事実は必ず渡す**。「調べた結果 0 件だった」も事実
- **判断が済んでいるなら、済んでいると書く**。残っているならどれが残っているかを書く
- **渡した先の出力を自分で読み込まない**。必要なら人が戻してくる（`harness.md` の転記）
- **振り先を稼働中の課題にしない**。人が「この worktree で」と指示したときは、人が渡す

## Issue の作成と本文

- **書いてよいのは関係の行だけ** —— 宣言（`Depends on #N` / `Same branch as #N`）と `Refs #N`。目的・受入条件・非目標・リスク・設計判断には触ら**ない**
- **書く前に digest を持つ記録の有無を確かめる**。触ってよいのは記録がまだ無いもの（`未計画` で refine 前）か、陳腐化させると分かったうえで人が指示したときだけ。判断は `same-branch.md`
- **宣言は本文の先頭区画へ、行頭に置く**（形と置き場所は `same-branch.md`）

### 規約の穴を起票するとき

自分が読んでいる skill の記述の誤り・欠落・矛盾は、**ここでしか外部化できない**。製品判断ではないので、起票禁止の射程には入らない。

発火条件は `src/decide.ts` の `LADDER`。書くときの歯止めは 2 つ。

- **書くのは観測した事実だけ** —— 何を観測し、どの記述とどう食い違ったか。直し方・受入条件・非目標・優先度は書かない（計画の領分）
- **永続化と優先順位は別の責務**。最上段へ置いても、依存や入場を止める宣言で回ってこないことはある。それでよい

起票は `issue` を経由する。origin の値集合と対象行の形式は起票先 repo の project 差分が持つ。intake へ写さない。対象 path は事実として渡す。

### 起票したら最上段へ置く

**規約の穴は文書の課題なので、順序は規約が決めている**（`~/.agents/AGENTS.md`「作業単位」）。起票した工程がそのまま受け皿の最上段へ動かす。**人を待たない**（製品判断ではない）。

手段は GraphQL の `updateProjectV2ItemPosition`。位置指定が無いのは `gh project` の CLI だけ。**「できない」を理由にしない**。

**それ以外の並べ替えは、人が順序を指定したときだけ実行する**。断りを返さない（範囲は本文「選出」）。
