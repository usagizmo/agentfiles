# 課題の計画

**「何を作るか」を決めて Issue に固定する工程。**「どう作るか」（触る範囲・資源キー）は
着手時に決まるので、ここでは扱わない。

**実装しない。**コードを書かず、branch も worktree も作らない。

## 手順

1. Issue と関連コードを読む（**人待ちの記録が `waiting` なら前のセッションが死んでいる**。
   質問を出し直すか、答えが返っていれば解釈して `cleared` にしてから進む）
2. `consult` で方針を確定する（複数案があるとき。自明なら省く）
3. Issue 契約の項目を埋める
4. **製品判断が要る項目が埋まらなければ、そこで止めてユーザーに聞く**（下記）。
   止まるときは**人待ちの記録を `waiting` にする**（形式と消し方は `references/wait-record.md`）
5. 全部埋まれば本文を更新して Status を計画済みへ進める。埋まらなければ**進めずに不足を報告し、
   人待ちの記録を `waiting` にする**（記録が無いと、外からは「終わったのに Status が動いていない」
   と読めて起こし直される）

**「計画済み」に当たる Status 名は project 差分の対応表から引く。**推測で動かさない
（読む側が別の名前を見ていると、その Issue は誰にも選出されずに沈黙して止まる）。
対応表が無ければ Status を動かさず、本文の更新と報告だけを行う。

## Issue 契約

Status を計画済みへ進める = 「この 6 つが本文に揃っている」という宣言。1 つでも欠けたら移さない。

| 項目 | 埋める人 |
| --- | --- |
| 目的と期待する結果 | エージェント（ユーザーの意図を確認して） |
| 受入条件（真偽が言える文） | エージェント |
| 非目標 | エージェント |
| **確定済みの製品判断**（「A を採用、B はしない」） | **ユーザー** |
| リスク（配信・migration・security・外部サービス） | エージェント |
| 依存（無ければ「なし」） | エージェント |

**未決の判断を「エージェントが決めて」埋めない。**埋まっていない = まだ計画済みではない、が正しい。
ここで無理に埋めても、着手後に「本文に無い判断が必要」で止まるだけで、待ちが後ろへずれる。

**確定済みの製品判断には、その判断を出した Artifact の URL を併記する。**判断だけが残って根拠が
辿れない状態を作らない。**人待ちの記録に書くだけでは足りない**（`cleared` で書き換わり、
コメントは埋もれる）。読んで前提にした過去の Artifact があれば、同じ場所に並べる。

**実行メタデータは本文に書かない**（base・worktree path・セッション ID・候補 SHA）。時間で
変わるので、Project field・branch・PR に置く。本文に書くと着手時には必ず古い。

## 1 本で直す課題を宣言する

読んだ結果「これは別の課題と同じブランチで直る」と分かったら、`Same branch as #N` を書く。
条件・記法・隣接する記法との違いは `references/same-branch.md`。

**計画の時点で書ききる。**着手が始まってからでは間に合わない。

## 製品判断をユーザーに聞くとき

聞き方は `~/.agents/AGENTS.md`。

特に落としやすいのは**非目標**。「何をやらないか」が書かれていないと、着手後にスコープが
際限なく広がる。やらないと決めたことは理由ごと残す。

## 一括で流すとき

複数の Issue をまとめて refine するよう頼まれたら、1 件ずつ完了させる。
**未決の判断が出たものは飛ばして次へ進み、最後にまとめて質問する。**
1 件ごとに止まるとユーザーの待ち時間が増える。
