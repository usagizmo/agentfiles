# 課題の計画

**実装しない**。コードを書かず、branch も worktree も作らない。

1. Issue と関連コードを読む
2. `consult` で方針を確定する。規模（`~/.agents/AGENTS.md`）が中規模以上なら深い・事前、それ以外は軽量。製品判断が要る項目は `~/.agents/AGENTS.md` の形で聞く。聞く前に、埋まった項目を本文へ書ききる
3. Issue 本文へ書く: 目的 / 受入条件（検証手段つき）/ 採用する方式と比較した代替 / 設計記述（中規模以上。定義は `consult`）/ 変更面（責務・module。path ではない）/ 依存する Issue / **`実物確認: 要` または `実物確認: 不要`**。人に見せる面（UI・公開 API・設計骨格）を変える見込みなら **要**。機械的・内部のみなら **不要**
4. 完了条件: 本文だけで実装役が計画を足さずに着手できる。設計記述の前提が検証済み。未決の判断・欠けた項目・未検証の前提があれば 2 へ戻る
5. Status を計画済みへ進める。依存する Issue の未着地は計画済みの妨げにならない（着手可否は `resolve` が依存関係で判定する）。Status 名と操作は project 差分が持つ。無ければ Status を動かさず、本文の更新と報告だけをする

本文に 3 の項目が揃っているなら、2 はそのまま行い、3 は方針か項目が変わったときだけ書き直す。

複数の Issue を頼まれたら 1 件ずつ完了させ、未決の判断は最後にまとめて聞く。
