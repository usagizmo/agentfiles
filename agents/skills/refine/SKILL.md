# 課題の計画

**「何を作るか」を決めて Issue に固定する工程。**「どう作るか」（触る範囲・資源キー）は着手時に決まるので、ここでは扱わない。

**実装しない**。コードを書かず、branch も worktree も作らない。

## 手順

1. **起動したら `references/wait-record.md` の「起こし直されたら」を実行する**。そのうえで Issue と関連コードを読む
2. `consult` で方針を確定する（複数案があるとき。自明なら省く）
3. Issue 契約の項目を埋める
4. **製品判断が要る項目が埋まらなければ、埋まった項目を先に本文へ書ききってから止めて聞く**（聞き方は `references/wait-record.md`。記録を先に書き、それを指す短い問いだけを出す。記録を書けなければ聞かずに報告して終える）
5. 全部埋まれば本文を更新し、**在庫の鮮度の記録を書いてから** Status を計画済みへ進める（下記）。埋まらなければ進めずに不足を報告する。これも人の答えを待って終えるので 4 と同じ手順に載る（記録が無いと、外からは「終わったのに Status が動いていない」と読めて起こし直される）
6. **同じ質問の記録が既にあるのに答えが無いまま起こし直されたら、待たずに退避先へ移して終える**（下記）。初回は待つ

**進められるところは、聞く前に進めておく**。答えを待つあいだ本文が空だと、セッションが死んだ時点で埋めた判断が消え、人が答えた後も同じ項目を埋め直すことになる（セッション文脈はキャッシュ、外部化したものが復旧契約）。**それでも Status は動かさない** —— 契約が揃うまでは計画済みではない。

## 計画は譜面にする

**聞くことが無くても必ず作る**。人が「これから何が起きるか」を読む先で、判断を仰ぐためだけのものではない —— 聞くことが無い計画ほど、人は中身を知らないまま着手される。

**新しく作る前に引き当てる**。計画を作り直したときも同じ譜面を書き直す（失効した版を残さない）。引き当てと group の扱いは `references/score.md`。

載せるのは下の Issue 契約の項目を人が読める形にしたもの。**本文の写しにしない**（本文が SSOT で、こちらは読ませる面）。

**聞いて止まるときは、判断待ちの節も載せる**（未決の項目と、何が分かれば決まるか）。止まるほど人はこの譜面しか見ないので、そこが空だと判断材料が短い問いの中にしか無くなる。

## 答えを待ち続けない

**述語は「2 回目かどうか」**。同じ質問の記録（`waiting`）が既にあるのに答えが無いまま起こし直された —— そのときだけ退避先へ移す。**初回は待つ**（`/refine` を直に呼んだ人はその場に居るので普通に解ける）。

**述語には「人の入力が一度も無い」を含める**。人が催促のつもりで `/refine` を叩き直したときは入力そのものなので初回として扱う（狭めないと、その場に居る人に質問を出し直さずに退避先へ落とす）。

**これはセッションが落ちたときの復帰経路であって、枠の回収手段ではない。枠が足りないことを理由に自分から退避先へ移らない** —— 複数件の状態で決まる制約は、キューを回す側が持つ。

「何も進められない」を条件にしない —— 埋まった項目を書ききった後は常に真になり、待つ側と退避する側が同じ観測で当たって一意に決まらない。

1. 埋まった項目が本文に書ききられていること（手順 4 で済んでいる。落ちていたらここで埋める）
2. Status を**退避先**へ移す（拾わせない置き場。名前は project 差分の対応表）
3. 人待ちの記録を `cleared` にしてセッションを終える

**待ち続けると計画枠を占有し続ける**。計画枠は実行器が生きている限り返らないので、答えの来ない計画が枠の数だけ溜まると計画工程が全停止する。退避先に置けば枠が空き、人が見て未計画へ戻した時点で自動的に拾い直される。

**「計画済み」に当たる Status 名は project 差分の対応表から引く**。推測で動かさない（読む側が別の名前を見ていると、その Issue は誰にも選出されずに沈黙して止まる）。対応表が無ければ Status を動かさず、本文の更新と報告だけをする。

## Issue 契約

**項目・見出しの字面・書き方の SSOT は `references/issue-contract.md`**（キュー管理と共有する契約なので、
ここには写さない —— 写すと片方だけ古くなり、揃っているのに不足と判定される）。

**見出しは完全一致で書く**。充足はその字面で機械的に判定されるので、言い換えると契約が観測できない。

## 在庫の鮮度

**計画済みへ進めるときに、固定 marker `ready` を書く**。計画は着手されるまで在庫として積まれ、その間に default が進む。

形式・発行順・`invalidationScope` の書き方は `references/ready-record.md`。

## 着地面が制御面と違うなら宣言する

**成果物が Issue の repo に生まれない課題は、本文の先頭区画へ行頭 `Lands in <owner>/<repo>` を書く**（1 行 1 件。形と置き場所は `references/same-branch.md`、意味論は `references/landing-surface.md`）。

**Issue 契約の項目には数えない**。既定は制御面 1 面で、宣言が要るのは違う課題だけ —— 項目にすると、既定で足りている在庫が全件差し戻される。

- **claim より前に書ききる**。claim の記録へ固定されるので、着手後に足しても着地面は動かない
- **書く先を全部挙げる**。宣言があるとそれが全体になり、制御面は自動では入らない。制御面にも commit を作るなら、そちらも 1 行で挙げる
- **同居する課題は同じ集合にする**（違えば claim されない）。書く先が違うなら、そもそも同居の条件を満たしていない
- **座標表に無い repo を宣言しない**（project 差分が持つ）。統合先が引けない面は終端に到達できず、枠を返せないまま滞留する

## 1 本で直す課題を宣言する

読んだ結果「これは別の課題と同じブランチで直る」と分かったら、**両方の本文の先頭区画へ、行頭に**
`Same branch as #N` を書く。条件・形と置き場所・隣接する記法との違いは `references/same-branch.md`。

相互記載は相手の本文を書き換えるので、**触ってよいかは相手の本文の所有者で決まる**（表は `references/same-branch.md`「他人の本文を触ってよいか」）。**別の計画セッションが生きている相手には書かない** —— 自分の本文にだけ書けば、片方向でも group として辿られる。

**計画の時点で書ききる**。着手が始まってからでは間に合わない。

## 一括で流すとき

複数の Issue をまとめて refine するよう頼まれたら、1 件ずつ完了させる。**未決の判断が出たものは、その場で記録だけ書いて次へ進み、最後にまとめて聞く**（`references/wait-record.md`）。1 件ごとに止まるとユーザーの待ち時間が増える。**記録を後回しにしない** —— まとめて聞く前に落ちると、記録の無い人待ちが残る。
