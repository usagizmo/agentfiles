# 課題の計画

**「何を作るか」を決めて Issue に固定する工程。**「どう作るか」（触る範囲・資源キー）は
着手時に決まるので、ここでは扱わない。

**実装しない**。コードを書かず、branch も worktree も作らない。

## 手順

1. **起動したら `references/wait-record.md` の「起こし直されたら」を実行する**。そのうえで
   Issue と関連コードを読む
2. `consult` で方針を確定する（複数案があるとき。自明なら省く）
3. Issue 契約の項目を埋める
4. **製品判断が要る項目が埋まらなければ、埋まった項目を先に本文へ書ききってから止めて聞く**
   （聞き方は `references/wait-record.md`。記録を先に書き、それを指す短い問いだけを出す。
   記録を書けなければ聞かずに報告して終える）
5. 全部埋まれば本文を更新し、**在庫の鮮度の記録を書いてから** Status を計画済みへ進める（下記）。
   埋まらなければ**進めずに不足を報告する**。これも人の答えを待って終えるので 4 と同じ手順に載る
   （記録が無いと、外からは「終わったのに Status が動いていない」と読めて起こし直される）
6. **答えが来るまで計画を進められないと分かったら、待たずに退避先へ移して終える**（下記）

**進められるところは、聞く前に進めておく**。答えを待つあいだ本文が空だと、セッションが死んだ時点で
埋めた判断が消え、人が答えた後も同じ項目を埋め直すことになる（**セッション文脈はキャッシュ、
外部化したものが復旧契約**）。**それでも Status は動かさない** —— 契約が揃うまでは計画済みではない。

## 計画は Artifact にする

**聞くことが無くても必ず作る**。人が「これから何が起きるか」を読む先で、判断を仰ぐためだけの
ものではない —— **聞くことが無い計画ほど、人は中身を知らないまま着手される。**
**本文を更新する前に作る**（URL を本文へ入れるため）。条件は `references/artifact.md`。

載せるのは Issue 契約の中身を人が読める形にしたもの —— 目的・受入条件・非目標・主要な設計判断と
理由・スコープ外・リスク・依存。**本文の写しにしない**（本文が SSOT で、こちらは読ませる面）。

## 答えを待ち続けない

**述語は「2 回目かどうか」**。同じ質問の記録（`waiting`）が既にあるのに答えが無いまま起こし直された
—— そのときだけ退避先へ移す。**初回は待つ**（`/refine` を直に呼んだ人はその場に居るので普通に解ける）。

**述語には「人の入力が一度も無い」を含める**。人が催促のつもりで `/refine` を叩き直したときは
**入力そのものなので初回として扱う**（狭めないと、その場に居る人に質問を出し直さずに退避先へ落とす）。

**これはセッションが落ちたときの復帰経路であって、枠の回収手段ではない。枠が足りないことを理由に
自分から退避先へ移らない** —— 複数件の状態で決まる制約は、キューを回す側が持つ。

「何も進められない」を条件にしない —— 埋まった項目を書ききった後は常に真になり、
**待つ側と退避する側が同じ観測で当たって一意に決まらない。**

1. 埋まった項目が本文に書ききられていること（手順 4 で済んでいる。落ちていたらここで埋める）
2. Status を**退避先**へ移す（拾わせない置き場。名前は project 差分の対応表）
3. 人待ちの記録を `cleared` にしてセッションを終える

**待ち続けると計画枠を占有し続ける**。計画枠は実行器が生きている限り返らないので、
**答えの来ない計画が枠の数だけ溜まると計画工程が全停止する**。退避先に置けば枠が空き、
人が見て未計画へ戻した時点で自動的に拾い直される。

**「まだ答えられるかもしれない」で粘らない**。判断材料を出して聞いたのに決まらないものは、
その場に留めても決まらない。

**「計画済み」に当たる Status 名は project 差分の対応表から引く**。推測で動かさない
（読む側が別の名前を見ていると、その Issue は誰にも選出されずに沈黙して止まる）。
対応表が無ければ Status を動かさず、本文の更新と報告だけを行う。

## Issue 契約

Status を計画済みへ進める = 「この 6 つが本文に揃っている」という宣言。1 つでも欠けたら移さない。

| 項目 | 埋める人 |
| --- | --- |
| 目的と期待する結果 | エージェント（ユーザーの意図を確認して） |
| 受入条件（真偽が言える文） | エージェント |
| 非目標 | エージェント |
| **確定済みの製品判断**（「A を採用、B はしない」） | **ユーザー** |
| リスク（配信・migration・security・外部サービス） | エージェント |
| 依存（無ければ「なし」） | エージェント |

**「依存」は宣言と理由を分けて書く**。関係の宣言（`Depends on #N` / `Same branch as #N`）は
**本文の先頭区画へ、行頭に 1 行 1 件**。「依存」の項目に書くのは**理由だけ**で、そこでは
**番号を伴わない語**を使う。同じ場所に両方書くと、理由の散文が宣言として読まれる。
形と置き場所の定義は `references/same-branch.md`。

**未決の判断を「エージェントが決めて」埋めない**。埋まっていない = まだ計画済みではない、が正しい。
ここで無理に埋めても、着手後に「本文に無い判断が必要」で止まるだけで、待ちが後ろへずれる。
ユーザーへの聞き方は `~/.agents/AGENTS.md`。

**受入条件は原則で書く。識別子や箇所の列挙にしない。**「この N 個の名前を直す」と書くと、そのとき
検索で拾えた分だけがチェックリストになり、**同じ原則の対象なのに拾えなかったものが、受入条件にも
再発防止の仕掛けにも現れないまま残る**。主文は「〜という性質のものを残さない」と書き、
列挙はその時点の実測として添えるだけにする。**列挙を直しきったことを完了条件にしない。**

**非目標**が落ちると、着手後にスコープが際限なく広がる。やらないと決めたことは理由ごと残す。
**書かれていない不在は、後続から「判断して残した」ではなく「漏れ」として読まれる。**
**互換の扱いは必ず書く** —— 互換 shim / deprecated alias / feature flag / migration を持つか
持たないかを、理由ごと。既定は「持たない」（`~/.agents/AGENTS.md`「最終形に不要なコードは
初手から書かない」）。書かれていないと、着手側は安全側に倒れて温存コードを足す。

**確定済みの製品判断には、その判断を出した Artifact の URL を併記する**。判断だけが残って根拠が
辿れない状態を作らない。**人待ちの記録に書くだけでは足りない**（`cleared` で書き換わり、
コメントは埋もれる）。読んで前提にした過去の Artifact があれば、同じ場所に並べる。

**実行メタデータは本文に書かない**（base・worktree path・セッション ID・候補 SHA）。時間で
変わるので、Project field・branch・PR に置く。本文に書くと着手時には必ず古い。

## 在庫の鮮度

**計画済みへ進めるときに、固定 marker `ready` を書く**。計画は着手されるまで在庫として積まれ、
その間に default が進む。

形式・発行順・`invalidationScope` の書き方は `references/ready-record.md`。

## 1 本で直す課題を宣言する

読んだ結果「これは別の課題と同じブランチで直る」と分かったら、**両方の本文の先頭区画へ、行頭に**
`Same branch as #N` を書く。条件・形と置き場所・隣接する記法との違いは `references/same-branch.md`。

相互記載は相手の本文を書き換えるので、**触ってよいかは相手の本文の所有者で決まる**
（表は `references/same-branch.md`「他人の本文を触ってよいか」）。**別の計画セッションが
生きている相手には書かない** —— 自分の本文にだけ書けば、片方向でも group として辿られる。

**計画の時点で書ききる**。着手が始まってからでは間に合わない。

## 一括で流すとき

複数の Issue をまとめて refine するよう頼まれたら、1 件ずつ完了させる。
**未決の判断が出たものは、その場で記録だけ書いて次へ進み、最後にまとめて聞く**
（`references/wait-record.md`）。1 件ごとに止まるとユーザーの待ち時間が増える。
**記録を後回しにしない** —— まとめて聞く前に落ちると、記録の無い人待ちが残る。
