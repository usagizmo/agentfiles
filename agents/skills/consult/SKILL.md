# 設計判断の突き合わせ

**判断主体は実行中のエージェント**。アドバイザー（別モデル）は検証者であって命令ではない。判定基準と規模の定義は `~/.agents/AGENTS.md`。技術的収束はアドバイザーへ、製品判断はユーザーへ。

## モード

| モード     | いつ                           | 出すもの                                               | 終わり方                                                                                                                                                |
| ---------- | ------------------------------ | ------------------------------------------------------ | ------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 軽量       | 修正方針・短い技術的疑問       | 問い / 案 / 触るパス / 懸念（3〜6 行）                 | 統合して 5〜10 行で提示                                                                                                                                 |
| 深い・事前 | 中規模以上の着手前             | 設計記述 / ゴール / 変えるファイル / スコープ外 / 懸念 | 呼ぶ側が固定済みと示していない製品判断は **ユーザーの GO** まで実装しない。固定済みの範囲では技術レビューとして完了してよい（第二の製品 GO は要らない） |
| ループ     | 中規模以上の diff を書き終えた | 設計記述 / 原因表（下記）/ 前巡の採否                  | 同じ agent と双方「指摘なし」まで往復する。固定巡数で終えない。GO は要らない                                                                            |

## 設計記述

深い・事前とループが使う。親が書き、アドバイザーは要件から照合して訂正する。

- data model と責務・所有者・SSOT
- 書き込みから読み取りまでのデータフローと、派生値の更新・無効化
- 不変条件と、それを固定する型・API・検証
- 既存形との差・維持する契約・未検証の前提

既存形を流用するときも、この照合で妥当性を示す。成立が不確かな前提は関連コードか最小の検証で確かめる。未検証の前提を残したまま実装へ進めない。基準を巡の途中で変えるときは新しい根拠を示す。

## 手順

1. 自分の判断を書く（モードの「出すもの」）。ループなら先に gate（lint / test）を通す
2. プロンプトを `mktemp` のファイルへ書く（下記。書き方は `references/advisors.md`）
3. `CONSULT_BACKEND` を明示して `<skills root>/consult/scripts/consult-backend.sh start <prompt-file>` → `collect <run-dir>`（起動表・backend 切替は `references/advisors.md`）
4. 統合する。論点ごとに 一致 / 取り込み / 不採用（理由）/ ユーザー判断が要る点
5. ループなら往復する（下記）。軽量・事前はここで終える
6. `close <run-dir>`

事前の GO ゲートに載せるのは 仕様 / 設計記述 / 変更対象 / スコープ外 / 検証 / アドバイザーとの一致・取り込み・不採用。Plan Mode がある harness はそれを使う。

指摘を実測で不採用にするときは、測った対象（ディレクトリ・生成物・時点）が指摘の対象と一致することを確かめる。ずれているなら測り直す。

## ループ

1. 指摘を原因単位にまとめ、原因表を更新する。原因は「破られた不変条件 + 原因となる所有・導出・更新経路」で書く。各原因に 影響範囲 / 修正 / 検証 / 状態（未対応・修正済み・再発）を持つ。分類はアドバイザーに検証させる
2. 修正済みとした原因が再び現れた、または設計記述の前提が成立しないと分かったら、個別修正を止めて構造見直しへ戻る: 設計記述を改訂し、同じ agent と照合してから直す。巡の連続は問わない。初回でも前提の破綻が分かれば戻る
3. 採用した原因を直す。承認済みの製品契約内なら構造見直しも自律で決めきる。製品判断が変わるときだけユーザーに聞く
4. gate（lint / test）を通し、原因表・採否と理由・問い・修正の要約と gate の結果 1 行を書き、`ask <run-dir> <prompt-file>` で同じ agent へ送り、`collect` する。agent は文脈を保っているので diff は取り直させる
5. 1 へ戻る

同じレビューの継続は同じ run の `ask` で行う。生きている agent を巡ごとに `start` し直さない。

終了は、`verify <run-dir>` が `verify: pass`（agent が rc=0 で `判定: 指摘なし`）を返し、かつ自分に未解決の問いが無い巡。判定は `verify` の出力で見る。自分で応答を読んで「指摘なし」と判断**しない**。**採用 0 件で指摘が残る巡が 2 連続したらユーザーへ**（新しい根拠も修正も出ていない）。固定ラウンド数では終わらない。構造見直しとユーザーへの判断依頼は保留であって終了ではない。

**終了ゲート（厳守）**: 「指摘なし」以外・必須が残る・「十分」「後で」「N 巡で打ち切り」なら、`close` / `finish` 続行 / Draft·Ready PR / レビュー合格の報告を**してはならない**。直して `ask` するか、上の 2 連続エスカレートだけ。`close` 後に直したら新しい `start` からループを始めるまで未終了。復旧のための `close`（`references/advisors.md` の失敗時）は終了ではない。レビュー合格を報告するときは `verify` の出力（run dir・巡・判定）をそのまま貼る。

`start` が失敗して run dir が無いとき、または agent が終端したときの復旧は `references/advisors.md` の失敗時。復旧できる agent が尽きたら、自分の判断だけで 1 巡して終え、**未レビューとして報告する**（レビュー合格ではない）。

## プロンプト

```markdown
あなたは設計判断のレビュアーです。コードは変更せず分析と提案だけ返してください。

## 必読

- ~/.agents/AGENTS.md（設計原則・ボーイスカウトルール）
- {文書を変えたとき: <skills root>/docs/SKILL.md の品質基準 / 編集した文書 / その規則が関係する文書}

## 背景・要件

{...}

## レビュー対象

{事前: パス + 注目点。全文は貼らない}
{ループ: git status --short / git diff / git diff --cached / untracked の中身。lint / test の gate は呼び出し側が通した（結果を 1 行）。実行は主張の検証に必要なときだけ}

## 設計記述

{深い・事前 / ループ: 設計記述の 4 項目。軽量では省く}

## 私の判断

{軽量・事前: 判断と理由。ループ: 原因表と前巡の採否}

## 観点

- 設計記述が要件に照らして理想形か。既存形の流用・未検証の前提を含む
- 設計原則からの逸脱（ゼロベース一致・根本解決・互換 shim / deprecated / dead code の残存）
- SSOT 複製（test が production 形を手コピー・同一 helper の二重）、shape / 型 / mock / 生成物の drift
- 経緯コメント（「以前は〜だった」・Issue / PR 番号）
- 文書を変えたとき: 参照先の節・ファイルが実在する / 同じ規則・数値が 2 箇所に実体として無く文書間で矛盾しない / 削ると判断ができなくなる記述を落としていない / 複数の文書を順に読んだとき順序・前提・差し戻し先が噛み合う
- バグ・エッジケース・軸の混在・より良い代替・隠れたトレードオフ

## 出力

1. 設計記述の訂正（無ければ省く）
2. 設計記述と対象の構造差を原因単位で、重要度順に: 破られた不変条件 / 原因となる所有・導出・更新経路 / 関連する writer・reader・状態遷移（確認済み範囲と未確認範囲）/ 推奨修正 / 検証。「ファイル:行」の指摘は根拠として原因の下に置く。件数で省略しない
3. 原因表の分類の訂正（ループのみ。無ければ省く）

なければ「指摘なし」のみ。nitpick 不要。
最後の行は `判定: 指摘なし` / `判定: 修正推奨` / `判定: 再考推奨` のどれか 1 つだけ。
```
