# 設計判断の突き合わせ

**判断主体は実行中のエージェント**。アドバイザーは検証者（命令ではない）。判定基準は `~/.agents/AGENTS.md` の設計原則。

## いつ

- **軽量**: 修正方針・短い技術的疑問（「これでいい？」）。自分の案は 3〜6 行でよい。承認ゲートなし
- **深い**: 新機能・大リファクタの設計方針、複数案のトレードオフ、実装後の骨格の問い直し
- 着手見込みが中規模以上なら深い・事前。実装済み diff があるときは深い・事後
- 技術的収束はアドバイザーへ、製品判断はユーザーへ（分担は `~/.agents/AGENTS.md`）

## 手順

### 1. 自分で判断を書く

- **軽量**: 問い / 案 / 触るパス / 懸念（短く）
- **深い・事前**: ゴール / 変えるファイル / 主要判断と理由 / 懸念
- **深い・事後**: ゼロベースで理想形を考え、責務分割・API・データフロー・SSOT・エッジで現状を評価（`git diff` 等で対象を特定し関連コードも読む）

### 2. プロンプトを一時ファイルへ

本文は下記。ファイルへの書き方と起動は `references/advisors.md`。軽量なら観点を絞って短くてよい:

```markdown
あなたは設計判断のレビュアーです。コードは変更せず分析と提案だけ返してください。

## 必読

- ~/.agents/AGENTS.md（設計原則）

## 背景・要件

{...}

## 関連ファイル

{パス + 注目点。全文は貼らない}

## 私の判断

{...}

## 観点

- 設計原則からの逸脱（特にゼロベース一致・根本解決・互換温存の有無）
- 見落としエッジケース・より良い代替・隠れたトレードオフ

（軽量時は「致命的な穴と短い代替」に絞ってよい）
末尾: このまま進めてよい / 修正推奨 / 再考推奨（一言）。
```

### 3. アドバイザーに渡す

同ディレクトリの `references/advisors.md` に従う（アドバイザー起動の SSOT）。

### 4. 統合して提示

手順 3 で回収した出力を読む。出力が無いときは手順 1 の判断を提示する。論点ごとに一致 / 取り込み / 不採用（理由）/ ユーザー判断が要る点を書く。最終判断は実行中のエージェント。軽量は 5〜10 行でよい。複数アドバイザーなら出典タグ（`references/advisors.md` の出典表記）を付す。

アドバイザーの指摘を実測で不採用するとき:

- 測った対象（ディレクトリ・生成物・時点）を書く
- 測った対象が指摘の対象と一致することを確かめる
- ずれているなら**不採用にしない**。指摘の対象を測り直す

「全走査した」と書くときは、走査の範囲（根と件数）を添える。

### 5. 実装プラン確定時のみ承認ゲート

発動するのは、深い・事前で実装プランを確定する場合と、深い・事後で修正プランを出す場合だけ。

手順 4 の統合結果とプランを 1 つの文書にして提示し、**ユーザーの GO** まで実装しない。載せるのは 仕様 / 変更対象 / 主要判断と理由 / スコープ外 / 検証 / アドバイザーとの一致・取り込み・不採用（理由）/ ユーザー判断が要る点。GO が出なければ直して再提示する（骨格から崩れるなら手順 1 に戻る）。Plan Mode がある harness はそれを使う。無ければ構造化 Markdown + 明示 GO。この突き合わせの終了で実装完了としない。

**呼び出し元が譜面を持っているなら、更新は提示の前に行う**。Plan Mode 中は書き込みを禁じる harness があるため、その中では作らない・直さない（GO が出なければ抜けてから更新して再提示する）。
