# ドキュメント

## いつ

**発動条件の SSOT は description。**ここは発動した後に「どのケースで何をするか」を引く表で、
**新しい条件を足さない**（足すなら description にも書く。body だけに書いた条件では発動しない）。

| トリガー | やること |
| --- | --- |
| 仕様変更・機能実装があった（中規模以上の仕上げ） | コミット前に project docs / agent-facing 文書の更新要否を判定し更新する |
| AGENTS / skills / prompts / references を新規・編集した | コミット前に品質パスを実行する。規模不問 |
| 使用した AGENTS / skills の不備（誤誘導・欠落・冗長・手順の摩擦）に気づいた | 反映先と可否は `~/.agents/AGENTS.md` の層契約に従う。直した agent-facing 文書は品質パスを通す |
| **skills の構造を変えた**（状態・工程・層・共有ファイルの増減） | **`agents/docs/` の図を引き直す**（図は機械検査に掛からない。索引のずれだけが手順 1 の `derived` で落ちる）。**leaf 以外の層で skill を増減したら** `scripts/layers.tsv` も直す。文言修正では引き直さない |

規模 SSOT は `~/.agents/AGENTS.md`。

## 契約

- 下書きは判断材料の抜け漏れを優先してよい。品質は品質パスが担保する
- 該当トリガーをすべて完了して docs 完了。未完了なら commit しない
- レビュアーは subagent。委譲の契約は `references/review-contract.md`。subagent を持たない harness は、編集の性質を問わず自己レビューで代替する
- **自己レビューで済ませてよいのは次の両方を満たすときだけ。**どちらかを外れたら委譲する
  - 変更が **1 ファイル**に収まる
  - 既存の規則の言い換え・typo・表記であって、**新しい規則・条件・判断基準を足していない**
- **迷ったら委譲する。**自己レビューは tokens こそ少ないが**読んだものが全部自分の context に乗る**。
  委譲すれば tokens は増えても context は汚れない。常駐セッションでは context の方が先に枯れるので、
  「重いから自分で読む」は逆向きの最適化になる

## 品質パス（基準 + 手順）

agent-facing 文書の品質 SSOT。global も project も同じ。

基準:

- **抜け漏れなく、要点だけ**: 判断に必要な不変条件・境界・例外は落とさない。言い換えの重複・経緯・メタ説明は書かない
- **AGENTS / skills は薄く**: 発動条件・判断・恣意的な規約（命名・境界・優先順位の決定）・SSOT への誘導に留め、モデルが自力で再導出できる一般ベストプラクティスは書かない。方向性を定める文（基準の高さ・どちらに倒すか）は残し、挙動を変えない飾り文だけ削る。状況限定の詳細・事例は `references/` へ。数行で書ける知見は reference を新設せず本文で圧縮する
- **行動を変えられる具体性**: 何をするか / 何をしないか / SSOT はどこかを明示する。装飾・自己言及は削る
- **非自明な境界を持つ API は動く正例を残す**: prose の言い換えで代替しない。入口では詳細カタログを複製せず深い SSOT へ誘導する
- **repo 内で完結させる**: Issue / PR 番号等の外部リンクを張らない。仕様・判断は文書本文に書き、参照は repo 内へ張る
- **確立した技術用語は訳さない**: `dead code` `stale` `advisory` `lease` 等は英語のまま使う。訳すと判定範囲がぼやける（`dead code` →「不要なコード」にすると「動くが要らない」まで含み、到達不能という機械的判定が失われる）。確立した英語名が無い概念は説明的な日本語で書く
- **図は文章や表より速く読めるときだけ**: 直列手順は箇条書き、分類は表の方が短い。**表せるものに合った図種を選ぶ**（分岐は `flowchart`、状態遷移は `stateDiagram-v2`、登場人物のやりとりは `sequenceDiagram`、構造は `classDiagram` / `erDiagram`…）。**禁止は experimental な図種（`*-beta`）だけ** — レンダラが追随しておらず壊れて表示されうる
- **ゲート系 skill は置き換える生コマンド名にする**: `git commit` を塞ぐなら commit、`gh issue create` なら issue というように、名前から対応が引ける。語が既存の skill と衝突するときだけ別語にする（`gh pr merge` は merge が埋まっているので ship）。それ以外の skill 名は自由
- **発動条件は description に書く**: description が発動判定に使われ、本文は発動後にしか読まれない。**本文にだけ書いた条件は永久に発動しない。**本文側は「どのケースで何をするか」の対応に留め、条件そのものを新設しない（発動後のモード分岐は条件ではないので本文でよい）
- **skill 本文は同じ層と上位層を参照しない**: 参照は上位層 → 下位層の一方通行。単体で完結する skill（leaf）の本文に他 skill 名を書かない。順序と棲み分けは上位層の skill が持つ。**skill を分割した直後が危ない** —「前段は〜」「〜へ渡す」を書いた瞬間に崩れる。**例外は skill 自体を対象にする skill**（`docs` / `skill-creator`）で、対象としての名指しは可
- **1 件を扱う skill に、複数件の状態で決まる制約を持たせない**: 在庫上限・同時数・順番待ちは
  キューを回す上位層の都合。書くと**人が 1 件を直接頼んだときに依頼を断る**skill になる。
  持ってよいのはその 1 件の中で完結する制約だけ
- **文書どうしが実行可能に噛み合うか**: 1 ファイルが読めることと、複数を順に読んで動けることは別。
  A が「X を待ってから Y」、B が「Y があってから X を出す」と書けば、どちらも単体では正しいのに
  **合わせるとデッドロックする**。同じ状態遷移・同じ差し戻し先・同じ数値を扱う文書は、
  **並べて突き合わせないと矛盾が見えない**

手順:

1. `sh <skills root>/docs/scripts/audit-skills.sh <skills root>` を実行する。**スクリプトも root も、編集している checkout のものを使う** — `~/.agents/skills` は別 checkout への symlink なので、worktree で既定に頼ると別のツリーを古いスクリプトで検査して通る。見るのは skills root 配下と、その隣の `shared/` `docs/`。どれにも触れていない編集（project の AGENTS.md だけ等）では飛ばし、**飛ばしたことをレビュアーに伝える**（黙ると検査済みと誤認される）。**`SUMMARY` 行が出なければ検査は走っていない**（root 不在等）ので、root を直して実行し直す。`VIOLATION` は次へ進む前に直す。ただし層違反は `scripts/layers.tsv` の更新漏れでも出る。**そのときの直す先はデータ側で、文書ではない。**`REVIEW` は機械では意味を判定できない候補なので、棄却せずレビュアーへ渡す。**取れるのは実在・形・重複だけで、しかも skill 名はバッククォート付きしか拾えない。**出力が空でも基準を満たした証明にはならない
2. 節単位で書き直して基準へ適合させる。太字剥がし・言い換え削除だけの diff は不合格
3. 大型 reference（約 300 行超）は、節ごとの書き直しで壊れた見出し階層・表 / fence を潰す第 2 パスを親が行う
4. レビュアーに出す。渡すのは対象ファイルのパス（節を絞るならその名前）・上記の基準・`references/review-contract.md`・手順 1 の出力（`REVIEW` は棄却可否と実害を判定させる）・「前提を知らない読み手がこの文だけで実行できるか」という問い・下の探索観点。執筆意図・経緯・何を直したかは渡さず、git 履歴も参照させない
   - **起点だけでなく、その規則が関係する文書をまとめて渡す。**1 ファイルだけ渡すと、基準の大半（重複・矛盾・数値の二重化）が原理的に検出できない
   - **探索観点は毎回そのまま渡す**（基準を再解釈させると読みやすさの指摘に流れる）:
     1. 同じ規則・同じ理由が複数箇所に実体として書かれていないか（ファイル内・ファイル間の両方）
     2. 数値・既定値が 2 箇所以上に実体として書かれていないか
     3. 表とその直後の散文が同じことを言っていないか
     4. 参照先の節・ファイルが実在するか
     5. **複数の文書を順に読んだとき、実行できるか**（順序・前提条件・差し戻し先が噛み合うか）
     6. **削ると判断ができなくなる記述**はどれか（残すべき理由つきで挙げさせる）
   - 6 を必ず入れる。**入れないと、事故のたびに足された一文が「冗長」に見えて消える**
   - 自己レビューでは隔離が作れないので、基準 1 項目ずつに対象を照らす通し読みへ置き換える
   - `references/review-prompt.md` は更新判定用。品質基準を含まないので品質パスには使わない
5. 指摘を適用する。実害があるものは起点外でも直す。棄却は理由を 1 行残す。レビュアーが「提案」と書いたことは棄却の理由にしない
6. 適用した修正があったら、手順 1 をやり直してから 1 度だけ再レビューする（**自己レビューのときに省くのは再レビューだけ。手順 1 はやり直す**）。2 巡目には棄却済み一覧も渡して蒸し返しを止める。2 巡目の指摘も 5 と同じ扱いで、3 巡目には入らない
7. プロジェクトに Markdown lint があれば通す
8. 適用と棄却を簡潔に報告する（棄却理由の行き先はここ。2 巡目で渡した一覧はレビューの終わりで消える）

コスト目安はレビュー 1 巡 40〜70k tokens。**巡回数は削らない** — 2 巡目は 1 巡目の修正が生んだ穴（条件の欠落・語の二重定義・範囲の食い違い）を拾うので、そこが一番落としてはいけない。委譲するか自分で読むかは「契約」の 2 条件で機械的に決まるので、都度の裁量で軽くしない。

**完了条件**: 品質パス開始時点の下書きと比べて、必要な判断情報の被覆を維持または改善し、より短く明確になっていること。行数だけが減った変更や構造が壊れた変更は未完了。自己レビューで足りる編集は、編集した節に基準違反が無ければ完了。

## project docs 更新判定

確立済みの知見の永続化判定と、触った docs 周辺の削除・最新化。新しい設計原則の発見器ではない。追加の前に削れる箇所を先に洗う。起点外でも削れる・直せる記述は直し、テーマが完全に別の大規模再構成だけ別提案にする。

1. `git status --short` で起点を確定する（混在 working tree は絞る。起点と diff の食い違いは報告）
2. 材料を整理する: **知見**は検証可能な罠・正解パターン。**設計上の選択**は「A ではなく B」の主張で照合対象。単独で一般原則にしない
3. `references/review-prompt.md` に起点・知見・選択を埋めて渡す
4. 妥当な更新は起点外でも適用する
5. 更新・見送りを簡潔に報告する

**完了条件**: 起点に対する更新要否を判定し、要なら適用済み、不要なら見送り理由が言えること。
