# ドキュメント

## いつ

| トリガー | やること |
| --- | --- |
| 仕様変更・機能実装があった（中規模以上の仕上げ） | コミット前に project docs / agent-facing 文書の更新要否を判定し更新する |
| AGENTS / skills / prompts / references を新規・編集した | コミット前に品質パスを実行する。規模不問 |
| 使用した AGENTS / skills の不備（誤誘導・欠落・冗長・手順の摩擦）に気づいた | 反映先と可否は `~/.agents/AGENTS.md` の層契約に従う。直した agent-facing 文書は品質パスを通す |

規模 SSOT は `~/.agents/AGENTS.md`。

## 契約

- 下書きは判断材料の抜け漏れを優先してよい。品質は品質パスが担保する
- 該当トリガーをすべて完了して docs 完了。未完了なら commit しない
- レビュアーは subagent。委譲の契約は `review-contract.md`。読み手の行動が変わらない編集（typo・表記・等価な言い換え）は自己レビューでよい。subagent を持たない harness は、編集の性質を問わず自己レビューで代替する

## 品質パス（基準 + 手順）

agent-facing 文書の品質 SSOT。global も project も同じ。

基準:

- **抜け漏れなく、要点だけ**: 判断に必要な不変条件・境界・例外は落とさない。言い換えの重複・経緯・メタ説明は書かない
- **AGENTS / skills は薄く**: 発動条件・判断・恣意的な規約（命名・境界・優先順位の決定）・SSOT への誘導に留め、モデルが自力で再導出できる一般ベストプラクティスは書かない。方向性を定める文（基準の高さ・どちらに倒すか）は残し、挙動を変えない飾り文だけ削る。状況限定の詳細・事例は `references/` へ。数行で書ける知見は reference を新設せず本文で圧縮する
- **行動を変えられる具体性**: 何をするか / 何をしないか / SSOT はどこかを明示する。装飾・自己言及は削る
- **非自明な境界を持つ API は動く正例を残す**: prose の言い換えで代替しない。入口では詳細カタログを複製せず深い SSOT へ誘導する
- **repo 内で完結させる**: Issue / PR 番号等の外部リンクを張らない。仕様・判断は文書本文に書き、参照は repo 内へ張る

手順:

1. 節単位で書き直して基準へ適合させる。太字剥がし・言い換え削除だけの diff は不合格
2. 大型 reference（約 300 行超）は、節ごとの書き直しで壊れた見出し階層・表 / fence を潰す第 2 パスを親が行う
3. レビュアーに出す。渡すのは対象ファイルのパス（節を絞るならその名前）・上記の基準・`review-contract.md` のレビュアー行・「前提を知らない読み手がこの文だけで実行できるか」という問い。執筆意図・経緯・何を直したかは渡さず、git 履歴も参照させない
   - 自己レビューでは隔離が作れないので、基準 1 項目ずつに対象を照らす通し読みへ置き換える
   - `references/review-prompt.md` は更新判定用。品質基準を含まないので品質パスには使わない
4. 指摘を適用する。実害があるものは起点外でも直す。棄却は理由を 1 行残す。レビュアーが「提案」と書いたことは棄却の理由にしない
5. 適用した修正があったら、1 度だけ再レビューする（自己レビューのときは省く）。2 巡目には棄却済み一覧も渡して蒸し返しを止める。2 巡目の指摘も 4 と同じ扱いで、3 巡目には入らない
6. プロジェクトに Markdown lint があれば通す

コスト目安はレビュー 1 巡 40〜70k tokens で、数ファイルの編集ではレビューが変更本体より重くなる。それでも 2 巡目は 1 巡目の修正が生んだ穴（条件の欠落・語の二重定義・範囲の食い違い）を拾うので、削るなら巡回数ではなく自己レビューで足りる範囲の判定を精度良くする。

**完了条件**: 品質パス開始時点の下書きと比べて、必要な判断情報の被覆を維持または改善し、より短く明確になっていること。行数だけが減った変更や構造が壊れた変更は未完了。自己レビューで足りる編集は、編集した節に基準違反が無ければ完了。

## project docs 更新判定

確立済みの知見の永続化判定と、触った docs 周辺の削除・最新化。新しい設計原則の発見器ではない。追加の前に削れる箇所を先に洗う。起点外でも削れる・直せる記述は直し、テーマが完全に別の大規模再構成だけ別提案にする。

1. `git status --short` で起点を確定する（混在 working tree は絞る。起点と diff の食い違いは報告）
2. 材料を整理する: **知見**は検証可能な罠・正解パターン。**設計上の選択**は「A ではなく B」の主張で照合対象。単独で一般原則にしない
3. `references/review-prompt.md` に起点・知見・選択を埋めて渡す
4. 妥当な更新は起点外でも適用する
5. 更新・見送りを簡潔に報告する

**完了条件**: 起点に対する更新要否を判定し、要なら適用済み、不要なら見送り理由が言えること。
